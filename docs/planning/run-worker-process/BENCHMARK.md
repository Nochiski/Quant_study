# run 실행 방식 측정 기록

[설계 spec](../../superpowers/specs/2026-10-19-run-worker-process-design.md)의 근거다. 성능 주장은 이 절차로 다시 잰 숫자로만 한다.

## 환경

- 2026-10-19, Windows 10 Home, 논리 코어 12개, RAM 15.9GB, Python 3.11, Rust `backtest_core`(release, 그날 다시 빌드)
- 데이터: 로컬 원장 `~/quant-ledger/data/equity`(2026-09-21 동기화, 2010-01-04~2026-09-18), duckdb 어댑터
- 전략: 12-1 모멘텀(252세션 수익률, 최근 21세션 제외), 기준일 거래대금 상위 30%, 월별 20종목, 종목당 5%,
  유니버스 `krx.common-stock`, 기본 비용, Rust 코어
- 상시 부하: 메신저·백신·브라우저 자동화 등 약 3~4코어. 측정마다 시스템 전체 사용 코어를 함께 적는다.

## 절차

1. 스레드 측정은 **측정 전용 서버**를 대상으로 한다. 라이브 DB·산출물에 측정 run이 쌓이지 않게 경로를 임시 디렉터리로 준다:
   `STRATEGY_WORKBENCH_DB_PATH`·`STRATEGY_WORKBENCH_RESEARCH_DB_PATH`·`STRATEGY_WORKBENCH_CONTINUOUS_DB_PATH`·
   `STRATEGY_WORKBENCH_ASSISTANT_DB_PATH`·`STRATEGY_WORKBENCH_ARTIFACT_ROOT`, 그리고 `STRATEGY_WORKBENCH_EQUITY_ADAPTER=duckdb`·
   `STRATEGY_WORKBENCH_EQUITY_ROOT`. 2026-10-19 측정은 개발 서버에 직접 보냈다(인라인 초안이라 계열·N은 늘지 않았다).
   서버에 도는 run이 없는지 확인한다.
2. 구간마다 **워밍업 run 1회**를 별도 프로세스로 돌려 버린다(OS 파일 캐시).
3. 측정 중에는 테스트·빌드 같은 무거운 작업을 돌리지 않는다.
4. 측정 방식:
   - **스레드**: 서버에 `POST /api/v1/backtests`를 보내고, 끝날 때까지 0.25초 간격으로 `GET /health`를 잰다. 동시 2개는
     초기자본을 1원 다르게 준다. 같은 요청은 진행 중인 run에 합쳐지기 때문이다(US-SM-11).
   - **프로세스**: 시제품 스크립트가 새 프로세스에서 `build_http_app`(경로는 모두 임시 디렉터리)을 조립하고 같은 요청을 돌린다.
     그동안 서버 `GET /health`를 같은 간격으로 잰다.
5. 시작일은 모두 2020-01-02 이후다(`holdout-window.md`). 10년 구간은 2016~2019 홀드아웃을 열게 되어 재지 않는다.

재현 명령(전략은 [bench-strategy.yaml](./bench-strategy.yaml), 서버는 duckdb 어댑터로 떠 있어야 한다):

```sh
cd backend
uv run --no-sync --with psutil python scripts/bench_run_isolation.py \
  ../docs/planning/run-worker-process/bench-strategy.yaml \
  --start 2025-01-02 --end 2025-12-30 --mode thread --parallel 2 --server http://127.0.0.1:8000
# --mode process 는 run 마다 새 프로세스로 돌리고, --server 를 주면 그동안의 서버 응답도 잰다
```

## 결과

### 1. 실행 방식(스레드 대 별도 프로세스), 1년 구간 2025-01-02~2025-12-30, 조용한 상태

| 방식 | run 벽시계 | 부팅 | 서버 `GET /health` p50 / p95 / 최대 | 시스템 사용 코어 |
|---|---|---|---|---|
| 스레드 1개 | 44.6초 | - | 475.8 / 721.4 / 1,421ms | 2.1 |
| 프로세스 1개 | 37.4초 | 3.8초 | 2.0 / 2.4 / 380ms | 2.4 |
| 스레드 2개 동시 | 각 83.1초 | - | 1,219.7 / 1,837.2 / 2,614ms | 2.5 |
| 프로세스 2개 동시 | 각 39.7초 | 각 3.3초 | 2.2 / 3.2 / 125ms | 3.6 |

- 스레드 2개는 혼자 실행의 1.86배가 걸린다. GIL이 두 run을 직렬로 돌린다. 프로세스 2개는 혼자 실행과 거의 같다(진짜 병렬).
  run 2개를 끝내는 데 스레드는 83초, 프로세스는 44초다(처리량 1.9배).
- run이 도는 동안 API p95는 스레드 721ms, 프로세스 2.4ms다(약 300배). 프로세스 값은 부모가 worker 진행 줄을 파싱하지 않는 시제품(유휴 서버) 값이다. 실제 제품 경로 값은 W3-01이 다시 잰다.
- 1년 run 하나의 최대 RSS는 2.0GB다. 2개를 동시에 돌리면 가용 메모리가 1.8GB까지 떨어졌다.

올리고 저장된 지문·같은 입력 잇기의 단절을 받아들여야 한다.

### 5. 열 지향(numpy) 시제품과 GPU(CuPy)

시제품은 어댑터가 실제로 보내는 격자 SQL을 가로채 Arrow로 받고, 같은 의미(종목별 252칸 창·lag 21·가림, 거래대금 상위 floor(N×0.3),
값 내림차순·security_id 오름차순 동점 처리, 상위 20)로 계산했다. 선정 종목을 실제 tape와 프레임마다 대조했다.

| 구간 | 격자 행 | 현재 tape | SQL→Arrow | 배열 변환 | 계산 | 프레임 일치 |

| 1년 | 1,196,759 | 약 36초(run 기준) | 4.7초(부하 중) | 0.14초 | 0.13초 | 11/11 |
| 6.7년 | 4,213,109 | 247초 | 2.2초 | 0.43초 | 0.74초 | 80/80 |

- 같은 SQL 결과를 Python 튜플로 받으면 14초(6.7년), Arrow로 받으면 2.2초다.
- 6.7년 tape는 247초에서 약 3.4초가 된다(약 70배). 이 숫자는 이 전략이 쓰는 연산만 다룬다. 전 언어로 넓힐 때의 추가 비용은 spec 10절을 본다.

### 6. 예비 worker(W2-01, spec D7·V-5·V-7)

2026-10-20, 같은 PC. 측정 중 이 작업의 다른 테스트·빌드는 돌리지 않았다(다른 세션의 상시 부하는 있었다).

재현 명령(시작 지연·유휴 비용, 프로세스 방식 앱 둘을 임시 경로로 조립한다):

```sh
cd backend
uv run --no-sync --with psutil python scripts/bench_run_start.py \
  ../docs/planning/run-worker-process/bench-strategy.yaml \

# mock: --equity-adapter mock --start 2026-01-02 --end 2026-02-20
```

접수(202)부터 첫 `tape` 진행까지. 예비와 직접 띄우기를 3회 번갈아(회마다 앞뒤를 바꿔) 재고, tape 에 들면 취소했다.
절차 2의 워밍업 run 은 돌리지 않았다. 재는 구간이 tape 에 드는 순간까지라 OS 파일 캐시가 데우는 데이터 적재를 거의 지나지 않고,
두 방식이 같은 파일을 번갈아 읽어 캐시 상태가 같으며, 3회 최솟값이 첫 회의 차가운 캐시를 걸러 낸다.

| 데이터 | 예비 worker(최소 / 중앙) | 직접 띄우기(최소 / 중앙) | V-5(≤ 0.5초) |
|---|---|---|---|
| 실데이터(duckdb, 1년 2025-01-02~2025-12-30) | 0.036 / 0.036초 | 1.871 / 1.922초 | 통과 |
| mock | 0.028 / 0.029초 | 1.613 / 1.652초 | 통과 |

- 직접 띄우기 1.6~1.9초는 spec 2절의 부팅 6.2초보다 짧다. 그 값은 OS 파일 캐시가 차기 전 5년 run 의 부팅이고, 이번은 같은 앱에서
  연달아 띄운 값이다.

job 을 기다리는 예비 하나의 유지 비용(60초, Windows venv 런처 + 인터프리터 두 프로세스의 합):

| 데이터 | working set | private(commit) | CPU |
|---|---|---|---|
| 실데이터(duckdb) | 78.1MB | 410.4MB | 0.0%(한 코어 기준) |
| mock | 58.8MB | 400.6MB | 0.0% |

- 기다리는 동안 worker 는 Windows 에서 20ms 간격으로 stdin 파이프를 들여다보지만(`_StdinPipe`) CPU 는 측정 한계 아래였다.
- working set 은 Windows 가 유휴 프로세스에서 덜어 내 spec D7 의 118MB 보다 작게 보인다. 예비는 늘 떠 있으므로 메모리 가드(W2-02)가
  읽는 가용 물리 메모리에는 이미 빠져 있다.

V-7 전체 `npm run test:e2e`(Windows, mock, 95개 테스트). 스레드(기본)와 프로세스(`STRATEGY_WORKBENCH_RUN_ISOLATION=process`, 예비 worker
기본)를 T·P·P·T·T·P 순서로 3회씩 돌렸다. 벽시계는 타입 검사·빌드를 포함한 명령 전체이고, Playwright 값은 그 보고(0.1분 단위)다. 다른 e2e 와
겹치지 않게 잠금과 전용 포트(`PW_BACKEND_PORT`·`PW_PREVIEW_PORT`)로 돌렸다.

| 방식 | 1회 | 2회 | 3회 | 최소 | 평균 |
|---|---|---|---|---|---|
| 스레드 벽시계 | 990초 | 987초 | 993초 | 987초 | 990초 |
| 프로세스 벽시계 | 994초 | 1,005초 | 1,015초 | 994초 | 1,005초 |
| 스레드 Playwright | 16.1분 | 16.1분 | 16.2분 | 16.1분 | |
| 프로세스 Playwright | 16.2분 | 16.4분 | 16.6분 | 16.2분 | |

- 최소끼리 +0.7%(7초), 평균끼리 +1.5%(15초)다. V-7(≤ 5%)을 통과한다.
- 프로세스 2회의 실패 1건(US-DM-15)은 worker 와 무관한 locator 결함이었다. 이름 일부 일치(`name: "홈"`)가 그 테스트가 저장한 전략 링크도
  잡아, 최근 작업 목록이 먼저 그려진 회차에 strict mode 로 실패했다. `exact: true` 로 고친 뒤 스레드 2·3회와 프로세스 3회는 모두 통과했다.
- e2e 서버의 예제 앱(`tests/e2e_ideas_app.py`의 `ideas`)은 조립 때만 바꿔 낀 mock 어댑터를 쓰므로 worker 가 같은 데이터를 다시 만들 수
  없다. 그래서 이 앱은 설정과 무관하게 스레드 방식이다. 측정 대상은 주 앱의 run 이다.

V-3 실데이터(duckdb, 1년 2025-01-02~2025-12-30, bench 전략): 스레드 방식과 예비 worker 로 같은 요청을 차례로 돌렸다. `run_fingerprint`·
`target_tape_hash`·`data_snapshot_id`·`engine_version`·지표가 같고, run_id·시각을 뺀 결과 전체의 해시가 같았다(`137923fe7879bccc`).
run 시간은 38.9초 대 38.7초다. 최장 허용 구간(2020-01-02~)은 run 하나가 약 7GB 를 쓰는데 같은 PC 에 다른 작업이 돌고 있어 이번에는 재지
않았다(W3-01 재측정 몫).

### 7. 메모리 가드(W2-02, spec D8)

2026-10-20, 같은 PC. 다른 세션의 에이전트가 함께 돌아 시작 때 가용 물리 메모리가 약 4.5GB 였다. 이 작업의 다른 테스트·빌드는
돌리지 않았다. run 은 한 번에 하나만 돌렸다(스크립트가 시작 전 가용 메모리가 예약치보다 작으면 멈춘다).

재현 명령(프로세스 방식 앱을 임시 경로로 조립하고 부모 로그에서 예약치·최대 RSS 를 모은다):

```sh
cd backend
uv run --no-sync python scripts/bench_run_memory.py \
  ../docs/planning/run-worker-process/bench-strategy.yaml \
  --start 2025-01-02 --end 2025-12-30 --equity-root ~/quant-ledger/data/equity \
  --experiment-start 2023-01-02 --experiment-end 2024-12-30
```

예약치(추정식) 대 worker 가 보고한 최대 RSS(실데이터 duckdb, bench 전략, Rust 코어). GB 는 2³⁰ 바이트다.

| 구간 | 세션 수 어림(평일 + 워밍업) | 읽은 세션 | 원시 관측 행 | 예약치 | 최대 RSS | 예약치 ÷ 최대 RSS | run |
|---|---|---|---|---|---|---|---|
| 1년 2025-01-02~2025-12-30 | 531 | 514 | 1,196,759 | 2.54GB | 1.93GB | 1.31 | 41.3초 |
| 2년 2024-01-02~2025-12-30 | 793 | 758 | 1,742,841 | 3.52GB | 2.97GB | 1.19 | 63.1초 |
