# GPT 자문 — 소스 표기 분산·서식 드리프트를 설계로 줄이는 법 (2026-09-28)

> 요청 맥락: `scratchpad/db_design_context.md`(최근 2주 결함 8유형·현 설계 요약). 모델 gpt-6-astra(codex exec, read-only). 아래 §1 은 답변 원문, §2 는 우리 코드 사실과의 대조·채택 판단(오케스트레이터).

## 1. 답변 원문

현재 설계의 핵심 공백은 **“같은 입력을 일관되게 처리했는가”에 비해 “원래 있어야 할 정보를 제대로 추출했는가”를 확인하는 장치가 약하다는 점**입니다. 해시·행수·PIT 검사가 모두 통과해도 금융업 전체가 NULL이거나 오래된 추정치가 남을 수 있습니다. 아래 평가는 제공된 설계 설명 기준입니다.

**1. 소스 표기 분산·서식 드리프트를 설계에서 다루는 방법**

**① 정규화는 표기 정리와 의미 판정을 나눕니다.**

현재 층을 유지하면서 책임을 다음처럼 명확히 하는 편이 좋습니다.

| 위치 | 책임 | 이 시스템에 적용할 예 |
|---|---|---|
| raw | 받은 응답과 수집 사실 보존 | HTML/XML/JSON 원문, 요청 조건, 수집 시각, 응답 해시 |
| stage | 소스 구조 해석, 형변환, 검색용 표기 정리 | 원본 계정명과 공백 정리 계정명 병존, 실제 응답의 연결·별도 구분 추출 |
| equity 입구의 canonical 로직 | 표준 개념 선택과 의미 확정 | 업종별 순이익 코드 대응, CAPEX 집계·상세 선택, 단위·부호·기간 판정 |
| equity 파생·모델 | 확정된 의미에 기반한 계산 | 비율·점수·유니버스 구성 |

canonical을 위해 별도 저장소나 67개 표의 복제본을 만들 필요는 없습니다. 기존 equity 입구에 뷰·함수·대응표로 구현하면 됩니다.

공백 제거는 **후보 검색 규칙**이지 동일 계정이라는 증거가 아닙니다. 정확 일치 우선은 타당하지만, 정확 일치도 재무제표 종류·연결 여부·기간·단위·차원을 확인한 뒤 적용해야 합니다. 같은 값이라는 이유만으로 의미가 다른 후보를 하나로 취급해서도 안 됩니다.

CAPEX는 집계행이 있으면 상세행과 중복 합산하지 않고, 상세행만 있으면 서로 중복되지 않는 구성항목인지 확인합니다. 부호는 행의 의미와 소스 규칙에 따라 변환하고, `abs()` 일괄 적용은 피해야 합니다.

**② NULL을 결과값과 실패 상태로 분리합니다.**

SQL NULL만으로는 다음 상황을 구별할 수 없습니다.

- `not_applicable`: 해당 지표가 적용되지 않음
- `source_missing`: 해당 원문에 값이 없음
- `fetch_failed` / `parse_failed`: 수집 또는 구조 해석 실패
- `unmapped`: 값은 있으나 대응 규칙이 없음
- `ambiguous`: 복수 후보의 의미나 값이 충돌함

신선도는 별도 상태로 두는 편이 좋습니다. 값은 유효하게 파싱됐지만 낡을 수 있기 때문입니다.

기존 `_reject`는 **입력 행 자체가 만들어지지 않은 경우**를 놓칠 수 있습니다. 수집 요청 목록이나 공시 목록에서 예상 처리 대상을 만들고, 대상마다 성공·정상 결측·실패 중 하나의 결과가 남도록 해야 합니다. 정정 공시가 100건인데 표지 파서 결과가 0건이면, reject가 0건이어도 실패입니다.

**③ 출처 라벨은 요청 의도가 아니라 실제 선택 근거를 기록합니다.**

`revenue_basis`, `capex_basis`를 다음 정보와 연결하십시오.

- 실제 응답의 연결·별도 구분
- 원문 식별자와 선택한 행 식별자
- 적용한 규칙 ID, 선택 방식과 후보 수
- 단위·부호 변환, 원본 기간
- 파서·매핑 버전

모든 파생 컬럼에 메타데이터를 반복할 필요는 없습니다. 별도 근거 테이블을 두고 참조해도 됩니다. WISE 연결 요청 실패 후 별도로 대체했다면, **값과 실제 기준을 함께 바꾸고 대체 사실을 기록**해야 합니다.

**④ 파서와 대응표를 버전화하고, 보존 원문에서 재처리합니다.**

SQLite에 “파싱된 행”만 저장한다면 원장 사본을 고정해도 파서 오류는 복구할 수 없습니다. 먼저 재파싱 가능한 원문이 남아 있는지 확인해야 합니다.

빌드에는 입력 스냅샷 ID, 코드 커밋, 파서·매핑 버전, 의존성·설정, 판정 기준시각을 기록합니다. 수정 시 영향받는 소스·서식·기간과 하류만 재처리합니다. SQLMesh도 상류 오류 수정 후 지정 기간과 하류를 다시 계산하는 restatement를 지원합니다. 여기서 필요한 것은 이러한 재처리 원칙이며, 도구 교체는 필수가 아닙니다. [SQLMesh 재처리 문서](https://github.com/SQLMesh/sqlmesh/blob/main/docs/concepts/plans.md)

재파싱 시각을 원래 데이터의 `available_date`로 덮어쓰면 안 됩니다. 공개 시각, 시스템 최초 관측 시각, 재처리 시각을 구별하고, 과거 공개정보를 복원하는 백테스트와 당시 시스템이 실제 알던 정보를 재현하는 실행을 구분해야 합니다.

**⑤ 자동 학습은 대응표 후보 발굴에 활용합니다.**

1인 운영에서는 버전 관리되는 명시적 대응표가 적합합니다. 소스·업종 템플릿·재무제표·연결 여부·적용 기간 등을 조건으로 두고, 매칭 방식·우선순위·집계 방식·근거를 기록하십시오.

문자열 유사도나 LLM은 미매핑 계정의 후보를 찾는 데 쓸 수 있습니다. 운영값에 자동 반영하는 대신, 빈도와 영향 종목 수가 큰 후보부터 원문 확인 후 대응표와 픽스처에 추가하는 방식이 관리하기 쉽습니다.

**⑥ 골든 데이터·계약·운영 감시는 서로 다른 역할을 맡깁니다.**

- **골든 데이터:** 연결/별도, 금융업별 템플릿, 집계/상세, 혼재 부호, 공백 충돌, 정정 표지 신·구 서식, 비12월 결산 등 *형태의 다양성*을 보장합니다.
- **계약:** 키·타입뿐 아니라 연결 기준, 기간, 단위, 정상 결측 조건, 허용 신선도를 선언합니다.
- **운영 감시:** 실제 유입 데이터에서 새 서식·미매핑·모호성·결측 증가를 찾습니다.
- **외부 대사:** 내부 규칙이 일관되게 틀리는 경우를 찾습니다. 동일 기업·기간·연결 기준·단위·정정 판본을 맞춘 뒤 비교해야 합니다. 동일 원천을 재판매하는 두 소스의 일치는 독립 검증으로 보기 어렵습니다.

고정 입력 테스트와 실제 실행 결과 검사는 별개입니다. SQLMesh도 이를 tests와 audits로 구분하고 실행 결과에 대한 차단 검사를 제공합니다. [SQLMesh audits 문서](https://sqlmesh.readthedocs.io/en/latest/concepts/audits/)

**2. 빠진 것과 과한 것: 1인 운영 우선순위**

비용은 기존 배치·계약 코드를 활용한다는 전제의 **초기 구현 인일 추정**입니다. 대규모 원문 복구와 과거 전체 재처리 시간은 제외했습니다.

| 순서 | 우선순위 | 제안 | 막거나 조기에 발견하는 결함 | 비용 |
|---|---|---|---|---|
| 1 | 상 | 기존 전 컬럼 diff를 정식 배포 게이트로 만들고, 버전 변경 시 해시 검사와 변경 검사를 분리 | 규칙 수정으로 생기는 값→NULL, 잘못된 합산·부호·라벨 변경. 특히 ②③④⑧ | 1~2일 |
| 2 | 상 | 핵심 지표부터 NULL 사유·처리 결과를 기록하고, 예상 대상 기준의 그룹별 커버리지 감시 | 연결 고정 수집, 업종별 미매핑, 파서 전체 실패. ①②③④⑤ | 2~3일 |
| 3 | 상 | 종목·지표별 정보 신선도 계약과 기준시점별 판정 이력 저장 | 오래된 추정치 잔존, 최신 판정으로 과거 실행 검사. ⑥⑦ | 1~2일 |
| 4 | 중 | canonical 선택 근거·실제 연결 기준·파서/매핑 버전을 연결하고 원문 재파싱 경로 확보 | 라벨과 값 불일치, 원인 추적 불가, 수정 후 복구 곤란. ①~⑤ | 3~5일 |
| 5 | 중 | 27개 골든 픽스처의 유형별 커버리지 점검 및 최근 결함 원문 추가 | 기존에 고친 변형의 재발, 기간·부호·충돌 처리 회귀. ①~⑤⑧ | 1~2일, 이후 결함 수정에 포함 |
| 6 | 하 | 위험 유형별 소수 표본의 원문·외부 소스 대사 | NULL은 아니지만 일관되게 잘못된 값·기간·연결 기준 | 초기 1일, 이후 주 1~2시간 |

유지할 것은 입력 고정, PIT 불변식, 원문 보존, 격리, 핵심 계약입니다. **테스트 1,420개와 표 97개라는 숫자만으로 과잉이라고 판단할 수는 없습니다.**

다만 다음은 조정할 필요가 있습니다.

- **전체 격리 비율 ≤3%를 충분조건으로 삼는 것:** 금융업 전체의 실패가 전체 분모에 묻힐 수 있습니다. 핵심 지표·업종·서식별 검사를 추가해야 합니다.
- **`RULES_VERSION` 변경 시 재현성 검사를 통째로 skip하는 것:** 버전 간 동일 해시는 요구할 수 없지만, 새 버전 내부의 결정성과 구버전 대비 변경 범위는 계속 검사해야 합니다.
- **모든 표·컬럼에 동일한 강도의 감시를 추가하는 것:** 점수·유니버스·PIT에 직접 쓰는 항목부터 시작하십시오.
- **별도 품질 플랫폼, 자동 매핑 모델, 대규모 canonical 재구축:** 지금은 기존 DuckDB SQL과 작은 품질 이력 테이블로 구현할 수 있는 범위가 큽니다.

**3. 조용한 NULL·낡음을 드러내는 장치와 회귀 검증**

**저비용 감시의 핵심은 분모·시계·그룹을 제대로 잡는 것입니다.**

| 장치 | 구체적인 검사 | 초기 운영 방식 |
|---|---|---|
| 예상 대상 대조 | 수집·공시 목록과 처리 결과를 LEFT JOIN하여 결과 없는 대상 탐지 | 처리 결과 자체가 없으면 즉시 오류 |
| 조건부 파싱 성공률 | 정정 공시 중 해당 필드가 기대되는 문서에서 추출 성공률 계산 | 기대 문서가 있는데 전부 실패하면 차단 |
| 그룹별 유효값 비율 | 소스×업종×연결 기준×지표별 성공 건수/예상 건수 | 전부 NULL이면 차단, 부분 하락은 영향 건수와 함께 경고 |
| 종목별 정보 나이 | 판정시각−소스 갱신일 또는 검증 가능한 정보 기준일 | 지표별 상한 초과 시 모델 사용 제한·유니버스 제외 |
| 해석 경로 변화 | 미매핑·모호성·대체 규칙 사용률, 실제 연결 기준 분포 | 새로운 미매핑과 대체 사용 급증을 요약 |
| 값의 의미 변화 | 부호·0 비율, 규모 분포, 선택된 기간 길이 | 분포 변화는 경고, 명백한 계약 위반은 차단 |

분모를 “성공적으로 만들어진 행”에서 계산하면 소실된 행을 감출 수 있습니다. 또한 `not_applicable`을 제외할 때는 **값이 NULL이기 때문이 아니라 독립적인 적용 조건에 근거**해야 합니다.

부분 하락 경고는 예를 들어 “유효값 비율 5%p 하락이면서 영향 5건 이상”처럼 시작할 수 있습니다. 이는 업계 표준 수치가 아니라 초기 운영값입니다. 소수 업종은 비율보다 실패 건수와 고정 대표 사례 검사가 더 유용합니다.

신선도에는 두 시계가 필요합니다.

- **수집 신선도:** 최근에 요청·수집했는가?
- **정보 신선도:** 가져온 정보 자체가 얼마나 오래됐는가?

dbt의 소스 신선도도 지정한 시각 컬럼 등을 기준으로 계산합니다. 해당 컬럼이 수집 시각이면 재수집된 과거 정보의 낡음까지 판정해주지는 못합니다. [dbt 소스 신선도 문서](https://docs.getdbt.com/docs/build/sources)

추정치에는 소스 갱신일·커버리지 상태를 사용하고, 그런 정보가 없으면 신선도를 확인할 수 없다는 상태를 남겨야 합니다. 값이나 응답 해시가 바뀌지 않았다는 사실만으로 낡았다고 단정해서도 안 됩니다. 정상적으로 유지되는 값일 수 있습니다. 재무 실적에는 일률적인 “30일 초과” 대신 해당 기업의 보고 주기를 반영한 정책이 필요합니다.

과거 날짜 실행은 고정된 `as_of`와 당시 이용 가능한 판정 이력을 사용해야 합니다. 최신 판정 테이블은 조회용 뷰로 유지하고, 검사 입력은 이력에서 선택하십시오. 이미 덮어써서 사라진 과거 상태는 보존된 스냅샷 등이 없다면 정확히 복원할 수 없습니다.

경보에는 지표 숫자만 남기지 말고 **영향 건수, 대표 종목·원문 3건, 최초 발생 빌드, 실패 이유**를 함께 출력하십시오. 같은 원인의 반복 경보는 묶어야 1인이 처리할 수 있습니다.

3. **변경을 구분해서 셉니다.** 값→NULL, NULL→값, 값→다른 값, 행 추가·삭제, 출처·기준·`available_date` 변경을 별도 집계합니다. NULL 안전 비교를 사용하고, 부동소수점은 컬럼별 허용오차를 정합니다. 실행시각 같은 운영 메타데이터는 의미값 비교에서 분리합니다.

5. **골든 테스트와 결정성을 함께 검사합니다.** 기존 결함 사례의 정답을 확인하고, 신버전을 동일 입력으로 두 번 실행했을 때 의미값 해시가 같은지 검사합니다. 정규화의 반복 적용, 입력 행 순서 변경 등에도 결과가 유지돼야 하는 규칙은 작은 변형 테스트로 보강합니다.

6. **검증된 판만 운영판으로 지정합니다.** 별도 빌드 디렉터리에 생성하고 검사 완료 후 운영 포인터를 바꿉니다. 이전 정상판과 비교 보고서를 보존합니다. 검사 실패 시 이전 판을 유지하되 그 판의 기준시각과 낡음은 명시해야 합니다.
