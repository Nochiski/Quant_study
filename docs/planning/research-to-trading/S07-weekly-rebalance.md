# S07 운영 관찰: scope 상위 10 주간 리밸런싱

[S07 패킷](../../auto-trading-roadmap.html#session-s07)의 운영 경로(B3)다. 미리 정한 신호와 실행 규칙으로
키움 모의계좌를 매주 운용하며, 신호를 먼저 남기고 연구의 목표와 계좌의 실제 상태 사이 차이를 기록한다.
전략의 실력 판정은 이 문서의 범위가 아니다. 모의 체결은 실전 시장충격·용량의 근거로 쓰지 않는다.

## A: 신호 읽기·목표 계산·주문안

### 신호 (`adapters/outbound/scope_signal`)

고른 종류(`--basis`: 장 마감 빌드 `evening`이 기본, 주말 보강판 `supplement`)의 현재 빌드만 읽는다.
두 종류는 서버 quant-ledger 의 다른 루트에 있다. 장 마감 빌드는 모델 DB(`data/model_db`), 주말 보강판은
아침 확정판과 같은 연구 모델 루트(`data`)이고 배치(`model/`·`factor_inputs/`)는 같다. `--model-root`로
그 루트를 준다. 서버 예약 실행은 주말 보강판을 쓴다(G절).

1. `model/latest_<basis>.json`의 `status`가 `ok`, `basis`가 고른 종류, `date`가 신호일이어야 한다.
   아니면 `not_ready`.
2. 그 빌드의 `specs["scope@2.0"].gates`가 모두 `pass`·`warn`·`skip`이고 `excluded_specs`에 없어야 한다.
   아니면 `gate_failed`.
3. 그 빌드가 `model/scope@2.0/MANIFEST.json`의 빌드 목록(`builds`, 커밋된 판)에 있어야 한다.
   `current_build`는 보지 않는다(G절 보강판 보호). `scores.parquet`의 `score_date`가 신호일 하나이고
   종목·순위가 겹치지 않아야 한다. 아니면 `unreadable`.
4. 기준가격은 그 빌드가 점수를 계산한 가격 판(`fi_build_id`의 `factor_inputs/fi_prices`)의 신호일
   종가다. 신호일 거래량 0 종목은 매매가 막힌 것으로 본다.

### 목표 계산 (`domain/rebalance`)

- 보유 종목: 순위가 30위 안이면 남기고, 밖이거나 순위가 없으면 전량 판다. 매매가 막혔으면 둔다.
  남긴 종목이 10개를 넘으면 순위가 낮은 것부터 판다.
- 빈 자리: 보유하지 않은 종목을 순위대로 채운다. 막혔거나 가격이 없거나 1주가 목표 금액보다 비싸면
  건너뛰고 다음 순위로 채우되 30위 밖은 사지 않는다.
- 종목당 목표 금액 = (현금 + 기준가 평가액) × 98% ÷ 10. 새 종목은 이 금액, 남긴 종목은 ±25%를 넘게
  벗어날 때만 이 금액으로 맞춘다.
- 주식 수 = 목표 금액 ÷ (기준가 × 1.0035) 내림. 금액은 원 정수, 비율은 bp 정수다.

### 주문안 (`application/weekly_rebalance`, `adapters/outbound/rebalance_files`)

- `prepare`는 신호일마다 주문안 `weekly-<신호일>` 하나를 만든다. 이미 있으면 다시 만들지 않는다.
- 주문안 파일에 순위 전체, 점수 파일 SHA-256, 가격 판 id, 그때의 현금·보유, 줄마다 순위·현재·목표·기준가·
  사유를 남긴다. 임시 파일에 다 쓴 뒤 제자리에 붙이고(덮어쓰기 없음) 600 권한이다.
- 실행 원장이 있으면 먼저 대사하고, 어긋나면 주문안을 만들지 않는다(`not_reconciled`).
- `approve`는 한 번만 기록한다. 주문은 보내지 않는다.

### 사용법 (backend/에서)

```bash
# 맥에서: 서버 현재 빌드 파일만 가져온다(저장소 밖 도구)
~/quant-data/kiwoom-mock/tools/fetch_model_db.sh ~/quant-data/kiwoom-mock/model_db
uv run python -m strategy_workbench.bootstrap.weekly_rebalance prepare \
  --workdir ~/quant-data/kiwoom-mock/strategy/scope-top10 \
  --model-root ~/quant-data/kiwoom-mock/model_db --signal-date 2026-10-23
uv run python -m strategy_workbench.bootstrap.weekly_rebalance approve \
  --workdir ~/quant-data/kiwoom-mock/strategy/scope-top10 --plan weekly-2026-10-23 --approver <이름>
```

키는 설정 화면이 저장한 내 문서 `auto_trading/.env`에서 읽는다(2026-10-24, 예전 `secrets.json`은 열 때 옮긴다).
작업 폴더가 저장소 안이면 거부한다.

  계좌 읽기 4개(가짜 키움 서버).
- 2026-10-21 실데이터 확인(조회만): 10-20 빌드와 모의계좌로 주문안을 만들었다. 그날 산 10종목이 모두 30위

## B: 주간 실행기와 기록·복기

### 실행 (`application/weekly_rebalance`의 `WeeklyExecutionService`)

- 주문안이 있어야 하고, 승인도 있어야 한다. `--without-approval`이면 승인 없이 낸다 — 서버 예약 실행은
  10-26부터 이 방식이다(C절 "승인"). 신호일
  다음 날부터 5일 안에만 낸다. 실행 원장이 없으면 첫 `--send` 때 지금 계좌를 기준 잔고로 잡는다.
- 대사가 맞지 않으면 아무것도 내지 않는다(`halted`).
- 주문은 실행일 오전에 모두 낸다. 미루지 않고 시장가로 호가를 긁지도 않는다(10-21 사용자 결정).
- 주문안 종목만 본다. 목표에서 지금 보유와 살아 있는 주문을 뺀 만큼 낸다.
- 여는 단계(`--phase open`, 09:05): 매도를 먼저 내고 체결을 잠깐(최대 2분) 기다린 뒤, 그때
  현금(예약분 제외)으로 살 수 있는 만큼 순위 순서로 산다. 현금이 모자라 덜 산 수량은 추적 단계가 채운다.
- 추적 단계(`--phase chase`, 09:15~11:30 10분마다): 살아 있는 잔량을 취소하고, 취소가 확정되면 남은
  목표를 그때 2호가로 다시 낸다. 11:30에 낸 주문은 장 마감까지 걸어 둔다. 결과를 모르는 주문은 S05가
  취소하지 않으므로 그대로 두고, 그 종목·방향은 다시 내지 않는다.
- 지정가는 매수 매도 2호가, 매도 매수 2호가다. 호가 사이가 넓어도 미루지 않는다. 호가가 아예 없는
  종목(거래정지 등)만 그 회차를 건너뛰고(`no_quote`) 다음 회차에 다시 본다. 추적 가격 상한은 없다.
- 비용 상한은 매수 0.4%, 매도 0.7%(모의 매도 비용 0.55%)다. 주문안 하나에 주문(다시 낸 주문 포함)은
  200건까지다.
- 의도 ID는 `<주문안>-<종목>-<방향>`, 다시 낸 주문은 `-c<회차>`다. 살아 있는 주문을 목표에서 빼고
  내므로 다시 돌려도 같은 수량을 두 번 내지 않는다. 보내기 전 조회가 체결로 계속 바뀌어 S05가 결과
  불명을 주면, 원장에 의도가 없을 때만 15초 쉬고 같은 의도로 다시 시도한다(`retry`).
- `--send`가 없으면 무엇을 보낼지만 보인다(매도 대금은 지정가 대금에서 비용 상한을 뺀 값으로 어림).

### 기록·복기 (`adapters/outbound/rebalance_files`)

| 파일 | 내용 |
|---|---|
| `plans/weekly-<신호일>.json` | 신호(순위 전체·점수 지문·가격 판)와 계획. 바뀌지 않는다 |
| `records/events.jsonl` | 실행 사건: 보낸 시각, 그때 호가 3단계, 지정가, 신호 기준가, 결과 |
| `records/day-<날짜>.json` | 장 마감 기록: 현금·보유(장 마감가)·총자산, 종목·방향별 계획·체결 수량·금액·비용, 신호 기준가 대비 체결 차이(bp), 미체결 기회비용 |
| `records/raw-<날짜>.json` | 그날 키움 조회 원본(`kt00007`·`ka10170`·`kt00018`·`kt00001`). 감사·복기용 |
| `exports/*.csv` | `export` 명령: `days`·`orders`·`holdings`·`events` 네 표(UTF-8 BOM, 엑셀에서 바로 열림) |

체결 차이는 평균 체결가가 신호 기준가보다 불리한 정도(bp, 불리하면 양수), 미체결 기회비용은 계획보다
덜 산(판) 수량 × 기준가에서 장 마감가까지의 움직임(놓친 이익이 양수)이다. 모든 파일은 600이다.

### 명령 (backend/에서, 작업 폴더는 저장소 밖)

```bash
W=~/quant-data/kiwoom-mock/strategy/scope-top10
uv run python -m strategy_workbench.bootstrap.weekly_rebalance execute --workdir $W \
  --plan weekly-2026-10-23 --phase open            # 미리보기
uv run python -m strategy_workbench.bootstrap.weekly_rebalance execute --workdir $W \
  --plan weekly-2026-10-23 --phase open --send     # 월 09:05
uv run python -m strategy_workbench.bootstrap.weekly_rebalance execute --workdir $W \
  --plan weekly-2026-10-23 --phase chase --send    # 월 09:15~11:30, 10분마다
uv run python -m strategy_workbench.bootstrap.weekly_rebalance close --workdir $W    # 매일 15:40
uv run python -m strategy_workbench.bootstrap.weekly_rebalance report --workdir $W
uv run python -m strategy_workbench.bootstrap.weekly_rebalance export --workdir $W
```

### 실측으로 고친 것 (2026-10-21)

- 같은 TR을 1초 안에 두 번 부르면 키움이 1700으로 거절한다. 한 프로세스의 주문·호가 어댑터가 따로
  토큰을 받다가, 그리고 명령을 연달아 돌리다가 걸렸다. 호가 어댑터가 주문 어댑터의 접속(토큰·호출 간격)을
  함께 쓰고, 명령은 시작 때 1.5초 쉬며, 조회 TR의 1700은 간격을 지켜 한 번만 다시 읽는다(주문 TR은
  다시 보내지 않는다).

### 확인

- 순수 계산 5, 실행기 10(현금으로 줄인 매수 수량 손계산, 다시 돌려도 한 번만 보냄, 재시도, 넓은 호가도
  그때 2호가로 냄·호가 없음만 건너뜀, 승인·기한·정지 거절, 주문 수 상한, 추적 회차, 결과 불명 주문
  건드리지 않음, 장 마감 품질), 게이트웨이·호가 5(가짜 키움 서버, 1700 재시도),
  기록 파일 1, 명령줄 2(실행·마감·보고·내보내기).
- 2026-10-21 실데이터 확인(주문 없음): 시험 폴더에서 10-20 주문안 → 실행 미리보기(낼 것 없음) → 장 마감

### 예약(`backend/scripts/weekly_rebalance_cron.sh`, 서버 crontab은 UTC)

언제 도는지의 정본은 `backend/scripts/weekly_rebalance.crontab`이고 서버 crontab의 S07 줄은 이 파일과
같다(10-22 리뷰 #605). 아래 표는 그 파일을 KST로 옮긴 것이다. 겹쳐 돌지 않게 하는 잠금은 스크립트가 작업
폴더의 `.lock-<묶음>`으로 잡는다(open·chase는 같은 잠금). 빌드 준비 판정은 신호 어댑터 한 곳이 하고
스크립트는 `signal-status`의 종료 코드(0 준비 · 3 아직 · 그 밖 못 씀)만 본다.

| KST | 단계 | 하는 일 |
|---|---|---|
| 08:55 | `fills` | 15:35까지 실시간 체결 알림을 `records/fills-<날짜>.jsonl`에 기록(계좌번호 끝 4자리만) |
| 매일 09:00 | `prepare` | 휴장 첫날이고 그 전날이 그 주 마지막 거래일이면 그 거래일의 주말 보강판(`latest_supplement.json`)이 끝난 것을 확인한 뒤 주문안을 만들고 텔레그램으로 주문지를 보낸다(E절·G절). 23시까지 끝나지 않으면 신호를 읽지 못한 것으로 끝나며 실패 알림을 보낸다. 그 밖의 날은 건너뛴다 |
| 09:05 | `open` | 직전 거래일 주문안이 있으면 `execute --phase open --send` |
| 09:15~11:30 | `chase` | 10분마다 같은 주문안 `execute --phase chase --send`. 11:30에 낸 주문은 장 마감까지 걸어 둔다 |
| 15:40 | `close` | 장 마감 대사·하루 기록·키움 원본 |

`prepare` 밖의 단계는 휴장일에 건너뛴다. 판정은 quant-ledger `daily.calendar` 한 곳을 읽고, 연도 파일이 없어
판정할 수 없으면 휴장으로 위장하지 않고 실패한다(2027년 판은 12-15 전후 게시).

## D: 매주 확인과 데이터 누락 대응 (2026-10-21 사용자 결정)

scope 순위는 WISE 리비전 등 데이터가 비면 종목이 빠졌다가 돌아올 수 있다. 09-01~10-20 빌드 37개에서
빠졌다 돌아온 경우가 13건(1~11거래일)이었고, 그중 상위 30위 종목이 둘(09-28 192650 12위·354320 25위,
6~7거래일)이었다. 지금 보유한 354320·042510·484120도 이 13건에 들어 있다. 순위가 없다고 바로 팔면
데이터 누락에 따라 사고팔게 된다.

- **보유 종목이 신호에서 빠지면**: 파는 줄로 두되 `⚠확인`(`review`)으로 표시하고 직전 빌드 순위를 사유에
  싣는다. 사용자가 주말 확인 때 데이터 누락으로 보면 `approve --no-trade <종목>`으로 그 주 매매에서
  뺀다(사지도 팔지도 않는다). 10-26부터는 승인 없이 돌아서, 아무도 빼지 않으면 그대로 판다(C절 "승인"). 뺀 보유 종목은 자리를 그대로 차지하므로 같은 수만큼 순위가 낮은 새 매수도
  그 주는 하지 않는다(`domain/rebalance`의 `week_targets`, F절). 실행기는 승인의 `no_trade` 종목과 함께 빠진
  새 매수를 목표에서 빼고, 장 마감 기록에서도 뺀다. `approve`는 함께 빠진 새 매수를 출력한다.
- **빌드 전체가 의심되면**: 직전 빌드(모델 `MANIFEST.json`에서 바로 앞 판) 상위 30위 중 2종목 이상이
  사라졌거나, 점수 받은 종목 수가 3% 넘게 줄었으면 `prepare`가 주문안을 만들지 않는다
  (`signal_suspect`, 예약 실행은 실패로 남고 보류 알림을 보낸다 — E절). 사용자가 확인한 뒤에만 `prepare --accept-anomalies`로
  만들고, 그 사유를 주문안에 함께 남긴다. 37개 빌드에 대면 09-28 하루만 걸린다(종목 수 감소는 그 기간
  최대 0.7%).
- 직전 빌드를 읽지 못하면(첫 빌드·파일 없음·같은 날 재빌드) 빌드 점검을 건너뛰고 종목별 표시만 한다. 건너뛴
  이유는 주문안(`gap_check_skipped`)에 남고 주문지 끝에 "직전 빌드 점검 건너뜀" 한 줄로 보인다(10-22 리뷰 #606).
- 원인(WISE 리비전 수집 누락 여부) 진단은 데이터 파이프라인 쪽 일이다. 여기서는 전략이 흔들리지 않게만 한다.

  유효해 그날 체결도 그날 낸 주문에서만 생긴다. 실행일이 아닌 날은 보유·현금·총자산만 남는다.

### 원장을 사람이 고치는 명령 (#593 P2, 이번에 넣음)

응답을 잃어 묶이지 않은 주문(S05 `UNKNOWN`)과 정지 래치는 지금까지 원장 파일을 손으로 고쳐야 풀렸다
(10-21 측정 때처럼). 명령으로 고친다. 고친 일은 실행 사건 기록(`records/events.jsonl`, 단계 `repair`)에
고친 사람·메모와 함께 남고, 고친 뒤 S05 `resume`으로 다시 대사해 일치하면 신규 주문 정지가 풀린다.
원인이 남아 있으면 다음 조회에서 다시 멈춘다. 주문은 보내지 않는다(`transmit=False`).

| 명령 | 하는 일 |
|---|---|
| `ledger-status` | 정지 래치 사유, 실행 원장 정지 여부, 응답을 잃은 주문과 그 주문일 키움 주문 중 내용이 같은 후보 번호 |
| `ledger-bind --intent --order-no --operator` | 후보 번호일 때만 묶는다 |
| `ledger-reject --intent --operator` | 키움에 같은 내용의 주문이 하나도 없을 때만 거부(보내지 않음)로 확정한다 |
| `ledger-clear-latch --operator` | 래치를 풀고 다시 대사한다 |
| `ledger-resume --operator` | 다시 대사만 한다(예: 수동 주문을 정리한 뒤) |

- 사람이 고르는 후보는 내용(종목·방향·수량·지정가)만 본다. 자동 재식별은 이번에 시각 창에 뒤쪽 경계(전송
  시각 + 60초)를 더했다(#593 P3) — 한참 뒤에 낸 같은 내용의 주문은 자동으로 묶지 않고 사람에게 넘긴다.

### 그 밖의 리뷰 P3 (10-22)

- 서버 예약: 잠금을 스크립트 안으로 옮기고, 예약 시각의 정본을 `weekly_rebalance.crontab`으로 두고, 빌드
  준비 판정을 `signal-status` 하나로 모았다. 체결 기록 종료 시각(15:35)도 crontab이 인자로 넣는다(#605).
- 서버 `.env` 읽기를 `secrets_local`의 `read_env_values`로 옮겼다. 따옴표는 감싼 한 쌍만 벗기고, 따옴표
  없는 값의 줄 끝 주석(` #`)은 값에서 뺀다(#605).
- `truststore`·`websockets`를 직접 의존성으로 선언했다(잠금 파일의 판 그대로, #594·#605).
- 빌드 점검의 상위 N을 정책의 완충 순위로 맞췄고(#603), 미리보기 실행의 사건에 `preview` 표시를 달았고
  (#604), 따옴표로 감싼 `~` 작업 폴더를 명령줄 입구에서 푼다(#604). 실행 허용 기간은 신호일 뒤 9일(연휴,
  #605), 체결 기록기는 토큰 오류를 다시 시도하고 로그인 거절은 실패로 끝낸다(#605).

## G: 주문안은 휴장 첫날 주말 보강판으로 (2026-10-23 사용자 결정)

사용자 지시: "토요일에 주문지를 만들자. wise 의 추정치 데이터가 금요일분이 토요일에 오니까. 휴장때
주문지 만들자." WISE 는 그날 분 추정치를 밤사이(금요일 분은 토요일 06:00 전)에 올리고, 장 마감 빌드는
신호일까지 받은 추정치만 쓴다. 그래서 금요일 15:55 빌드에는 금요일 리비전이 빠진다. quant-ledger 의
주말 보강판(N-45)은 휴장 첫날 아침 WISE 재수집으로 마지막 거래일 모델을 다시 짓고 연구 모델 루트의
`data/model/latest_supplement.json`에 남긴다(10-22 스위치 켬, 첫 자동 10-24).

- **언제**: 예약 `prepare`는 매일 09:00 KST에 깨어, 오늘이 휴장 첫날이고 그 전날이 그 주 마지막
  거래일일 때만 돈다. 판정은 quant-ledger 달력의 `supplement_target`(보강판을 짓는 쪽과 같은 판정)에
  "다음 거래일이 다른 주" 조건을 더한 것이다. 보통은 토요일(→ 금요일 순위), 금요일이 공휴일이면 그날
  (→ 목요일 순위). 실행일은 다음 거래일이고 월요일 `open`은 그대로 직전 거래일 주문안을 찾는다.
- **무엇을**: `signal-status`·`prepare`에 `--basis supplement`와 `--model-root $S07_LEDGER_HOME/data`
  (연구 모델 루트)를 준다. 10-24 첫 배포본은 모델 DB 를 봐서 그날 지은 10-23 보강판을 못 찾았다(주문지는
  연구 루트로 손으로 만들어 보냄, 재현 테스트 `tests/test_weekly_rebalance_cron.py`). 주문안에 읽은 빌드 종류
  (`signal.basis`)를 남기고(이 칸이 없는 옛 주문안은 장 마감 빌드), 주문지 머리는 "주말 보강 신호"다.
- **빌드 점검**: 연구 루트에서 보강판 바로 앞 판은 같은 신호일의 아침 확정판이라, 직전 빌드 대비 누락
  점검은 신호일보다 앞 날짜의 가장 최근 판(보통 전 거래일 아침 확정판)과 견준다(`scope_signal`의
  `_previous`).
- **보강판 보호(2026-10-24 사용자 결정 D2)**: 연구 루트는 아침 확정판과 보강판이 모델 `MANIFEST.json`
  하나를 쓰고, 원장은 아침판만 다시 지어도 `current_build`를 그 판으로 바꾼다(quant-ledger
  `src/model/build.py`). 그래서 S07은 `current_build`가 아니라 `latest_supplement.json`의 `build_id`를
  읽고, 그 판이 MANIFEST 빌드 목록에 있는지만 본다. 포인터가 없거나(`unreadable`) 날짜가 신호일과
  다르면(`not_ready`) 다른 판으로 넘어가지 않고 실패 알림으로 끝난다(재현 테스트
  `test_supplement_survives_a_later_morning_rebuild_of_the_same_root`·`test_supplement_never_falls_back_to_another_build`).
- **보강판이 없을 때**: 스위치가 꺼졌거나 실패하면 23시까지 기다린 뒤 실패 알림을 보낸다. 장 마감 빌드로
  자동으로 대신하지 않는다(신호일 추정치가 조용히 빠진다). 그때는 보강판을 다시 짓거나(quant-ledger
  `scripts/weekend_supplement.sh --date D --wise-asof W`), 사람이 정해 장 마감 빌드로 만든다
  (`prepare --basis evening --notify --execute-on <실행일>`).
