# 페르소나

Strategy Workbench를 쓰는 세 사람이다. 기능을 설계하거나 리뷰할 때 "이 화면을 정동민이 보면
멈추지 않는가", "한상목이 이 개념을 설명 없이 알아듣는가", "김철수가 이걸로 자기 팩터를 만들 수
있는가"를 묻는다. 스토리는 [stories/](./stories/)에 사람별로 있다.

세 사람의 성별은 정하지 않는다. 문서에서 가리킬 때는 이름이나 "이 사람"이라고 쓴다.

| 약자 | 이름 | 한 줄 요약 | 주로 쓰는 표현 |
|---|---|---|---|
| `DM` | 정동민 | 퀀트는 잘 모르는 국내 주식 개인 투자자 | AI 어시스턴트, 그래프 |
| `SM` | 한상목 | 소프트웨어 개발자 출신, 투자는 처음 | YAML, 키보드, API |
| `CS` | 김철수 | 데이터를 가공해 자기 알파 팩터를 만드는 퀀트 투자자 | YAML, 그래프(노드), AI 조사 |

## 정동민 (`DM`)

**배경.** 국내 주식(국장)에 직접 투자한 지 몇 년 됐다. 증권사 앱과 HTS, 유튜브·커뮤니티에서
종목 정보를 얻는다. "요즘 오른 종목이 더 오른다", "PBR이 낮은 종목이 싸다" 같은 감은 있지만 이를
규칙으로 적어 과거 데이터로 검증해 본 적은 없다. 코딩은 하지 못한다.

**목표.**

- 자기 투자 감을 규칙으로 바꿔 과거에 통했는지 확인하고 싶다.
- 결과를 보고 "이 규칙을 계속 믿어도 되나"를 스스로 판단하고 싶다.

**지식 수준.**

- 투자: 종목·시가총액·PER·PBR 정도는 안다. 샤프 비율, 최대 낙폭, 리밸런싱, 팩터, 유니버스는
  낯설다.
- 도구: 엑셀은 조금 쓴다. YAML·JSON·API는 모른다.

**좌절 지점.**

- `max_name_weight`, `node_id`, `cross_sectional` 같은 영어 식별자가 화면에 그대로 나오면 멈춘다.
- 오류가 영어 문장이나 JSON Pointer(`/risk/max_name_wieght`)로만 나오면 무엇을 고칠지 모른다.
- 기간·수수료 같은 실행 조건을 전략 글 안에서 찾아 고쳐야 하면 어디를 만져야 할지 헤맨다.
- 결과 숫자가 좋은지 나쁜지 기준을 모른다.

**쓰는 표현.** AI 어시스턴트가 첫 진입로다. 말로 아이디어를 설명하고 제안을 받아 적용한다. 그다음
그래프 화면에서 카드와 문장으로 값을 바꾼다. YAML은 직접 고치지 않는다.

**성공의 모습.** 빈 화면에서 AI에게 "요즘 많이 오른 대형주를 사는 전략"을 말하고, 제안을 적용해
백테스트 결과까지 10분 안에 본다. 결과의 핵심 숫자가 무슨 뜻인지 화면이나 AI 설명으로 이해한다.
기간이나 수수료를 바꿔 다시 돌릴 때 전략 글은 건드리지 않는다.

## 한상목 (`SM`)

**배경.** 웹 백엔드 개발자로 일했다. 투자는 해 본 적이 없고, 퇴직연금 말고는 금융 상품을 잘
모른다. 새 도구를 만나면 문서와 스키마부터 읽고 API로 자동화하는 데 익숙하다.

**목표.**

- 퀀트 전략이 무엇이고 어떻게 검증하는지 직접 만져 보며 배우고 싶다.
- 전략을 코드처럼 다루고 싶다. 버전 관리, 차이 비교, 재현 가능한 실행이 필요하다.

**지식 수준.**

- 투자: 거의 없다. 모멘텀, 리밸런싱, 벤치마크, 연환산, OOS(표본 외 검증) 같은 말은 설명이 필요하다.
- 도구: YAML·JSON Schema·REST·git 흐름에 익숙하다. 키보드 단축키를 선호한다.

**좌절 지점.**

- 필드의 단위와 범위를 모르면 틀린 값을 넣는다. `0.05`가 5%인지 0.05%인지가 문서에 없으면 멈춘다.
- GUI로 고쳤을 때 원문 YAML이 통째로 다시 쓰이면 diff를 믿을 수 없다.
- 같은 설정으로 다시 돌렸는데 결과가 다르거나, 무엇으로 돌렸는지 기록이 없으면 신뢰하지 않는다.
- 금융 용어가 설명 없이 나오면 따로 검색하느라 흐름이 끊긴다.

**쓰는 표현.** YAML 편집기가 주 무대다. 명령 팔레트와 단축키를 쓰고, 계약(스키마) 패널에서 필드
뜻을 확인한다. 금융 개념은 AI 어시스턴트에게 묻는다.

**성공의 모습.** 키보드만으로 전략을 붙여 넣고, 필드 단위를 확인하고, 저장하고, 백테스트한다.
리비전 사이의 의미 차이를 Diff로 보고, 실행 기록(manifest)으로 같은 실행을 그대로 다시 돌린다.
실행 조건만 바꿔 돌려도 전략 해시가 같다는 것을 확인한다.

## 김철수 (`CS`)

**배경.** 몇 년째 혼자 퀀트 전략을 만들어 굴리는 투자자다. 파이썬과 판다스로 재무·수급 데이터를
받아 가공한다. 공개 팩터(모멘텀, 밸류)를 그대로 쓰기보다 원천 데이터를 2차 가공해 자기만의 알파
팩터를 만든다. 예를 들어 자본총계를 시가총액으로 나눈 뒤 횡단면 표준화한 값, 외국인 순매수를
시가총액으로 나눈 수급 강도 같은 것이다.

**목표.**

- 원천 필드를 산술·시계열·횡단면 연산으로 조합해 파생 팩터를 정의하고 싶다.
- 여러 팩터를 가중 결합해 전략을 만들고, 각 팩터가 점수에 얼마나 기여했는지 검증하고 싶다.
- 미래 데이터 누수(look-ahead) 없이 계산됐다는 근거를 보고 싶다.

**지식 수준.**

- 투자: 높다. 팩터, 정규화, 결측 처리, 리밸런싱, 거래 비용, 표본 외 검증을 안다.
- 도구: YAML과 데이터 파이프라인에 익숙하다. 노드 그래프 도구(Excel 파워 쿼리, 노드형 ETL)도 써
  봤다.

**좌절 지점.**

- 단위가 다른 팩터(원 단위 금액과 비율)를 그대로 더하면 큰 단위가 점수를 지배한다. 결합 전
  정규화가 없으면 결과를 믿지 않는다.
- 파생 팩터를 전략마다 다시 적어야 하면 실수가 생긴다.
- 중간값을 볼 수 없으면 계산이 맞는지 확인할 방법이 없다.
- 템플릿에 맞춰야만 전략을 만들 수 있으면 자기 아이디어를 담지 못한다.

**쓰는 표현.** YAML로 팩터 그래프를 직접 적고, 그래프 편집기에서 노드를 잇는다. 중간 결과(추적)와
실행 계획으로 계산을 검증한다. 논문·리포트 조사와 파라미터 조정안은 AI 어시스턴트에게 맡긴다.

**성공의 모습.** 원천 필드 두 개로 파생 팩터를 만들고 기존 모멘텀 팩터와 가중 결합한다. 종목별
중간값과 공개일을 추적해 계산을 확인한 뒤 백테스트한다. 같은 파생 팩터를 다른 전략에서 다시 쓴다.
