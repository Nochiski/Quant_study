# database/ 작업 규칙

이 폴더는 서버(`~/quant-ledger`)에 배포되는 일일 파이프라인이다: 원장 → stage → equity → factor_inputs → model → deliver.
저장소 공통 규칙(`.claude/rules/`)에 더해 아래를 지킨다.

## 결정과 플랜
- 결정 정본은 `docs/DECISIONS.md` 하나다. 미확정 값은 사용자에게 묻는다.
- 판단 원칙 P1~P9 는 `docs/DECISIONS.md` §0 에 있다. 원칙 안의 일은 정하고 N- 번호로 장부에 남긴다. 원칙 밖의 일만 묻고, 질문은 모아서 선택형 + 권고안으로 낸다.
- 큰 작업은 코드보다 플랜(`docs/plans/`)을 먼저 커밋한다. 플랜 맨 위에 진행률 표(작업 × 계획·구현·검토·배포·실전 확인·다음 관측)를 둔다. 작업 하나 = 결정 하나.
- 묶음 이름은 '배포 묶음 N' 이다('물결'은 옛 문서에만 남아 있다).

## 관문
- 재현 테스트(옛 코드에서 FAIL) → 수정(PASS) → 명세 검토 → 품질 검토(한 곳에서 판정하는가 · 책임이 섞이지 않았는가 · 도메인 경계를 넘지 않았는가) → 배포 → 서버 확인 → 기록.
- 서버 확인은 지난 날짜 재판정·임시 폴더 실행을 먼저 하고, 운영 실행은 마지막 확인으로 쓴다. 단계가 끝나면 전체 구조 검토를 한 번 한다.
- 테스트는 실물 > 가짜 > 목. 보고는 실제 / 가짜 / 미검증으로 나눈다. 결함은 4요소(상황·인풋·위치·위험성, `.claude/rules/pr-review.md`)로 쓴다.

## 서버 운영
- 배포는 `scripts/deploy.sh --apply --allow-branch <브랜치>` 로만 한다. 운영 체인 밖(10:30~15:10)에서 한다 — 15:20~16:30 측정기, 18:05~23:00 저녁 체인, 06:00~10:30 아침 체인을 피한다.
  - 배포 전: 서버에서 도는 체인과 원장·빌드 잠금이 비었는지 확인하고, 되돌릴 rev 를 적는다.
  - 배포 뒤: 보낸 파일의 해시를 대조한다. 배포 중에는 작업 트리를 고치지 않는다.
- 서버에서 모듈을 손으로 돌릴 때는 체인과 같은 환경을 쓴다: `cd ~/quant-ledger && export QL_HOME="$HOME/quant-ledger" PYTHONPATH="$HOME/quant-ledger/src"`. 지난 날짜 건전성 재판정은 `--out "$(mktemp -d)"` 로 운영 리포트를 건드리지 않는다.
- 작업끼리는 앞 작업의 끝을 감지해 잇는다(P9). 고정 시각은 외부 소스 공개 시각에만 쓰고, 늦어짐은 워치독이 알린다. 자정을 넘는 크론·워치독은 스크립트의 날짜 판정부터 확인한다(F-11).
- WISE 같은 날 재실행 절차는 `README.md` 운영 절에 있다. `--limit` 은 시험용이라 런 로그를 남기지 않는다.
- 백필 코드(`backfill_kw.py`·`backfill_kis.py`·`backfill_dart.py`)는 동결이다. 예외는 결정 장부에 있다(N-23 ③).

## 하지 않는 것
- `.env`·`logs/dart*.log` 처럼 키가 든 파일을 열지 않는다. 키·토큰을 출력하지 않는다.
- 운영 로그·경보를 텔레그램으로 보내지 않는다(`notify.sh` 는 `logs/notify.log` 기록만). 모델 엑셀 배달은 별개다.
- kael-system-v3 서버 파일은 읽기만 한다. 서버 데이터 삭제는 항목마다 사용자 승인을 받는다.
- 강제 push 를 하지 않는다. 공개 저장소에 서버 홈 경로·IP·계정명을 넣지 않는다.
