## 1. 카탈로그 스냅샷 식별자가 "내용" 이 아니라 "이름표" 만 해싱한다

### 무엇이 문제인가

백테스트를 돌릴 때마다 결과 옆에 `snapshot_id` 라는 16자리 지문이 찍힌다. 사람들은 이걸
**"어떤 데이터로 돌렸는지"의 영수증**으로 읽는다 — 지문이 같으면 같은 데이터, 다르면 다른 데이터.

그런데 이 지문은 데이터 내용을 전혀 보지 않는다. `catalog.py:67-70` 이 하는 일은
`"corp=b_001\nprice_daily=b_002\n..."` 같은 **표 이름 = 판본 이름** 문자열을 이어붙여 해싱하는 것뿐이다.
판본 이름이 같으면 안에 든 숫자가 완전히 달라도 같은 지문이 나온다.

비유하자면 상자에 붙은 라벨만 대조하고 상자를 열어보지 않는 것이다. 라벨이 같으니 같은 물건이라고
결론 내리는데, 누가 라벨을 그대로 두고 내용물을 바꿔치기하면 알 수 없다.

**언제 실제로 라벨이 재사용되는가**가 핵심이다. 서버 빌드는 판본 이름이
`b_20260906T100233_789959Z`(마이크로초 시각)라 절대 겹치지 않는다. 그런데 **로컬 개발·테스트 경로는
판본 이름을 손으로 고정한다** (`tests/test_equity_s08_flow.py:_chain` 의
`build_id=f"b_{rule.name}"`). MVP-B 백테스트 비교, 규칙 변경 전후 대조 — 사람이 실제로 "같은
데이터인가?" 를 묻는 자리가 전부 이 로컬 경로다. 즉 **충돌이 우연이 아니라 그 경로에서는 항상
일어난다**.

### 지금 실제로 사고가 나고 있는가

**났다. 하루치 오진이 확인됐다.** S21 본판 세션이 MVP-B 백테스트 수익률이 재현되지 않는 것을 두고
"snapshot `90115cc068146382` 이 같으니 데이터는 같다 → backend(엔진) 잘못이다" 라고 결론냈다.
S22 가 backend 6커밋 × equity 8커밋 교차 실험으로 재조사한 결과 **backend 는 완전히 무관했고**
원인은 equity 데이터 규칙 2건(`fc6e889` KRX 기준가 원천, `de75e9f` 무거래 이유 분류)이었다
(DESIGN §10 P25″). 두 데이터가 서로 달랐는데 지문은 같았던 것이다.

데이터 자체가 오염된 사고는 아니다. **"어느 데이터로 낸 결과인지" 기록이 못 미더운 것**이 사고다.

### 이 지문을 믿고 쓰는 곳 (전수)

| 어디 | 무엇을 하는가 | 지문이 틀리면 |
|---|---|---|
| `catalog.py:403` → `_catalog_meta.json` | 카탈로그가 어느 판을 가리키는지 기록 | 기록이 모호해진다 |
| `_source.py:79-83`(워크벤치 어댑터) | 카탈로그 meta 의 지문 ≠ 현재 표 판본 지문이면 **카탈로그를 낡음(stale)으로 막는다** | 판본 이름만 같고 내용이 다른 낡은 카탈로그를 "신선함" 으로 통과시킨다 |
| `_adapter.py:327·417·686·825·999` | 워크벤치가 내보내는 모든 결과에 `snapshot_id`/`data_snapshot_id` 로 붙는다 | 결과의 출처 표기가 틀린다 |
| `_service.py:149-160`(팩터 프리뷰) | 클라이언트가 본 지문과 실제 지문을 대조해 불일치면 에러 | 다른 데이터인데 통과한다 |

다행히 **as-of 회귀 게이트(EG5c)는 이 결함에 안 걸린다** — 지문이 아니라 기록 시각순 직전 표본과
행 단위로 비교하므로 지문이 같아도 내용이 달라지면 잡는다(`catalog.py:249-260`).

### 고치는 방법과 작업량

지문 계산식에 **내용 축을 한 줄 더한다**. 각 표의 `MANIFEST.json` 에 이미
`content_hash`(예: `9201516:253f90ab748e80cd` = 행수:해시)가 들어 있으므로 **새로 계산할 것이 없다**.
`f"{table}={build_id}"` → `f"{table}={build_id}:{content_hash}"` 로 바꾸면 끝이다.

작업량은 **반나절**. 다만 세 가지가 함께 움직인다:

1. **같은 계산식이 두 곳에 복사되어 있다** — `database/src/equity/catalog.py:67` 과
   `backend/.../equity_duckdb/_source.py:79`(주석에 "import 하지 않고 여기서 다시 쓴다" 라고 적혀 있다).
   한쪽만 고치면 **모든 카탈로그가 낡음으로 판정되어 워크벤치의 재무·컨센서스 필드가 전부 죽는다.**
   두 파일을 동시에 고쳐야 한다.
2. **기존 스냅샷 무효화** — 표 자체는 하나도 다시 짓지 않아도 된다(지문은 파생물이다). 다시 지어야
   하는 것은 `equity.duckdb` 카탈로그 1회(`python -m equity catalog`, 서버 수 초)뿐이다.
   `_asof/` 옛 표본은 디렉토리 이름이 옛 지문이라 남지만 EG5c 는 시각순으로 찾으므로 그대로 동작한다.
3. **기록된 백테스트 결과의 지문·`tape_hash`·`run_fingerprint` 가 전부 바뀐다.** 옛 run 기록과
   숫자로 대조할 수 없게 된다(수익률·MDD 는 안 바뀐다 — S23 이 표 하나를 더했을 때 이미 같은 일이
   일어났고 수익률은 16자리까지 같았다, P43). "언제부터 지문 규약이 바뀌었다" 를 문서에 남기면 된다.

### 심각도: **중**

데이터를 망가뜨리지는 않는다. 하지만 **실측 하루를 태운 전례가 있고**, "이 결과가 어느 데이터에서
나왔는가" 는 연구 기록의 근간이라 틀린 채로 두면 앞으로도 같은 오진이 반복된다. 고치는 비용이
반나절로 매우 싸다는 점이 심각도보다 우선순위를 끌어올린다.

## 2. 로컬 테스트용 절단본이 **저장소 어디에도 없다** (스크립트도, 데이터도)

### 무엇이 문제인가

equity 층의 테스트 660개는 서버 원장(8.5GB) 대신
`database/tests/fixtures/stage_slice/` 라는 **소형 사본**(15종목·11법인·61개 표·14MB) 위에서 돈다.
이걸 "절단본" 이라 부른다.

원래 보고된 문제는 "절단본을 만드는 스크립트(`slice_stage.py`)가 세션 스크래치에만 있고 저장소에
없다" 였다. 조사해 보니 **그보다 한 단계 더 나쁘다**:

- **스크립트가 없다** — `git log --all -S"slice_stage"` 로 저장소 전 이력을 뒤져도 실물 파일이
  들어온 커밋이 없다. `EQUITY_HANDOFF.md` §8 의 절차 5단계가 README + 커밋 이력에서 **역추적한
  기억**이고, 그 문서 자신이 "재현 가능한 스크립트로 만드는 것이 후속" 이라고 적어 두었다.
- **데이터도 저장소에 없다** — `.gitignore:240` 의 `*.parquet` 이 이 트리를 통째로 가린다.
  `backend/tests/fixtures/**/*.parquet` 은 예외로 풀어 놨는데 **`database/tests/fixtures/` 는 예외에서
  빠졌다**. 실측: 절단본 트리에 parquet 403개가 있는데 git 이 추적하는 것은 **0개**다.
  추적되는 것은 `MANIFEST.json` 61개와 `README.md` 1개, 즉 **목차만 있고 본문이 없다**.
- **CI 가 이 테스트를 아예 돌리지 않는다** — `.github/workflows/ci.yml` 은 `backend/` 와 `frontend/`
  만 돈다. `database/tests` 는 어느 job 에도 없다.

정리하면: **equity 층 테스트 660개는 이 노트북의 작업 디렉토리에서만 돌아간다.** 새로 clone 한
사람도, CI 도, 다른 기계도 한 개도 못 돌린다. 그리고 데이터를 다시 만들 방법이 문서 산문뿐이다.

### 지금 실제로 사고가 나고 있는가

**두 종류가 이미 났다.**

1. **재절단이 테스트를 깼다(P35′)** — stage 가 텍스트 정규화 규칙(공백·개행·NFKC)을 바꿨을 때,
   절단본 안에 정규화 **이전** 문자열로 굳어 있던 골든 픽스처 키가 서버와 어긋나 EG4 게이트가
   실패했다(`shares_outstanding`, 커밋 `bd114bf`). 절단 규칙이 코드가 아니라 사람 손이라 stage 가
   바뀌었을 때 무엇을 다시 잘라야 하는지가 자동으로 드러나지 않는다.
2. **모집단 의존 픽스처 사고 2건(P26′·P38′)** — 절단본 15종목에서 잰 값(순위·커버 시작일)을
   골든 값으로 굳혔더니 서버 3,478법인에서 반드시 실패했다. 이것도 "절단본이 무엇을 대표하는가"
   가 코드로 표현돼 있지 않아서 생긴 사고다.

지금 이 순간의 상태는 **"사고가 나고 있지는 않지만 한 번의 실수로 회복 불가"** 다. 이 작업
디렉토리의 `database/tests/fixtures/stage_slice/` 를 지우면(clean checkout, 디스크 사고, 다른
기계로 이사) equity 테스트 660개가 영구히 못 돈다. 복구하려면 서버 8.5GB 원장에서 61개 표를
README 산문만 보고 손으로 다시 자르는 수밖에 없다.

### 고치는 방법과 작업량

두 갈래가 있고 **둘 다 하는 것을 권한다**.

**(a) 절단 스크립트를 저장소에 넣는다** — `database/scripts/slice_stage.py`.
필요한 재료는 전부 이미 있다:
- 축 정의: README 의 티커 15 / 법인 11 / 접수번호 33,971 — 이걸 스크립트 상단 상수로 옮긴다.
- 표별 축 매핑: 61개 표를 티커축·법인축·접수번호축·무축(전량) 넷 중 하나로 분류. README 가
  이미 그룹별로 적어 놓았다.
- 판본 해석·MANIFEST 재작성: `stage.manifest` 모듈이 그대로 쓰인다.
- 0행 표 규약: 스키마 보존용 빈 파티션 1개를 반드시 쓰기(항목 3 참조).
- **선례가 있다**: `backend/scripts/slice_krx_fixture.py` 가 같은 성격의 스크립트다.

작업량 **1~1.5일**(61표 축 분류 + 실행 + 산출 대조). 서버 SSH 로 읽어 로컬에 쓰는 형태라
서버 쓰기는 없다.

**(b) 절단본 parquet 을 git 에 넣는다** — `.gitignore` 에 한 줄:

## 3. `stg_flow_split_daily` 절단본 결함 — **이미 고쳐졌는데 우회 코드가 남아 진짜 데이터를 가리고 있다**

## 4. 어댑터가 "언제부터 이 값을 알 수 있었나" 를 **자기 상수로 우겨서** 대장(`dataset_profile`)과 어긋난다 — **실제 미래 훔쳐보기**

### 무엇이 문제인가

"공개시차(lag)" 는 **어떤 값이 실제로 언제부터 알려졌는가**를 세션(거래일) 단위로 표현한 것이다.
시차 0 = "D일 값은 D일 장 마감 시점에 알 수 있다", 시차 1 = "D일 값은 D+1일에야 알 수 있다".

백테스트에서 이걸 틀리면 **미래를 훔쳐본다**. 시차 1짜리 값을 시차 0으로 읽으면, 전략은 D일에
"내일 발표될 숫자" 를 보고 오늘 주문을 낸다. 성과가 실제보다 좋게 나오고, 실전에서는 재현되지
않는다. 이게 look-ahead bias 다.

equity 층은 이 시차를 정하는 **정본 대장**을 따로 만들어 뒀다 — `dataset_profile` 표(서버 72행,
필드마다 `recommended_lag_sessions` 컬럼). 그런데 워크벤치 어댑터는 그 대장을 **읽지 않는다.**
`_specs.py` 안에 원천 묶음별로 `lag_sessions=0` 이라는 상수를 13개 박아 두고 그걸 쓴다.

| | 대장(`dataset_profile`) | 어댑터(`_specs.py`) |
|---|---|---|
| 값의 출처 | 각 표의 선언(`FieldProfile.recommended_lag_sessions`) | 하드코딩 상수 13개, 전부 `0` |
| 코드 | `rules_s19.py:188` | `_specs.py:177·195·214·233·251·271·291·309·335·354·373·392·411` |

### 지금 실제로 사고가 나고 있는가

**나고 있다. 어댑터가 내보내는 30개 필드 중 25개가 대장보다 한 세션 이르다.**

서버 `dataset_profile` 72행 실측: 시차 0 은 7필드(원주가 6 + 조정 종가), 나머지 **65필드가 시차 1**.
어댑터가 실제로 내보내는 30필드와 교차하면:

| 시차 | 대장 | 어댑터 | 어긋남 |
|---|---|---|---|
| `price.close`·`open`·`volume`·`trading_value`·`adj_close` (5) | 0 | 0 | — 일치 |
| `price.market_cap`·`price.shares_outstanding` (2) | **1** | 0 | ✗ |
| `flow.*` 3 · `short.*` 2 · `credit.margin_balance` (6) | **1** | 0 | ✗ |
| `financial.*` 8 (재무) | **1** | 0 | ✗ |
| `consensus.*` 6 | **1** | 0 | ✗ |
| `event.buyback_amount`·`dividend_per_share`·`insider_net_buy` (3) | **1** | 0 | ✗ |
| **합계** | | | **25 / 30 필드가 한 세션 이르다** |

게다가 어댑터는 자기 상수를 **대장인 것처럼 소비자에게 내보낸다** —
`_adapter.py:444` 가 `recommended_lag_sessions=source.lag_sessions` 로 필드 프로파일을 만든다.
워크벤치 화면에서 "이 필드 시차 0" 을 읽은 사람은 그게 equity 층의 결정이라고 믿게 된다.
`backend/tests/test_adapters_equity_duckdb.py:141` 이 `all(p.recommended_lag_sessions == 0)` 을
한 줄로 단언해 이 상태를 못 박고 있다.

**어느 필드가 실제로 위험한가.** 시차 1 선언이 전부 look-ahead 인 것은 아니다. 재무·컨센서스는
`available_date` 가 이미 DART 접수일·수집일(= 그날 실제로 알았던 날)이라 시차 0으로 읽어도 실질
누출이 거의 없다 — 대장의 1 은 보수적 여유에 가깝다. **진짜 위험은 격자 3표(수급·공매도·신용)** 다.
`_specs.py:58-61` 이 스스로 적어 놓았다:

> "랙 0 은 '원장 날짜가 곧 그날 알 수 있던 날' 이라는 **가정**이고 **신용잔고는 실제로 T+1
> 공표다**" (DESIGN §11 ⑫ 도 같은 문장)

`credit.margin_balance`(신용융자 잔고)는 D일 잔고가 D+1일에 공표된다. 어댑터는 D일에 D일 잔고를
준다. **하루치 look-ahead 가 확정적으로 존재한다.** 서버 격자는 9,201,516셀 × 15.6년이라
전 구간이 이 상태다. 수급(`flow.*`)·공매도(`short.*`)도 원천 stage 6개가 전부
`lag_known=false`(공표 시각 미상)이므로 같은 가정 위에 있다.

지금은 소비자가 질의할 때마다 `lag_overrides` 로 손으로 1을 물려 쓰는 것으로 버티고 있다.
**손으로 안 물리면 조용히 새는 구조**다.

### 고치는 방법과 작업량

**한 번에 전부** 바꿔야 한다. 한 필드군만 고치면 어댑터 안에서 규약이 갈려서 더 나빠진다.

1. 어댑터 기동 시 `dataset_profile` 표를 읽어 `field_id → recommended_lag_sessions` 사전을 만든다
   (표는 72행뿐이라 비용 0).
2. `_specs.py` 의 `lag_sessions` 필드 13개와 관련 상수를 **삭제**한다.
   `_adapter.py:1029`(`_lags`)와 `:444`(`list_fields`)를 그 사전을 읽게 바꾼다.
3. `views.py` 의 `FACTOR_LAG_SESSIONS`·`PRICE_LAG_SESSIONS`·`CONSENSUS_LAG_SESSIONS`·
   `FIN_LAG_SESSIONS`(전부 0, `views.py:60-63`)도 같은 규약으로 정리한다. 다만 이쪽은 매크로 본문에
   구워지는 값이라 카탈로그 재생성이 따라온다.
4. 대장에 없는 필드(어댑터만 아는 것)가 있으면 기동 실패로 막는다 — 조용한 기본값 0 은 금지.

**작업량 2~3일.** 대부분은 코드가 아니라 **기대값 이동**이다:

- **격자 조회가 한 세션 밀린다.** D일 셀이 D−1일 원장 값을 보게 되므로 수급·공매도·신용을 쓰는
  모든 팩터 값이 하루씩 이동한다. 백테스트 수익률이 바뀐다(이것이 **정정**이다).
- **계약 테스트 기대값이 움직인다** — `test_adapters_equity_duckdb.py:141` 의 한 줄 단언은 폐기하고
  필드별 기대 시차 표로 바꿔야 한다. 같은 파일의 셀 값 손검산(P40 이 24필드 × 두 창에서 잰 것)도
  25필드분이 하루 이동한다.
- **재무·컨센서스는 값이 거의 안 움직인다** — 원래 월 1회·분기 1회 갱신이라 하루 미뤄도 같은 값이
  나오는 세션이 대부분이다. 실제로 크게 움직이는 것은 격자 6필드다.
- 소비자가 이미 쓰던 `lag_overrides` 를 걷어낼 수 있다(이중 적용 방지 — 걷어내지 않으면 이틀 밀린다).

### 심각도: **상**

**확정된 look-ahead 가 하나 있고**(`credit.margin_balance`, T+1 공표를 T 로 읽음),
같은 가정 위에 5개 필드가 더 있으며, 대장이 이미 "1세션" 으로 판정을 내렸는데 어댑터가 따르지
않는 상태다. 백테스트 성과를 실제보다 좋게 만드는 방향의 오차라 **연구 결론 자체를 뒤집을 수 있다**.
9개 항목 중 유일하게 "지금 나오는 숫자가 틀렸다" 고 말할 수 있는 항목이다.

## 5. "원천이 안 준 것(=0으로 읽어도 되는 것)" 과 "그냥 모르는 것" 을 소비자가 구분하지 못한다

### 무엇이 문제인가

수급·공매도·신용 같은 일별 데이터는 **격자**(모든 종목 × 모든 거래일)로 만든다. 격자에는 반드시
빈 칸이 생기는데, 빈 칸의 의미가 네 가지로 다르다:

| equity 어휘 | 뜻 | 올바른 읽기 |
|---|---|---|
| `measured` | 원천이 값을 줬다 | 그 값 |
| `src_omitted` | **원천이 그날 그 종목을 정상 처리했는데 행을 안 실었다** | **0** (예: 그날 공매도가 없었다) |
| `empty_response` | 원천에 물었는데 빈 응답이 왔다 | 모름 |
| `not_collected` | 애초에 수집하지 않은 구간 | 모름 |

`src_omitted` 가 중요한 이유: "공매도가 0주였다" 와 "공매도가 얼마인지 모른다" 는 완전히 다른
사실이다. 전자는 유효한 관측(0)이고 후자는 결측이다. 이걸 섞으면 공매도 팩터가 "데이터가 있는
종목만" 을 대상으로 계산되어 **선택 편향**이 생긴다.

equity 층은 이 넷을 구분해 싣고, 필드 계약(FIELD_MAP §1)에도
`src_omitted → CellKind.SOURCE_OMITTED_ZERO` 로 못 박았다. 그런데 워크벤치 도메인 계약이
`SOURCE_OMITTED_ZERO` 셀에 **값이 반드시 있을 것**을 요구한다
(`domain/equity/_models.py:187-199`: OBSERVED·SOURCE_OMITTED_ZERO 는 `value is None` 이면 예외).
equity 는 그 자리를 NULL 로 두기로 결정했으므로(결정 8) 두 계약이 동시에 성립할 수 없다.

S21-3 은 **워크벤치 도메인을 안 고치는 쪽**을 택했다 —
`_adapter.py:163-167` 의 `_FILL_KIND_TO_CELL` 이 `src_omitted → CellKind.MISSING` 으로 접는다.
그래서 소비층은 "0으로 읽어도 되는 결측" 과 "그냥 결측" 을 **구분할 수 없다**.

### 지금 실제로 사고가 나고 있는가

**나고 있다. 규모가 문서에 적힌 절단본 수치보다 세 자릿수 크다.**

서버 실측(각 표 9,201,516셀, `_reject` 제외):

| 표 · 컬럼 | `src_omitted` 셀 | 비중 | 종목 | 기간 |
|---|---:|---:|---:|---|
| `short_daily.fill_kind_short_kiwoom` (키움 공매도) | **3,602,686** | **39.2%** | 2,540 | 2010-01-04 ~ 2026-08-20 |
| `credit_daily.fill_kind` (신용) | **108,611** | 1.18% | 3,175 | 2010-01-04 ~ 2026-08-20 |
| `short_daily.fill_kind_loan_kis` (KIS 대차) | 2,907 | 0.03% | — | — |
| `flow_daily.fill_kind` (수급) | **2,218** | 0.024% | **2** | 2010-01-04 ~ 2016-05-04 |
| **합계** | **3,716,422** | | | |

문서(DESIGN §11 ⑪)가 적어 둔 "절단본 flow 2,218 · short 3,576 · credit 62" 중 flow 의 2,218 은
**절단본 수치가 아니라 서버 전량과 같은 수**다. 이유가 재미있다 — 서버의 flow `src_omitted` 는
**036220(1,570) + 101970(648) 두 종목이 전부**이고, 이 둘이 절단본 15종목에 들어 있다(재상장 2종).
즉 flow 축은 사실상 문제가 없다.

**진짜 문제는 공매도다.** 키움 공매도 격자의 **39.2%**, 3,602,686셀 · 2,540종목 · 15.6년 전 구간이
"공매도 없었음(=0)" 인데 소비자에게는 "모름" 으로 전달된다. 공매도 관련 팩터를 만들면 격자의
40%가 통째로 빠진 채 계산된다 — 그리고 **빠지는 쪽이 무작위가 아니다**(공매도가 걸리지 않는
소형·비인기 종목이 우선적으로 빠진다). 크로스섹션 순위·분위 계산이 체계적으로 왜곡된다.

신용(108,611셀 · 3,175종목)도 같은 성격이나 비중이 1.2%로 훨씬 작다.

부수 확인 — **선언과 어댑터가 여기서도 어긋난다.** 서버 `dataset_profile` 은 격자 6필드의
`supported_cell_kinds` 를 `observed + source_omitted_zero + missing + not_collected + coverage_gap`
5종으로 싣는데, 어댑터 `_adapter.py:461-470` 은 `(OBSERVED, MISSING, NOT_COLLECTED)` 3종만
내보낸다. 항목 4 와 같은 병(대장과 어댑터의 이중 진실)의 다른 증상이다.

### 고치는 방법과 작업량

두 갈래이고, **(b) 를 권한다**.

**(a) equity 쪽에서 값 축과 지식 축을 분리한다** — `dataset_profile` 이 "이 필드는 `src_omitted`
자리를 0으로 읽어도 된다" 를 별도 컬럼으로 싣고, 소비자가 그걸 보고 스스로 0으로 채운다.

- 계약 테스트(`backend/tests/contract/test_raw_observation_port.py`)의 셀 종류 기대값 이동
- **소비층(팩터 계산)에서 `SOURCE_OMITTED_ZERO` 를 실제로 0으로 쓰는 코드** — 이게 진짜 일이다.
  라벨만 전달되고 아무도 안 쓰면 지금과 결과가 같다.

항목 4 와 **같은 파일·같은 성격**이라 함께 처리하면 겹치는 작업이 상당하다.

## 6. 차트용 조정가 뷰(`v_adj_price`)가 재상장 종목의 옛 구간 계수를 새 구간으로 흘린다

### 무엇이 문제인가

주식 분할·병합이 있으면 과거 주가를 보정해야 차트가 이어진다. 이 보정 계수를 누적할 때 **상장이
끊겼다 다시 붙은 종목**(재상장)은 조심해야 한다. 폐지 전 구간에서 있었던 분할의 계수를 재상장
후 구간까지 곱하면, 새 구간의 주가 수준이 통째로 틀어진다.

S23 이 이 문제를 **전방 조정 쪽**(`v_adj_price_fwd`·`v_adj_volume_fwd`·표 `price_adj_daily`)에서는
고쳤다. `views.py:_FWD_CTE` 가 `security_span` 을 ASOF 조인해 구간(`span_seq`)별로 누적을 끊는다.

**고치지 않은 쪽이 `v_cum_adj` 다.** `views.py:160-186` 을 보면 `security_span` 조인이 아예 없다.
그리고 `v_adj_price`·`v_adj_volume` 두 뷰가 이 `v_cum_adj` 를 그대로 읽는다
(`views.py:196·204`). 즉 차트·검산용 경로에는 구간 제한이 없다.

### 지금 실제로 사고가 나고 있는가

**지금은 나지 않는다. 값이 바뀌는 행이 0이다.** 다만 언제든 켜질 수 있는 지뢰다.

서버 실측:
- 구간이 둘 이상인 종목은 **정확히 2개**: `036220`(2 구간) · `101970`(2 구간).
  두 종목의 가격 행을 합쳐 **3,152행**(전체 10,890,251행의 0.029%).
- 이 두 종목의 조정계수(`adj_factor`) 상태:
  - `036220` — 계수 행 **0개** (곱할 것이 없다)
  - `101970` — 계수 행 5개, **전부 `factor_ok = false`** (2015-11-26 ~ 2018-10-15)
- 뷰의 계수 필터가 `WHERE factor_ok AND ...` 이므로 not-ok 계수는 애초에 안 들어온다.
  → **현재 새는 계수가 하나도 없다.** P43 이 표 쪽에서 잰 것과 같은 결론이다
    ("구간 규칙을 껐을 때 달라지는 행 0").

**언제 켜지는가**: 재상장 종목에 `factor_ok=true` 인 계수가 하나라도 생기는 순간. 두 경로가 있다 —
① 새 재상장 종목이 생긴다, ② `101970` 의 5건 중 하나가 규칙 개선으로 ok 로 바뀐다(항목 7 참조).

**누가 읽는가**: 워크벤치는 안 읽는다(`price.adj_close` 는 S23 부터 표 `price_adj_daily` 를 직접
읽는다). 읽는 곳은 ① EG8 교차소스 게이트(`rules_s06.py:512-513`) ② `_asof/v_adj_price/` 회귀 표본
③ parquet·카탈로그를 직접 쓰는 차트·분석. 즉 **백테스트 결과에는 지금도 앞으로도 영향이 없고**,
검산 게이트와 차트가 틀려질 뿐이다.

### 고치는 방법과 작업량

`_FWD_CTE` 의 구간 처리(`spn` CTE 의 `ASOF LEFT JOIN {security_span}` + `PARTITION BY ticker,
span_seq`)를 `v_cum_adj` 템플릿에 그대로 옮긴다. **10줄 남짓**.

주의 두 가지:
- `v_cum_adj` 는 **뒤에서부터 누적**(`ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING`)하는
  as-of 기준이라 전방 조정과 방향이 반대다. 구간 경계 부등호(`>` vs `>=`)를 기계적으로 복사하면
  안 되고, "구간 첫 행 누적 = 1" 이 아니라 "구간 마지막 행 누적 = 1" 이 서야 한다.
- 뷰가 바뀌면 카탈로그를 다시 만들어야 하고(`python -m equity catalog`), EG5c 가 `_asof` 표본
  차이를 잡을 수 있다. 지금은 표본 값이 안 바뀌므로 통과할 것으로 예상되나(P43 실측: n_diff 0),
  안 통과하면 `--rebase-asof` 승인이 필요하다.

작업량 **1~2시간** + 부정 픽스처 1건(합성 재상장 종목에 ok 계수를 심어 구간이 안 새는지 확인).

### 심각도: **하**

영향 종목 2개 · 행 3,152개 · **현재 달라지는 값 0**. 백테스트 경로 밖이다.
S23 이 표 쪽을 고치면서 "이 수정은 데이터 정정이 아니라 **회귀 방지**" 라고 적은 것과 같은 성격이며,
같은 회귀 방지를 뷰 쪽에도 걸어 두는 값싼 마무리다.

## 7. 거래소 기준가와 어긋나는 기업행위 **719건** — 정밀 조정으로는 거의 못 살린다

### 무엇이 문제인가

주식 분할·병합·무상증자가 있으면 거래소(KRX)가 그날 **기준가**를 새로 정해서 발표한다. equity 층은
이걸 이용해 조정계수를 뽑는다: `기준가 ÷ 전일 종가 = 가격 비율 r`, `당일 주식수 ÷ 전일 주식수 =
주식수 비율 S`. 순수한 분할·병합이라면 **시가총액이 변하지 않으므로 `r × S = 1`** 이어야 한다.

`|r × S − 1|` 이 허용치(`factor_product_tol_base` = 0.01, 즉 1%)를 벗어나면 계수를 못 믿겠다는
뜻이라 `krx_base_inconsistent` 로 분류하고 **계수를 만들지 않는다**(`factor_ok=false`, 계수 = 1).
그러면 그 종목의 그 시점 이후 조정 시계열에 **보정되지 않은 가격 점프가 남는다**.

핸드오프에는 "기준가 불일치 151건" 으로 적혀 있으나 이는 옛 수치다.

### 지금 실제로 사고가 나고 있는가

**서버 실측 719건** (S06-2 규칙 개정 후). 종목 515개, 적용일 561일, 2010~2026 전 구간에 고르게
분포(연 19~82건). P43 기록에 따르면 이 719건이 **가격 행 1,077,785개**(전체의 9.9%)에 대해
`n_unadjusted_events > 0` 을 만든다.

**핵심 질문은 "허용치를 조금 풀면 몇 건이 살아나느냐" 였다. 답은 '거의 없다' 다.**

`price_daily` 에서 r 과 S 를 직접 다시 계산해 편차 `|r × S − 1|` 분포를 냈다(719건 전건 계산 성공):

| 편차 구간 | 건수 | 누적 | 뜻 |
|---|---:|---:|---|
| ≤ 0.01 (현 허용치) | 0 | — | 정의상 없음 |
| (0.01, 0.02] | **23** | 23 | 허용치를 2%로 풀면 살아남 |
| (0.02, 0.05] | 91 | 114 | 5%로 풀면 |
| (0.05, 0.10] | 99 | 213 | 10%로 풀면 |
| (0.10, 0.30] | 209 | 422 | |
| (0.30, 1.00] | 218 | 640 | |
| > 1.00 | **79** | 719 | 시총이 2배 이상 변했다 |

분위: p10 = 0.037 · **p50 = 0.208** · p75 = 0.553 · p90 = 1.268 · p99 = 19.4 · 최대 116.8.

**중앙값이 20.8%다.** 3.2%(23건)만 "반올림 차이" 수준이고 나머지는 시가총액이 실제로 크게 변한
사건들이다. 허용치를 1%→2% 로 두 배 풀어도 719건 중 23건(3.2%)만 회수된다.

**사건 종류를 보면 왜인지 분명하다:**

| 사건 유형 | 건수 | ≤2% | ≤5% | ≤10% | 편차 중앙값 | 최대 |
|---|---:|---:|---:|---:|---:|---:|
| `unknown_krx` (DART 공시 없이 기준가·주식수만 움직임) | **568** | 9 | 71 | 129 | 0.268 | 57.6 |
| `capred` (감자) | **109** | 7 | 28 | 58 | 0.093 | 116.8 |
| `split` (액면분할) | 17 | 3 | 9 | 13 | 0.043 | 0.411 |
| `reverse_split` (액면병합) | 15 | 4 | 5 | 12 | 0.060 | 0.326 |
| `bonus` (무상증자) | 10 | 0 | 1 | 1 | 0.352 | 0.662 |

719건 중 **677건(94%)이 `unknown_krx` 와 `capred`** 다. 이 둘은 **시가총액이 안 변한다는 가정
자체가 성립하지 않는 사건**이다 — 유상증자 권리락, 유상감자, 현물배당처럼 회사에 돈이 들어오거나
나가는 사건은 시총이 실제로 변한다. 즉 이건 "계수 계산이 부정확하다" 가 아니라 **"MVP 가 다루기로
한 4개 사건 유형(분할·병합·무상증자·무상감자) 밖의 사건이 격자에 들어와 있다"** 는 뜻이다.

시총 불변이 실제로 성립해야 하는 MVP 유형(`split`·`reverse_split`·`bonus`)은 **42건**뿐이고,
그 중 허용치 2%로 살아나는 것은 7건, 5%로 15건이다.

### 고치는 방법과 작업량

**허용치 조정은 권하지 않는다.** 3.2% 회수를 위해 허용 오차를 두 배로 늘리면 진짜로 틀린 계수를
통과시킬 위험이 커진다. 대신 세 갈래를 권한다:

1. **사건 유형을 먼저 가른다** (권장, **2~3일**) — `unknown_krx`(568) 와 `capred`(109) 를
   "시총 불변 검사 대상" 에서 빼고, 별도 사유
   (`non_neutral_event` 같은 이름)로 재분류한다. 그러면 `krx_base_inconsistent` 는 42건으로 줄고,
   "계수를 못 낸 진짜 이유" 가 소비자에게 정직하게 전달된다. 조정 결과는 **변하지 않는다**
   (어차피 계수를 안 만든다) — 바뀌는 것은 라벨과 그로 인한 소비 판단이다.
   `unknown_krx` 568건은 별도로 "이게 정말 유상증자·권리락인가" 를 표본 조사할 필요가 있다.
2. **MVP 유형 42건만 정밀 조사** (**1일**) — 편차가 4.3~6% 중앙값이라 다른 원인
   (전일 종가가 기준가일·주식수 관측 시점 어긋남)이 있을 가능성이 있다. 이 42건은 손으로 볼 만한
   분량이다. 여기서 원인이 잡히면 진짜 정정이 된다.
3. **허용치 상향은 하지 않는다** — 하더라도 MVP 유형에 한정해서, 위 2번 조사 결과를 근거로.

### 심각도: **중**

**데이터가 틀린 것은 아니다** — equity 층은 못 믿을 계수를 만들지 않았고
(`factor_ok=false`, 계수 = 1), 몇 건이 걸리는지를 `n_unadjusted_events` 로 정직하게 싣는다.
문제는 ① 라벨이 오해를 유발한다는 것(`krx_base_inconsistent` 는 "우리 계산이 부정확하다" 로
읽히지만 실제로는 "이 사건은 우리 모델 밖이다" 다), ② 이 719건 탓에 가격 행의 9.9%가
"불완전" 딱지를 달아 소비자가 일률 필터를 걸면 유니버스가 크게 줄어든다는 것이다.
**정밀 조정으로는 3%밖에 못 살리므로, 고칠 것은 계산이 아니라 분류다.**

내가 서버에서 **읽기 전용으로** EG3 의 무거운 블록들을 따로 재실행해 재 봤다(캐시가 따뜻한
단독 세션이라 빌드 중보다 유리한 조건):

| EG3 블록 | 하는 일 | 시간 |
|---|---|---:|
| ② 격자 양방향 | `universe_daily` 10.9M 에서 격자를 다시 만들어 양방향 대조 | **4.2s** |
| ③a measured → 원장 | 측정 셀마다 원장 행이 있는지 | 2.0s |
| ③b 원장 → measured | 원장 행마다 측정 셀이 있는지(+격자 소속) | 3.8s |
| ③c 17축 원값 재조인 | 원장 값과 산출 값이 컬럼 17개 전부 같은지 | 2.6s |
| ⑤ 잔고 > 주식수 | `price_daily` 재조인 | 1.0s |
| ④ 채움 규약 | 단일 스캔 | 0.1s |
| (대조) 단순 조인 1회 | | 0.9s |

즉 **개별 검사는 하나하나 싸다**. 비싼 것은 **같은 무거운 부분질의를 여러 번 다시 만드는 것**이다.
`rules_s10.py:225-315` 를 보면 격자 재생성 식(`_grid_sql()`, `universe_daily` 10.9M 전량 스캔)이
② 와 ③ 에 **4번 인라인**되고, 잔고 초과 후보식(`_over_shares_sql()`)이 ⑤ 안에서 **3번** 인라인된다.
DuckDB 가 공통 부분식을 항상 재사용해 주지는 않는다.

**`dataset_profile` 이 더 큰 표적이다** — 결과가 72행인데 60초가 걸린다. 이 표는 필드마다
"실제 커버리지가 몇 %인가" 를 원본 표 위에서 재는 구조라, 사실상 전 표를 한 번씩 훑는다.
전량 재빌드의 15%가 이 한 표다.

### 고치는 방법과 작업량

**검사를 약하게 만들지 않고** 줄일 수 있는 여지가 명확하다:

1. **공통 부분식을 임시 표로 한 번만 만든다** — `grid`(4회) 와 `over_src`(3회)를
   `CREATE TEMP TABLE` 로 한 번 물리고 재사용. **술어는 한 글자도 안 바뀐다** — 순수한 중복 제거다.
   격자 재생성이 4.2초짜리이므로 3회분 회수 = 약 12초 절약(추정). 작업량 **반나절**.
   격자 3표가 같은 구조이므로 한 번 고치면 셋에 다 적용된다.
2. **같은 관계를 훑는 `_row()` 호출을 합친다** — 지금 8개 문장 그룹이 각각 독립 스캔이다.
   같은 관계를 보는 것끼리 하나의 SELECT 로 묶으면 스캔 횟수가 준다. 작업량 **반나절**, 절약 추정
   10~20%.
3. **`dataset_profile` 의 커버리지 측정을 파티션 단위 집계로** — 60초짜리라 여기가 더 크지만
   구조 변경이라 작업량 **1~2일**, 리스크도 더 크다.

**검사를 약화시키지 않는 경계선**: EG3 는 "산출식을 다시 계산하지 말 것"(GATES §1)이라는 규율이
있다 — 검사가 산출과 같은 식을 쓰면 항진명제가 되어 아무것도 못 잡는다. 위 1·2번은
**입력에서 유도한 중간 결과를 재사용**하는 것이지 산출식을 끌어오는 것이 아니므로 이 규율을 깨지
않는다. 3번은 커버리지 정의 자체를 건드리므로 EG2-P08(정수 분자·분모 + 고정 반올림) 규약을 유지하는지
확인이 필요하다.

### 심각도: **하**

7분짜리 재빌드가 5분이 되는 문제다. **정확성 위험이 전혀 없고**, 지금 병목이 되는 워크플로도
없다(전량 재빌드는 하루에 몇 번 하지 않는다). 다른 여덟 항목을 다 처리한 뒤 손이 남으면 하는 일이다.
다만 1번(공통 부분식)은 반나절에 12초를 회수하므로 다른 작업 중에 곁들이기 좋다.

## 9. 거래소 매매거래정지 목록을 수집하지 않아, 정지의 **약 절반**을 "그냥 거래가 없었다" 로 처리한다

### 무엇이 문제인가

주식이 거래되지 않는 날은 두 가지다: ① 거래소가 **매매거래정지**를 걸었다(살 수도 팔 수도 없다),
② 그냥 **아무도 안 샀다**(사려면 살 수 있었다). 백테스트에서 이 둘은 완전히 다르다 —
①인데 ②로 알고 있으면 **거래 불가 종목을 샀다고 계산한다**. 정지 종목은 정지 해제일에 가격이
크게 튀므로(±30%가 흔하다) 성과가 통째로 왜곡된다.

지금 equity 층은 정지를 **공시 문구로 추정한다** — `stg_disclosure.report_nm` 에
`'매매거래정지'` 가 들어간 공시(서버 11,970건, 2010-01-04~2026-09-01)를 찾아 지정·해제 구간을
만든다(`sql/universe_daily.sql:101-105·170`). 거래소가 발표하는 **매매거래정지 현황 목록 자체는
수집하지 않는다**.

공시로 안 잡힌 정지는 무거래 사유 우선순위의 맨 마지막인 `illiquid`(그냥 거래가 없었음)로 떨어진다.
안전장치가 하나 있다 — 무거래가 `no_trade_run_k`(=5) 세션 이상 이어지면 이유와 무관하게
`suspended` 로 본다. 그래서 **긴 정지는 우연히 잡히고 짧은 정지가 샌다**.

### 지금 실제로 사고가 나고 있는가

**나고 있다. 공시 축의 적중률이 약 50%다.**

2026-09-01 부터 KRX 일별 마스터(`stg_master_daily`)가 `is_trade_halt`(거래소가 직접 주는 정지
플래그)를 싣기 시작했다. 이걸 대조축으로 삼아 equity 의 판정과 비교했다.

2026-09-01 에 KRX 가 정지로 표시한 종목 **125개**(코스피 37 · 코스닥 88)를, equity 가 마지막
백필일(2026-08-20)에 어떻게 라벨했는지:

| equity 라벨 (2026-08-20) | 종목 | 판정 |
|---|---:|---|
| `suspended` / `halt_disclosed` (공시로 잡음) | **62** | ✅ 정확히 잡았다 |
| `suspended` / 사유 `none`(정지 구간 열림) | 1 | ✅ |
| `suspended` / `illiquid` (무거래 5일 이상이라 우연히 잡힘) | **28** | △ 결과는 맞으나 이유는 틀렸다 |
| `suspended` / `corp_action_window` | 1 | △ |
| **`listed` / `illiquid`** (무거래인데 정지가 아니라고 봤다) | **12** | ❌ **이 항목의 결함 그 자체** |
| `listed` / `none` (08-20 에는 정상 거래) | 21 | — 08-21~09-01 사이에 시작된 정지로 보임 |

종목 유형: 보통주 102 · 스팩 15 · 우선주 4 · 외국주 2 · ETF 1 · 리츠 1.

읽는 법: **공시 문구 축이 잡은 것은 125건 중 63건(약 50%)** 이다. 무거래 5일 규칙이 29건을 더
건졌고, **12건은 어느 그물에도 안 걸려 투자 가능 종목으로 남았다.**
(주의: 08-20 과 09-01 은 8세션 차이라 이 대조는 **근사**다. 21건의 `listed/none` 은 그 사이에
시작된 정지일 가능성이 높아 오류로 세지 않았다. 완전한 대조는 백필이 09-01 이후로 연장돼야 가능하다.)

`illiquid` 124,384셀 중 **56,804셀(1,142종목)은 5일 규칙으로 `suspended`** 가 되어 유니버스에서

**정리**: 보통주 기준으로 오염 규모는 0.05% 로 작다. 하지만 **오염 방향이 나쁘다** —
정지 종목은 재개일에 크게 튀므로 몇 천 셀이 저변동성·역추세 계열 팩터의 롱사이드를 통째로 설명할
수 있다(`DATA_CATALOG.md` MS-04·DS-02 가 같은 위험을 이미 지적해 두었다).

### 고치는 방법과 작업량

**앞으로의 데이터는 이미 공짜로 해결됐다.**
`stg_master_daily`(KRX 일별 마스터, 크론 `daily_wise` 가 매일 수집 중)에 `is_trade_halt`·
`is_admin_issue`·`is_liquidation` 이 실려 있고, `universe_daily.sql:19` 가 이미
"2026-09-01~ `stg_master_daily` 행이 있으면 `is_trade_halt`(측정)가 우선" 이라고 구현해 두었다.
**추가 API 콜 0, 추가 작업 0.** 다만 지금 stage 에 있는 것은 2026-09-01·09-02 **이틀뿐**이라
효력은 앞으로 쌓이는 만큼이다.

**과거(2010-01-04 ~ 2026-08-31)는 사정이 다르다.** 세 갈래가 있다:

| 방법 | 커버 | 작업량 | 한계 |
|---|---|---|---|
| (a) 키움 `ka10099`(종목 상태 스냅샷) | **오늘 이후만** | 이미 COLLECT_PLAN E2 에 있음 | 과거 소급 불가 — "그날 상태는 복원 불가" |

| (c) KRX 정보데이터시스템 매매거래정지 이력 | 조회 가능 구간 | **미검증 — 먼저 확인해야 한다** | 소급 범위가 관건 |

**권고 순서**:
1. **(c)의 소급 범위를 먼저 확인한다**(반나절). 여기서 2010년까지 나오면 이 항목은 완전 해결이다.
2. 안 되면 **현 상태를 정직하게 표기한다**(1일) — `universe_daily` 에
   `halt_basis`(`measured_krx` / `disclosed` / `unknown`) 컬럼을 두고,
   `dataset_profile.universe.status` 의 `requires_confirmation` 을 `true` 로 올린다.
   **소비자가 "2026-09 이전 정지 판정은 공시 추정이고 적중률 약 50%" 를 데이터에서 읽게** 만든다.
3. equity 쪽 작업량은 (c)가 되는 경우 stage 표 하나를 입력에 추가하고 우선순위 ① 에 꽂는 것뿐
   (**1일**). 지금 `is_trade_halt` 우선 규칙이 이미 있으므로 자리는 비어 있다.

### 심각도: **중**

보통주 기준 오염 셀이 0.054%로 작고, 5일 규칙이 긴 정지를 대부분 건지며, 앞으로의 데이터는
0콜로 해결됐다. 그러나 **적중률 50%는 "정지 판정을 신뢰할 수 있다" 고 말하기에는 낮고**,
오염이 저변동성 팩터라는 특정 전략군에 집중적으로 나타난다. 무엇보다 **소급 수집이 불가능할 수
있는 항목**이라, "지금 못 고친다" 는 결론이 나오더라도 **그 사실을 데이터에 표기하는 일(위 2번)은
반드시 해야 한다** — 안 그러면 소비자가 정지 판정을 측정값으로 오해한다.

## 10. 정지된 채 재개하지 않는 종목의 기업행위가 **백테스트 run 전체를 죽인다** (전 종목 실측에서 처음 드러남)

### 무엇이 문제인가

2026-09-06, 서버 전 종목 데이터 위에서 MVP-B 백테스트를 처음 돌렸다(그전까지는 절단본 15종목
에서만 완주했다). **1년 구간에서 즉시 실패했다.**

```
CorporateActionWithoutBar: no traded session for instrument at or after corporate action
  instrument=450140:1 ts=2025-12-15 action=reverse_split ratio=0.976965827588816
  feed_sessions=242 last_session=2025-12-30
```

세 가지 **각각은 옳은** 결정이 겹쳐서 생긴다.

1. **어댑터는 `price_kind='reference'` 행(거래량 0 · 정지일 기준가)을 Bar 로 내지 않는다** —
   `adapters/equity_duckdb.py:24-25`. 거래할 수 없는 세션을 거래 가능한 바로 내면 안 되므로 옳다.
2. **equity 는 `adj_factor.factor_ok` 행을 전부 사건으로 낸다** — 같은 파일
   `EquityCorporateActionSource`(`:568-620`). 정지 여부를 보지 않는다.
3. **커널은 사건 시점 이후 그 종목의 바가 있는 세션을 반드시 찾는다** —
   `engine/loop.py:760-769` `_settlement_session`. 못 찾으면 예외를 던진다.

정지된 뒤 데이터 끝까지 재개하지 않은 종목에 감자·병합이 걸리면 (1) 때문에 바가 없고,
(2) 때문에 사건은 나가고, (3) 때문에 **run 전체가 죽는다**. 그 종목 하나를 건너뛰는 것이 아니라
백테스트가 통째로 중단된다.

### 규모 (서버 실측, 2026-09-06)

`adj_factor.factor_ok` 사건 중 **해당 종목의 마지막 `price_kind='trade'` 행보다 apply_date 가
뒤인 것**:

| 축 | 실측 |
|---|---|
| 사건 | **26건** |
| 종목 | **25종목** |
| 유형 | `capred` 20 · `reverse_split` 5 · `bonus` 1 |
| `apply_basis` | `krx_base_price` 18 · `nominal` 8 |
| 마지막 거래일 ~ 사건일 간격 | 최소 **1일** · 중앙 **약 200일** · 최대 **3,495일**(9.6년) |
| `universe_daily.status` | **25종목 전부 `suspended`** |

`krx.liquid`·`krx.investable` 은 술어에 `status = 'listed'` 가 있어 이 25종목을 멤버로 잡지
않는다. 즉 **유동성 유니버스 백테스트는 지나가고, 전 종목(`krx.common-stock`) 백테스트만
죽는다** — 그래서 지금까지 드러나지 않았다.

### 지금 실제로 사고가 나고 있는가

**예 — 확정.** 재현 절차는 아래 한 줄이고, 서버에서 2분 34초 만에 실패한다.

```bash
uv run --project backend python database/scripts/run_mvp_backtest.py \
  --root data/equity --start 2025-01-02 --end 2025-12-30 \
  --universe krx.common-stock --price-field price.adj_close --top 20
```

- **상황**: 전 종목(`krx.common-stock`) 유니버스, 2025년 1년 구간. 종목 2,428 · 세션 242.
- **인풋**: 종목 `450140` 이 2025-12-12 을 마지막으로 거래가 정지되고 데이터 끝(2026-01-06)까지
  `price_kind='reference'` 만 남는다. `adj_factor` 는 그 종목에 `capred`
  (`apply_date=2025-12-15` · `share_factor=0.976965827588816` · `apply_basis='nominal'`)를 낸다.
- **에러 위치**: `backend/src/backtest_engine/engine/loop.py:760-769` —
  `_settlement_session` 이 `snapshot.ts >= action.ts ∧ snapshot.has(instrument)` 인 스냅샷을
  끝까지 못 찾고 `CorporateActionWithoutBar` 를 던진다.
- **위험성**: **가용성 결함**이다. 한 종목의 기업행위 하나가 전 종목 백테스트 전체를 실패시키고,
  부분 결과도 남지 않는다(`total_return=None`). 소비자가 전 종목 유니버스로 전략을 돌리는 순간
  100% 재현되며, 우회하려면 유니버스를 줄이는 수밖에 없어 **전 종목 백테스트라는 기능 자체가
  현재 동작하지 않는다.**

### 왜 "그냥 사건을 버리면 된다" 가 답이 아닌가

정지 중인 종목을 **보유한 채** 감자가 일어나면 주식 수는 실제로 변한다. 사건을 조용히 버리면
그 포지션의 수량이 틀린 채 남고, 재상장하면 그 시점부터 평가가 어긋난다. 26건 중 18건은
`apply_basis='krx_base_price'` 로, **거래소가 정지 기간에 기준가를 실제로 공표한** 사건이다 —
"아무 일도 없었다" 로 처리할 근거가 없다.

따라서 이것은 계산 버그가 아니라 **커널 정책 결정**이다. 후보 셋:

| 안 | 내용 | 대가 |
|---|---|---|
| **(가)** 커널이 사건을 마지막 바 세션에 정산 | `_settlement_session` 이 못 찾으면 예외 대신 마지막 보유 가능 세션으로 후퇴 | 정산 시점이 실제와 다름. 다만 그 뒤로 거래가 없어 체결에는 영향 없음 |
| **(나)** 커널이 "정지 중 사건" 을 보유 수량에만 적용하고 바를 요구하지 않음 | 사건 처리와 바 존재를 분리 | 커널 이벤트 루프 구조 변경. 가장 정확하지만 가장 비쌈 |
| **(다)** equity 가 사건에 "재개 없음" 표시를 실어 어댑터가 정책대로 처리 | `adj_factor` 에 컬럼 1개(마지막 거래일 이후 여부) | equity 는 한 시간이면 끝나지만 결정은 여전히 커널 몫 |

**권고는 (가) + (다)** 다. (다)로 equity 가 사실을 표기하고, (가)로 커널이 run 을 죽이지 않게
한 뒤, (나)는 정지 종목 보유 정책을 정할 때 함께 다룬다. 이 항목은
[engine-kernel-considerations] 의 「정지 세션에 바가 없는 목표」와 같은 뿌리다.

### 고치는 방법과 작업량

| 단계 | 하는 일 | 시간 |
|---|---|---|
| 1 | 재현 test 를 절단본에 심는다 — 정지 후 재개 없는 종목 + 감자 1건 픽스처 | 2~3h |
| 2 | (다) `adj_factor` 에 `no_bar_after_apply` 표기 + 게이트 지표 + 기준값 | 3~4h |
| 3 | (가) `_settlement_session` 후퇴 규칙 + 커널 test | 4~6h |
| 4 | 전 종목 백테스트 재실행으로 확인 | 1h |

**합계 약 1.5일.** 단, 3단계는 엔진 커널 의미론 변경이라 **사람 승인이 필요하다.**

### 심각도: **상**

전 종목 백테스트가 현재 불가능하다. 이 층의 존재 목적이 "백테스팅에 적절히 구성된 데이터베이스"
이므로, 팩터를 늘리는 어떤 작업보다 앞선다. 다만 유동성 유니버스(`krx.liquid`)로는 돌아가므로
**전면 중단은 아니다.**
