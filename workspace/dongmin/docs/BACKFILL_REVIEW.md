## 2. 수집기 blocker — 착수 전 수정

### B1. `ord` 미합성 → 동일 응답행이 조용히 압축된다 【실측】

`store()`의 PK가 행 내용 해시(`row_hash`)라, DART가 한 응답 안에 **바이트 단위 동일한 행**을 여러 개 주면 `INSERT OR IGNORE`가 1행으로 접는다. 응답 배열 인덱스를 키에 넣지 않기 때문이다.

로컬 파일럿 실측 (`ingest_log.n_rows` vs 실제 적재):

| 엔드포인트 | API | DB | 유실 |
|---|---:|---:|---:|
| `audit` | 45 | 39 | **13.3%** |
| `tesstk` | 129 | 115 | **10.9%** |
| `dividend` | 150 | 142 | **5.3%** |
| `capital` | 50 | 49 | 2.0% |
| `fin`·`elestock`·`majorstock`·`shares`·`hyslr`·`company` | — | — | **0** |

재무는 각 행이 `(sj_div, account_id, ord, account_detail)`로 갈려 유실이 없다. 배당·자사주·감사의견처럼 **행 자체가 반복되는** 엔드포인트에서만 발생한다. DEFECT-A01(`irdsSttus` 완전중복 2행)이 그 3종에도 적용된다는 게 새로 확인된 것이다.

`SPEC[*]["key"]`에 `ord`가 적혀 있으나 **코드 어디에서도 참조되지 않는 죽은 설정**이다.

**수정**: `store()`에서 `enumerate(rows)`로 응답 배열 인덱스를 합성해 해시에 포함.

### B2. `013` 영구 잠금 — 미공시 기수가 되살아나지 않는다

`--years` 미지정 시 기본이 `range(2015, 2027)` = FY2015~**FY2026**이다. FY2026 정기보고서는 아직 제출 시점이 안 왔으므로 전건 `013`이 온다.

- `VERDICT["013"] = "no_data"` → `ingest_log.status='no_data'` → `done` 집합이 `('ok','no_data')`를 종결로 본다
- 2027년에 실제 공시가 올라와도 **다시 호출되지 않는다**
- `no_data_pending` · `next_retry_at` · `period_end + 161일` 판정이 코드·스키마 어디에도 없다 (`grep` 0건)

설계 §3-1이 "이 표에서 유일하게 사소하지 않은 항목"이라 못박은 시나리오가 그대로 발생한다. corp_year 축 엔드포인트 × 3,478사 ≈ **23,000 유닛이 FY2026에 대해 영구 잠긴다.** 감사의견 거절로 사업보고서를 늦게 내는 종목도 같은 방식으로 소실된다.

### B3. 네트워크 예외 재시도 0회 — verdict와 status를 혼동했다 【실측】

```python
v, st = ("error", "exc") if j is None else classify(j)   # v="error", st="exc"
...
if v not in ("retry", "exc") or attempt == RETRY_MAX:    # v 를 검사하는데 "exc" 는 st 값
    return rows, v, st
```

`v`가 `"error"`라 조건이 참이 되어 **첫 시도에서 즉시 반환**된다. `"exc"` 분기는 도달 불가능한 죽은 조건이다. `RETRY_MAX`/`RETRY_BASE`는 `800`/`900`에만 살아 있다.

12일 실행에서 커넥션 리셋 한 번에 유닛이 `error`로 떨어지고, `done`이 그걸 종결로 안 봐서 30분 캐치업 틱마다 재발사된다.

### B4. `STAGES` 순서가 `acc_mt` 선행조건을 역전

```python
STAGES = {1: ["fin"],                                  # ← 재무가 먼저
          2: ["company", "elestock", "majorstock"],    # ← acc_mt 가 나중
          3: [...]}
```

설계 §2 일정표는 `P1 기반(company) → P2 연간재무`이고 P2 선행조건란에 **"P1b 필수(acc_mt 없으면 013 판별 불가)"**라고 명시돼 있다. stage 1에서 나오는 013은 `acc_mt`가 없어 B2를 고쳐도 판정 자체가 불가능하다. 3월 결산 법인은 `period_end`가 9개월 어긋나므로 12월 결산 폴백도 안전하지 않다.

## 3. 통합층 결함 — 콜 0으로 수정, 미루면 전량 재빌드

### T1. 금융업 매출이 결측인데 `revenue_basis='standard'`로 위장된다

`REVENUE_BY_SECTOR`(`fin_map.py:94`)가 **어디서도 import되지 않는 죽은 코드**다. `build_panel.py`가 `basis = "standard"`를 하드코딩한다.

결과: KB금융·삼성생명이 `revenue=NULL` + `revenue_basis='standard'`. 전 108행의 `revenue_basis`가 예외 없이 `'standard'`다. 결측이 정상 표기로 위장되어 사후 진단도 불가능하다.

**원재료는 원장에 다 있다** — KB금융 이자수익 291,561억 · 수수료수익 57,735억 · 보험수익 123,765억.

### T2. 섹터 없이 금융업을 판별할 수 있다 — WICS 5,174콜 불필요 【실측】

| | `Revenue` | `RevenueFromInterest` | `CostOfSales` |
|---|---:|---:|---:|
| KB금융 | **0** | 1 | 0 |
| 삼성생명 | **0** | 1 | 0 |
| 미래에셋증권 | 1 | 1 | 0 |
| 나머지 7사 | 1 | 0 | 1 |

`RevenueFromInterest` 존재 여부로는 안 갈린다 — 증권도 보유한다. **`ifrs-full_Revenue` 태그 부재가 정확히 은행·보험만 집어낸다.** `resolve()`가 `revenue`에 `missing`을 반환한 행에만 대체 규칙을 태우면 된다.

남는 미결: 은행이냐 보험이냐(어느 합산식)는 이 패턴으로 안 갈린다. KB금융도 보험 태그를 갖는다(KB라이프 연결). `FACTORS.md` §8이 이미 미결로 남긴 항목이고, 원장에 원문이 다 들어가면 나중에 어느 쪽이든 만들 수 있다.

### T3. `term_rank=1`은 재작성 값이다 — look-ahead 원천 【실측】

삼성생명 제69기말(2024-12-31)을 각 보고서가 다르게 말한다 (억원):

| 보고서 | 부채총계 | 자본총계 |
|---|---:|---:|
| 사업보고서 | 2,741,161 | **381,026** |
| 분기보고서 3종 | 2,794,809 | **327,379** |

차이 53,647억 = **자본의 16.4%**. 2024년말 실제 공시는 32.7조이고, 38.1조는 2025년 보험부채 산출지침 변경에 따른 **소급 재작성치**다. 이마트도 제14기말에서 993억 차이가 난다.

`term_rank=1`을 "전년 실적"으로 쓰면 그 시점에 알 수 없던 값을 읽는다. 예외도 NULL도 나지 않는다.

### T4. `term_rank=2`의 64%가 유령 행

`financials` 28행 중 **18행이 전 항목 결측**이다 (`term_rank=0`·`1`은 결측 0).

분기 보고서에 전전기 재무상태표는 원래 오지 않는데, `bfefrmtrm_amount`가 주변 계정(사용권자산 등)에 몇 건 채워져 있다는 이유만으로 파티션이 생긴다. KB금융 11012는 `total_liab` 한 칸만 있고 자산·자본이 NULL이라, 자산 없이 부채만 읽으면 부채비율이 발산한다.

전량 백필하면 (3,478사 × 11년 × 3분기) 규모의 빈 행이 생긴다.

### T3·T4 종합 → 스테이지를 당기만 펼친다

백필이 FY2015~2025 연간 + FY2016~2025 분기를 전부 받으므로, **당기 축만으로 연간 11개 + 분기 30개 관측이 쌓인다.** 전년 동기는 그해 보고서의 당기값으로 확보되므로 YoY에 전기 축이 필요 없다.

전기 축의 고유 용도는 **재작성 탐지** 하나뿐인데, T3이 보여주듯 그건 감사 작업이지 상시 파이프라인이 아니다. 원장이 `frmtrm_q_amount`·`bfefrmtrm_amount`를 그대로 보존하므로 필요할 때 다시 펼치면 되고 정보 손실은 0이다.

부수 효과로 DEFECT-C03(전기를 `frmtrm_amount`에서 읽어 손익·CF가 100% 결측)이 소멸한다.

### T5. 매핑 누락 2건 — 값이 원장에 있는데 못 쓴다

- **`cash` (KB금융)** — 은행 BS 계정은 `CashAndDuefromBanks`(현금 및 예치금)인데 규칙이 `CashAndCashEquivalents`만 본다
- **`lease_liab` (삼성생명)** — BS에 `LeaseLiabilities` 9행이 있는데 규칙이 `Current`/`Noncurrent` 접두형만 본다

이마트 등 5사는 리스부채가 `OtherCurrentFinancialLiabilities`에 묻혀 원장에 별도 계정이 없다(같은 BS에 사용권자산 29,124억은 있다). 유통·항공·통신처럼 리스 비중이 큰 업종이 체계적으로 저부채로 보인다.

### T6. 결측 사유가 BS·CF 계열에 안 남는다

`fin_reject` 213행의 사유가 전부 `empty_term` 한 종류이고 item이 전부 IS·CIS다. `resolve()`가 재무제표 pool 자체를 못 찾으면 `"missing"`을 반환하는데 `build_panel.py`가 그걸 기록에서 제외한다.

T1·T5의 결측이 로그에 한 건도 없다. 백필 후 "왜 비었나"를 되짚으려면 원장까지 손으로 파야 한다.
