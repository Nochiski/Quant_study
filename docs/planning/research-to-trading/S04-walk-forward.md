# S04 첫 slice — 워크포워드 연결곡선의 계좌 경계

## 목적

최종 목적은 감당 가능한 위험 안에서 비용 후 수익을 내는 자동매매다. 이를 위해 검증 창의 선택 절차를
평가한 곡선과 실제 하나의 계좌가 낸 손익을 구분해야 한다. 현재 창 수익률 연결을 실제 연속 계좌 성과로
읽으면 진입 비용·경계 거래·수량 변화가 빠진 비교에 과한 확신을 줄 수 있다.

이번 slice는 기존 결과의 의미를 API와 실제 실험 화면에 전달하고, 합성 장부로 두 의미의 차이를
입증한다. 기존 곡선·샤프·유지율·창 선택 규칙·trial key·설계 판본은 변경하지 않는다. 연속 계좌
실행기나 반증 시험 전체를 구현한 상태가 아니다.

## 질문과 현재 계산 계약

`domain/experiment/_walk_forward.py::stitch_out_of_sample`은 각 검증 실행의 첫 snapshot을 분모로
삼아 창 내부의 인접 snapshot 수익률을 잇는다. 첫 창 첫 점을 1.0으로 두고 다음 창의 첫 점은 추가하지
않는다. 따라서 다음 의미를 갖는다.

- 검증 창마다 기존 실행 설정의 같은 초기자본으로 새 실행을 시작한다.
- 초기자본에서 각 창의 첫 snapshot까지 발생한 진입 비용과 손익은 연결 수익률에 포함하지 않는다.
- 다음 창은 이전 창의 현금·보유 수량·미체결 주문을 받지 않는다. 경계에서 기존 보유를 바꾸기 위한
  실제 매도·매수 비용을 연결곡선이 새로 계산하지 않는다.
- 각 창의 첫 snapshot 이후 그 실행이 이미 반영한 거래 비용과 손익은 기존대로 포함한다.

이 결과는 학습에서 고른 파라미터가 각 검증 창 안에서 보인 수익률 비교다. 하나의 자본과 보유 상태를
이어 실행한 계좌 평가가 아니다. 첫 snapshot을 초기자본으로 바꾸거나 창 첫 점을 새로 삽입하는 것은
이번 의미 표시 수정이 아니라 별도 계산 계약 변경이다.

## 구현과 호환성

정본은 기존 계산 owner인 `domain/experiment/_walk_forward.py`에 추가한
`WalkForwardEvaluationBasis.WINDOW_RESTART_RETURNS`와 한글 `WALK_FORWARD_INTERPRETATION`이다.
이 enum과 안내를 기존 domain facade로 공개한다. `application/experiment_run/_service.py`의
`WalkForwardReport`는 다음 두 기본 필드를 추가한다.

| 필드 | 값·책임 |
|---|---|
| `evaluation_basis` | `window_restart_returns`: 수치가 어떤 평가인지 기계적으로 구분하는 값 |
| `interpretation` | 창별 초기자본 재시작, 첫 snapshot 이전 진입 비용·손익 제외, 현금·보유 수량 미이월을 설명한 backend 한글 문장 |

기존 `GET /api/v1/experiments/{id}/walk-forward` 반환 경로가 이 필드를 JSON에 담는다. 완료·진행 중·실패·
옛 설계의 결과에서도 같은 계산 방식의 안내를 제공하며, 결과가 없는 이유는 기존 `gap`이 별도로 전달한다.
이는 산출된 곡선이 없는데 곡선이 있다고 주장하는 표시가 아니다.

기본 필드 추가여서 기존 Python 위치 인자 호출은 유지된다. 기존 JSON 필드와 값은 그대로이며 기존
클라이언트는 추가 필드를 무시할 수 있다. OpenAPI와 생성 TypeScript 타입을 함께 갱신했다. 새 frontend는
실험 상세의 워크포워드 제목 바로 아래, 샤프·유지율 요약 앞에 backend 문장을 그대로 표시한다. backend
문장을 다시 조립하거나 frontend에서 계좌 계산을 추론하지 않는다. 옛 서버가 필드를 주지 않으면 계좌
연결 방식을 확인할 수 없다는 ko/en 안내를 보여 준다.

현재 별도 워크포워드 export API는 없으므로 새 export 형식은 만들지 않는다. 현재 API 응답을 저장하는
소비자는 새 의미 필드를 함께 보존할 수 있다. 기존 실험 저장 행·실행 manifest·trial 원장에 새 판본을
쓰거나 과거 결과 파일을 재작성하지 않는다. 향후 결과 export가 생기면 이 두 필드를 포함해야 한다.

UI는 기존 section·문단·표를 유지했다. ui-ux-pro-max의 시계열 설명을 가시적 요약으로 제공하는 지침을
적용했으며 새 차트나 디자인 체계를 만들지 않았다. 기존 US-SM-15 실험 모니터 수용 기준과 해당
US-SM-14·15 태그 e2e에 안내 확인을 추가했다.

## 증거 — 독립 합성 장부

`backend/tests/domain/test_walk_forward_account_boundary.py`는 원장 데이터 없이 초기자본 1000원,
두 개 검증 창, 종목 A→B 교체, 각 창에서 매수가 100원·종가 110원인 작은 fixture를 사용한다. 주문당
고정 비용과 정수 주 수를 명시하고 기존 stitch 함수의 결과를 독립된 손계산 계좌와 비교한다.

| 항목 | 주문 비용 0원 | 주문 비용 10원 |
|---|---:|---:|
| 각 독립 실행의 매수 수량 | 10주 | 9주 |
| 각 창 첫 snapshot | 1000원 | 990원 |
| 각 창 마지막 snapshot | 1100원 | 1080원 |
| 현행 연결곡선 최종값 | 1.21 | `(1080/990)^2 = 144/121 ≈ 1.190083` |
| 연속 계좌의 다음 창 B 매수 수량 | 11주 | 10주 |
| 연속 계좌의 최종 현금 | 0원 | 60원 |
| 연속 계좌 최종 평가액 | 1210원 | 1160원 |
| 초기자본 대비 연속 계좌 배수 | 1.21 | 1.16 |

10원 비용 사례에서 첫 A 매수 후 현금은 90원이고 첫 창 끝 평가액은 1080원이다. 경계에서 A 9주를
110원에 팔아 비용 10원을 내면 현금은 1070원이다. B 10주를 100원에 사고 비용 10원을 내면 현금은
60원이다. B가 110원이 되면 최종 평가액은 1160원이다. 첫 매수·경계 매도·경계 매수에 총 30원의
비용을 낸다. 독립 실행을 재시작한 두 번째 창은 9주를 사므로 보유 수량과 남은 현금부터 달라진다.

비용 0원 사례는 두 계산이 일치하는 통제 사례다. 비용이 있는 사례만 제시해 연결곡선이 언제나 특정
방향으로 왜곡된다고 일반화하지 않는다. 이 fixture는 제품의 연속 계좌 실행기나 엔진 회계 검증을
대체하지 않으며, 왜 현행 연결 수익률을 연속 계좌 손익이라고 부를 수 없는지를 보여 주는 기대값이다.

HTTP 통합 테스트는 계산을 완료한 실제 API 응답에 평가 방식과 세 가지 한계가 전달되는지 확인한다.
frontend MSW 테스트는 backend 문장을 그대로 표시하는 경우와 옛 응답의 미확인 안내를 모두 검증하고
기존 샤프·유지율 표시가 유지되는지도 확인한다. 기존 실험 스토리 e2e는 실제 mock backend에서 반환한
안내가 실험 상세에 보이는지 검증한다.

## 다음 결정과 연속 평가 후속 계약

현재 결과는 선택 절차의 창 내부 수익률 비교로 사용한다. 실제 배치 성과가 필요한 시점에는 다음 항목을
사양으로 동결한 뒤 기존 결과와 구별되는 평가 방식으로 구현해야 한다.

1. **시작과 상태 이월:** 전체 평가 시작 전 하나의 초기자본을 정하고 현금·보유 수량·평가 가격·기업행동
   정산 상태를 창 경계로 이월한다. 초기자본→첫 snapshot 손익도 전체 계좌 수익률에 포함한다.
2. **경계 정책:** 다음 학습 창에서 고른 후보를 언제부터 적용하는지, 직전 보유를 유지·매도·교체하는지,
   미체결 주문의 취소/이월과 거래정지·상폐 보유 처리 시점을 먼저 정한다. 새 후보의 목표를 기존 계좌의
   실제 보유와 비교해 필요한 거래만 주문한다.
3. **비용과 정수 수량:** 기존 실행 커널의 주문·참여 한도·수수료·세금·슬리피지·정수 주·현금 규칙을
   재사용한다. 창 사이의 날짜 손익과 매매 비용을 빠뜨리거나 중복 집계하지 않는다.
4. **시점과 선택 기록:** 각 창의 선택은 해당 학습 종료 시점의 정보만 사용한다. 후보/기간/비용 가정을
   변경한 이력을 보존하고 이미 본 평가 구간을 미사용으로 되돌리지 않는다. 학습 라벨이 겹치는 경우의
   purge는 실제 라벨 정보창에 맞춰 별도로 설계한다.
5. **결과 신원:** `window_restart_returns`와 구분되는 명시적 평가 방식, 정책과 초기 상태·코드·입력
   snapshot 출처를 결과에 남긴다. 기존 trial key와 통계적 시도 수의 변경 필요성은 별도 검토하며 이
   slice에서 키나 판본을 선제 변경하지 않는다.
6. **수용 기준:** 동일 후보·비용 0 통제 사례, 후보 교체와 경계 거래 비용, 보유 유지·정수 수량 변화,
   비거래일 경계·미체결·상폐·분할을 포함하는 독립 fixture와 커널 parity로 연속 계좌를 검증한다.

비용·지연·미체결 스트레스, 소수 종목/기간 기여 분석, 일반 평가 열람 이력과 동결·봉인 개봉 절차는
S04의 나머지 작업이다. 이번 slice는 실데이터·봉인·계좌에 접근하지 않으며 미래 수익성을 판정하지 않는다.
