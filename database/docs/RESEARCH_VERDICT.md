## 1. 핵심 질문 — "플랫폼별 DB 분리 + 통합 DB 리빌드"

### 판정: **수정해서 채택**

분리 구조 자체는 맞다. 통합층의 저장 포맷만 틀렸다.

**맞는 부분 (근거)**

| 우리 결정 | 실무 대응물 | 출처 |
|---|---|---|
| 소스별 원장 분리, 수집기와 1:1 | dbt staging: 소스 시스템별 폴더 + `stg_<source>__entity` 네이밍, sources.yml도 소스별 | docs.getdbt.com/best-practices/how-we-structure/2-staging (1차, 공식) |
| 소스 raw → 별도 통합 스키마 | Fivetran: 커넥터별 raw 스키마 전달 → 변환 스키마를 사용자에게 노출 | fivetran.com/docs/core-concepts (1차, 공식) |
| 파일 분리로 쓰기 락 회피 | 상용 제품이 "메인 DB + 소스별 수천 첨부 파일"로 쓰기 동시성 개선 | sqlite.org/forum (실무자 증언) — 우리 실측 3.37→2.09 콜/s(38%↓)와 동일 동기 |
| 뷰가 아니라 물리 리빌드 | SQLite가 ATTACH 대상 참조 영구 VIEW를 거부 | **직접 재현 확인** (부록 A-3) |

**"5개 소스 · 2인인데 레이어 나누는 게 과설계 아닌가" 반론은 기각한다.** medallion 오버킬 비판(towardsdatascience.com, dataengineeringweekly.com)이 겨냥한 대상은 명시적으로 *단일 소스* 소규모 팀이다. 우리는 KRX/키움/KIS/DART/WiseIndex 5개 이종 벤더이고, 이미 "같은 날 같은 종목 종가가 소스별로 다르다"를 겪었다. 이 비판의 사정권 밖이다.

**틀린 부분: 통합층을 SQLite 물리 테이블로 만드는 것**

리빌드 비용이 걱정되어 증분/뷰를 고민했다면 그 걱정은 근거가 없다. 실측했다.

| 리빌드 방식 (11,439,470행 · 3소스 조인 · 전량) | 소요 | 산출물 크기 |
|---|---|---|
| SQLite ATTACH 3개 → `CREATE TABLE AS SELECT` | 20.2s | 1.46GB |
| ↑ + UNIQUE 인덱스 | +5.0s | |
| DuckDB: 소스 parquet 3개 → 통합 parquet | **3.8s** | **0.36GB** |

전량 리빌드가 25초다. 증분 리빌드 로직을 짤 이유가 없다. 매일 밤 통째로 다시 만들어라. 그리고 같은 작업을 DuckDB로 하면 6.6배 빠르고 산출물은 4배 작다.

### 확정 구조

```
krx.db / kiwoom.db / kis.db / dart.db / wics.db   ← 원장. SQLite 유지. append + UPSERT + 정정 UPDATE
ref.db  ← 코드표. SQLite 유지 (작고, 조인 상대)
ops.db  ← 수집로그·검산결과·해시. SQLite 유지 (append 위주, 트랜잭션 필요)
────────────────────────────────────────────────
equity/*.parquet  ← 통합층. 매일 전량 리빌드. 백테스트는 이것만 읽는다
```

원래 안에서 바뀌는 것은 **`equity.db` → `equity/*.parquet`** 한 줄뿐이다.

## 2. 저장 기술 판정 — SQLite냐 Parquet+DuckDB냐

### 판정: **양쪽 다. 계층별로 다르게.**

"둘 중 하나"가 애초에 잘못된 질문이다. 우리 워크로드는 성격이 정반대인 두 개다.

| 워크로드 | 실측 | 승자 |
|---|---|---|
| 매일 append (2,763행) | SQLite 0.51s / Parquet 새 파일 0.03s | 무승부 (둘 다 무시 가능) |
| **과거 1일 정정 UPDATE** | **SQLite 0.006s** / Parquet 연 파티션 전체 재작성 0.27s | **SQLite** |
| 전체스캔 집계 A (일자별 core 평균) | SQLite 6.94s / **DuckDB+pq 0.03s** | **DuckDB 221배** |
| 전체스캔 집계 B (섹터×월 시총가중) | SQLite 6.66s / **DuckDB+pq 0.12s** | **DuckDB 57배** |
| 윈도우함수 (전종목 20일 모멘텀) | SQLite 21.59s / **DuckDB+pq 1.87s** | **DuckDB 12배** |
| 단일종목 전기간 (인덱스 히트) | SQLite 0.004s / DuckDB 0.013s | SQLite (실무상 무의미) |
| 특정일 단면 (인덱스 히트) | SQLite 0.003s / DuckDB 0.011s | SQLite (실무상 무의미) |
| 저장 크기 (실데이터 1년 672,910행) | SQLite 138MB / **Parquet(zstd) 23MB** | **Parquet 5.9배** |

**결론:**

- **원장(수집 계층)은 SQLite다.** Parquet은 행 단위 UPDATE가 원리적으로 불가능하다(파일/파티션 전체 재작성). 우리 핵심 요구사항인 정정(restatement)·UPSERT·트랜잭션·FK·유니크 제약이 전부 SQLite 쪽에 있다. 여기서 갈아탈 이유가 0이다.
- **통합/분석 계층은 Parquet + DuckDB다.** 팩터 계산은 전부 전체스캔이다. 12~221배 차이를 감수할 이유가 없다.
- **Iceberg/Delta Lake는 도입하지 않는다.** append-only 정정 이력이라는 목적은 같지만 Spark/Trino 전제이고 2인·수 GB에는 과설계다. 우리는 원장 SQLite가 그 역할을 이미 한다.
- **kdb+ / ClickHouse / QuestDB / ArcticDB는 검토 종료.** kdb+·ClickHouse는 조사에서 확인된 채택 주체가 HFT 데스크·Bloomberg급 조직뿐이다(arXiv 2301.12561, clickhouse.com/blog). ArcticDB는 BSL 라이선스라 프로덕션 유료 — 오픈소스가 아니다(docs.arcticdb.io/dev/history).

### 마이그레이션 비용과 시점

**시점: 지금 즉시.** 파일럿 1년(67만 행)만 적재된 현재가 최저 비용 지점이다. 16.6년 전량 적재 후에 옮기면 재적재 비용이 14배가 된다.

| 항목 | 비용 | 근거 |
|---|---|---|
| 수집기 코드 변경 | **0** | 원장은 SQLite 그대로 |
| 통합 리빌드 스크립트 | 신규 1개, ~30줄 | `duckdb.sql("COPY (SELECT ... FROM sqlite_scan/parquet JOIN ...) TO 'equity/panel.parquet'")` |
| 백테스트 읽기 경로 | `pd.read_sql` → `duckdb.read_parquet` | 쿼리 SQL 자체는 거의 호환 |
| 의존성 | `pip install duckdb` 1개 | 설치 확인 완료 (duckdb 1.5.5) |
| 위험 | 낮음 | 원장이 정본이므로 통합층은 언제든 재생성 가능. 실패 시 롤백 = SQLite 리빌드로 되돌리기 25초 |
| 총 공수 | **1~2일** | |

**중간 옵션도 실측해 뒀다:** DuckDB의 sqlite_scanner로 SQLite를 직접 읽으면 질의 A가 2.81s다(네이티브 SQLite 6.94s 대비 2.5배 개선, Parquet 0.03s 대비 94배 열세). 마이그레이션이 늦어지면 임시방편으로 쓸 수 있지만 최종형이 되면 안 된다.

| 항목 | 판정 | 근거 / 대안 |

| **CHECK 제약 428개** | **과잉. 축소하라** | 조사 5축 어디에서도 "스키마에 CHECK를 대량으로 박는다"는 실무 관행이 확인되지 않았다. 대응물은 dbt test류의 *적재 후 검증 쿼리*다. 게다가 SQLite는 CHECK를 ALTER로 수정할 수 없어 제약 하나 고칠 때마다 테이블 전체 재작성이다 — 16.6년 적재 후엔 스키마가 사실상 동결된다. **불변식(FK, UNIQUE, NOT NULL, 부호/범위)만 CHECK로 남기고, 나머지는 `ops.db`의 검산 결과 테이블로 빼라.** `ingest_log.csv`에 이미 `expected_min` 컬럼이 있으니 그 자리를 확장하면 된다. |
| **메타 15테이블** | **과잉. 5~6개로** | dbt의 대응물은 `sources.yml` 파일 하나다. 2인 프로젝트에서 메타 15개는 유지 비용이 산출물을 넘는다. |
| 원장 20 + 파생 4 | 유지 | 5개 벤더 × 시세/재무/수급/공매도/기업행위/섹터를 담으면 자연스러운 수다. 과하지 않다. |
| **조정계수를 패널의 영구 컬럼으로 저장**(`adj_factor_x`) | **재설계 권고 · 우선순위 높음** | Zipline은 기업행위를 원장(effective_date + ratio)으로만 저장하고 조정계수·수정주가는 **읽는 시점에 누적곱으로 파생**한다(github.com/quantopian/zipline, 코드 직접 확인). 우리는 이미 조정계수 정의 오류로 1,500:1 감자 종목에 `+29,948%`를 남겼다. 영구 컬럼으로 굳히면 정의 오류가 전 기간에 동결되고, 고칠 때마다 936만 행 재계산이다. `corp_actions_1y.csv`라는 원장이 이미 있으니 그것을 정본으로 삼고 `adj_factor_x`·`ret_1d_pct`는 통합층(Parquet) 리빌드 시 파생시켜라 — 25초면 전량 재생성된다. |
| 컬럼별 `available_at` 세분화 | **2개까지만 허용** | ALFRED·Qlib·Compustat 모두 행 단위 1개 timestamp만 쓴다(선례 없음). 다만 우리는 기준가 08:00 / 종가 15:30이 *실제로* 다르고, 파일럿은 이미 `available_at_pre`/`available_at` 2개로 잘 해결했다. **이 2개로 동결하고 3개 이상으로 늘리지 마라.** |
| 완전 bitemporal (valid·transaction 양쪽 구간) | **안 하는 게 맞다 (현행 유지)** | 프로덕션 금융 PIT 시스템(ALFRED, Qlib, Compustat) 중 채택 사례가 조사에서 확인되지 않았다. XTDB 등 범용 DB 제품 소개 자료 수준. `asof_date + available_at + vintage_seq` 3요소가 실무 표준과 정합한다. |
| raw JSON 해시 기반 CAS 보관 | **단순화 권고** | "정규화 전 raw 보관"은 표준이나, 해시 CAS를 금융 시세에 쓴다는 사례는 확인 실패. `raw/<src>/<yyyymm>/<date>.jsonl.gz` + `ops.db`에 sha256 한 컬럼이면 감사 목적은 충족한다. |

## 4. 실무 표준인데 **우리가 안 하고 있는 것** — 우선순위 순

### P0 — 지금 안 하면 데이터를 다시 모아야 하는 것

| # | 항목 | 왜 P0인가 |
|---|---|---|
| **1** | **DART 정정보고서 이력을 실제로 수집** | DART는 정정보고서를 **별도 rcept_no의 별개 문서**로 등록하고, 검색 UI에서 "최종보고서"를 체크하면 정정 전 버전이 숨는다. **즉 DART는 vintage를 관리해주지 않는다 — 수집기가 원본+정정본을 전부 긁어 append해야 한다.** 우리 `financials_294.csv`에는 `value_is_pit(값의PIT여부 0=오늘확정치 소급)` 컬럼이 있다. **0이면 현재 파일럿은 PIT가 아니다.** 재무 정정의 82%가 결산기말+90일 이후 발생한다는 우리 실측을 감안하면, 지금 이 상태로 16.6년을 채우면 PIT 백테스트가 원리적으로 불가능해진다. 스키마에 `vintage_seq`가 있는 것과 데이터를 실제로 그렇게 모으는 것은 다른 문제다. |
| **2** | **look-ahead를 조회 API가 물리적으로 차단** | 우리는 `available_at`을 *스키마에* 두었을 뿐, 전략 코드가 원장을 직접 읽으면 아무것도 막지 못한다. QuantConnect/LEAN은 엔진이 시간을 스트리밍으로 전진시키며 `OnData(slice)`로만 데이터를 노출해 **아키텍처 수준에서** 미래 접근을 차단한다(개발자 재량이 아니다). 전직 BNP/BofA/Citadel 인프라 엔지니어 Susan Potter도 같은 권고(susanpotter.net/quant/backtest-bias-taxonomy). 최신 논문(arXiv 2607.04958)은 정적 검증 도구가 아직 연구 초기임을 지적하므로 **스키마 제약·린트에 기대지 말고 리더 함수 하나로 강제하라.** → `read_panel(as_of: datetime)` 단 하나만 공개하고, 그 함수가 `available_at <= as_of` 필터를 반드시 건다. 원장 직접 접근은 금지 규칙으로. |
| **3** | **decision time ≠ execution time 프로토콜 강제** | arXiv 2605.23959(2026-05)가 정보시점·체결시점 혼동만으로 Sharpe가 **5~26포인트** 부풀려짐을 실증. 우리 `backtest_smoke.csv`에 이미 sharpe 컬럼이 있는데 이 프로토콜이 강제되는지 불명이다. → **t일 종가 정보 → t+1일 시가 체결**을 엔진에 하드코딩하고 전략별 override를 막아라. (단, 이 근거는 2026-05 논문 1건이고 2차 교차검증 소스가 없다 — 신뢰도 중간. 다만 비용이 거의 0인 조치라 채택 권고.) |

### P1 — 나중에 해도 되지만 하는 게 맞는 것

| # | 항목 | 내용 |
|---|---|---|
| 4 | **vintage 종료 필드** | ALFRED는 관측치마다 `realtime_start`/`realtime_end`를 두고, 정정 시 직전 레코드의 `realtime_end`만 닫고 새 행을 append한다. 우리는 "다음 seq가 없으면 최신"이라는 암묵 판정이라 as-of 조회가 서브쿼리를 요구한다. `available_at_end` 한 컬럼 추가로 조회가 단순해진다 — append-only 원칙도 안 깨진다(최신 값 자체는 불변, end만 갱신). 실무에서 필수로 요구되는지는 미확인. |
| 5 | **membership spell (entry/exit 구간) 유니버스** | 실무에 daily-flag와 spell 두 갈래가 공존하고(Norgate/Concretum 워크플로가 후자), 어느 쪽이 낫다는 비교 근거는 못 찾았다. 우리 `universe_daily` 3층 플래그가 **틀린 건 아니다.** 다만 daily-flag는 4,073일×2,300종목을 매일 재판정하는 반면 spell은 종목당 수 행이다. **파생 테이블로 spell을 추가**하는 저비용 절충 권고(리빌드에 몇 초). |
| 6 | **PR/TR(가격수익률/총수익률) 분리 저장** | CRSP가 "highly accurate total return calculations"를 판매 포인트로 명시(벤더 주장, 구체 스키마 미확인). 배당 재투자를 반영 안 하면 16.6년 장기 백테스트가 구조적으로 왜곡된다. 현재 파일럿 패널에 배당 관련 컬럼이 없다 — **확인 필요.** |
| 7 | **검산 결과의 영속화** | `ingest_log.csv`(src/status/rows/expected_min/return_msg/elapsed_ms)는 이미 좋다. 여기에 `flow_resid_mkrw(12주체합계 검산 ±6)` 같은 assertion 결과를 행으로 남겨라. CHECK 428개에서 빼낸 것들의 착지점이다. |

### 근거 확보 실패 (조사로 답이 안 나온 것 — 추측으로 채우지 않음)

- 원장팀 vs 엔진팀 조직 경계 설계: 실무 회고 확보 실패. 채용공고 수준 설명만. **2인 규모에서 쟁점이 아닐 것이라는 판단조차 근거가 없다.**
- 우리와 같은 규모(10GB·2인)에서 SQLite→Parquet 전환을 겪은 1차 회고: 발견 실패. **그래서 이 문서의 저장 판정은 남의 사례가 아니라 우리 데이터 실측에 근거한다.**
- "플랫폼별 DB 분리 + ATTACH 통합 리빌드"의 국내 개인/2인 선례: 발견 실패.

## 부록 A — 실측 조건과 원자료

이 문서의 모든 수치는 **우리 파일럿 데이터**로 직접 측정했다. 웹 자료의 벤치마크(1.1B rows 택시 데이터 등)는 규모가 100배 이상 달라 판정에 쓰지 않았다.

**A-1. 데이터**
- 원본: `/Users/claudeoscarmonet/Desktop/Quant_study/workspace/dongmin/data/pilot/panel_full_1y.csv` — 672,910행 × 33컬럼, CSV 160MB (실데이터, 1년)
- 16.6년 시뮬레이션: 위를 연도 오프셋으로 17배 복제 → **11,439,470행** (목표 936만 행보다 22% 큰 보수적 규모)
- 하드웨어: 로컬 macOS, DuckDB threads=8, SQLite 3.39.4 / DuckDB 1.5.5 / pyarrow 24.0.0

**A-2. 압축비 주의** — 17배 복제 데이터는 값이 반복되어 zstd 사전 압축에 유리하다. 그래서 **복제하지 않은 실데이터 1년으로 따로 측정**했다: SQLite(인덱스 2개 포함, VACUUM 후) 138MB vs Parquet(zstd-3) 23MB = **5.9배**. 복제 데이터의 6.7배와 큰 차이 없으므로 위 표의 압축비는 신뢰 가능하다.

**A-3. SQLite ATTACH-VIEW 제약 재현 결과** (우리 기존 실측을 확인 + 새 사실 1건)
```
CREATE VIEW v AS SELECT * FROM sa.t   → 실패: "view v cannot reference objects in database sa"
CREATE TEMP VIEW tv AS SELECT * FROM sa.t → 성공 (11,439,470행 조회됨)
```
기존 판단대로 **영구 VIEW는 불가**하다. 다만 **TEMP VIEW는 동작한다** — 조사 자료엔 없던 사실이다. 접속마다 재생성해야 하고 인덱스가 없어 백테스트 읽기 경로로는 부적합하지만, 임시 탐색·검산 쿼리에는 쓸 수 있다.

**A-4. 벤치마크 스크립트** (재현용)
