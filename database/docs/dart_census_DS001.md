## 0. 목록 확보 방법과 결과

`https://opendart.fss.or.kr/guide/main.do?apiGrpCd=DS001` 은 **정적 렌더**다. `curl` + `grep -oE "apiId=[0-9]+"` 로
전체 목록이 그대로 나온다(동적 로딩 아님). WebFetch 와 curl 두 경로가 **동일한 4건**을 반환했다.

```

```

교차 확인용으로 다른 그룹도 같은 방법으로 셌다(개수만, 프로브 안 함 — 이번 과제 범위 밖):

| 그룹 | 명칭 | apiId 개수 |
|---|---|---:|
| **DS001** | **공시정보** | **4** |
| DS002 | 정기보고서 주요정보 | 30 (2026001·2026002 = 2026년 신설 2건 포함) |
| DS003 | 정기보고서 재무정보 | 7 |

### 1.1 `list.json` — 실측 응답 필드 (9개)

```
corp_code corp_name stock_code corp_cls report_nm rcept_no flr_nm rcept_dt rm
```
메타: `status message page_no page_count total_count total_page`

| 필드 | 의미 | 실측 비고 |
|---|---|---|
| `corp_code` | 고유번호 8자리 | |
| `corp_name` | 종목명(상장) 또는 법인명(기타) | `company.json` 의 `corp_name` 과 **다르다** — list 는 `삼성전자`, company 는 `삼성전자(주)` |
| `stock_code` | 종목코드 6자리 | **비상장은 공란.** 2026-08-14 전체 4,600건 중 100건 샘플에서 45건이 공란 |
| `corp_cls` | Y(유가)/K(코스닥)/N(코넥스)/E(기타) | 하루 표본 분포 E:46 K:43 Y:11 |
| `report_nm` | 공시구분+보고서명. `[기재정정]`·`[첨부정정]`·`[첨부추가]`·`[정정명령부과]` 등 접두 | 실측: `[기재정정]임원ㆍ주요주주특정증권등소유상황보고서`. 뒤에 **공백 패딩**이 붙는 경우 있음(`중대재해발생(종속회사의주요경영사항)              `) → **저장 시 rstrip 필수** |
| `rcept_no` | 접수번호 14자리 = `YYYYMMDD` + 순번 6자리 | 뷰어 URL: `https://dart.fss.or.kr/dsaf001/main.do?rcpNo=<rcept_no>` |
| `flr_nm` | 제출인명 | 회사가 아닐 수 있다(실측 `홍창표` — 개인) |
| `rcept_dt` | 접수일자 YYYYMMDD | |
| `rm` | **비고. 단일 코드가 아니라 문자 조합** | 실측 분포(삼성전자 2025 100건): `''`×82, `공`×11, `유`×5, `정`×1, **`공정`×1**. `공정`은 `공`+`정` 연결 |

**`rm` 코드표**(가이드 원문):
`유`=유가증권시장본부 소관 · `코`=코스닥시장본부 · `채`=채권상장법인 · `넥`=코넥스 · `공`=공정거래위원회 ·
`연`=연결부분 포함 · **`정`=제출 후 정정신고가 있음** · **`철`=철회(간주)됨**

> **`rm` 은 enum 이 아니다.** `rm='정'` 으로 등호 비교하면 `공정` 이 누락된다. **`instr(rm,'정')` 또는 문자 분해로 파싱해야 한다.**

**소급성 실측**
- `corp_code='00126380'`, `bgn_de='19990101'`, `end_de='20260824'`, `pblntf_detail_ty='A001'` → `status=000`, `total_count=30`.
  가장 오래된 건 `19990403000009` 사업보고서(1998.12), 최신 `20260310002820` 사업보고서(2025.12).
  → **corp_code 를 주면 27년 창도 한 콜에 통과한다. 3개월 제한은 corp_code 를 생략했을 때만 걸린다.**
- 삼성전자 2025년 1년 전건: `total_count=827`, `total_page=9`.

**규모 실측 (백필 예산용)**

| 질의 | total_count | total_page(@100) |
|---|---:|---:|
| 전체(법인구분 무필터) 2026-08-14 하루 | **4,600** | 46 |
| `corp_cls='Y'` 같은 날 | 1,125 | 12 |
| `corp_cls='K'` 같은 날 | 1,865 | 19 |
| 현대차(00164742) 2016-01-01~2026-08-24 | 2,911 | 30 |
| 삼성중공업(00126478) 같은 기간 | 1,400 | 14 |

→ 상장(Y+K) = 2,990 / 4,600 = **전체 공시의 65%만이 상장법인 공시**다. 나머지 35%는 자산운용사 투자설명서 등 기타법인.

## 2. 문서에 없는 엔드포인트 프로브 (실측)

**대조군 확립**: 존재하지 않는 `.json` 경로는 HTTP 200 + `{"status":"101","message":"잘못된 URL입니다. 확인해주세요(/api/<name>)"}` 를 준다.
존재하지 않는 `.xml` 경로는 HTTP 200 + **HTML 오류 페이지(4,694 B)** 를 준다. 둘 다 명확한 판별 신호다.

## 3. 우리 계획에 없는데 받아야 할 것

기준 문서: `docs/DART_DESIGN.md`(§1.4 `dart_disclosure`, §5 P4 스윕), `docs/COLLECT_PLAN.md`.

### D1. `dart_disclosure` 에 `rm` 과 `corp_cls` 가 없다 — 최우선, 추가 콜 0

- **상황**: `DART_DESIGN.md:137-147` 의 `dart_disclosure` 스키마는
  `rcept_no, corp_code, corp_name, stock_code, report_nm, rcept_dt, flr_nm, window, collected_at` 9컬럼이다.
  `list.json` 이 실제로 주는 9개 응답 필드 중 **`corp_cls` 와 `rm` 두 개가 버려진다.**
- **인풋**: P4 공시 스윕(35,454콜) 전 구간. 매 응답 행마다 `rm`·`corp_cls` 가 담겨 오는데 INSERT 대상 컬럼이 없다.
- **에러 위치**: `docs/DART_DESIGN.md:137-147` — `CREATE TABLE dart_disclosure` 컬럼 정의.
- **위험성**:
  1. **`rm='정'`(제출 후 정정신고 있음) 을 잃는다.** 이건 "이 공시의 내용은 나중에 뒤집혔다"는 DART 가 주는 유일한 플래그다.
     이벤트 스터디에서 정정 전 원본을 유효 이벤트로 취급하면 **look-ahead 가 아니라 stale-fact bias** 가 생긴다.
     `rm='철'`(철회)은 더 나쁘다 — 일어나지 않은 이벤트를 일어난 것으로 센다.
  2. `corp_cls` 없이는 `stock_code` 공란(전체의 45%)이 **"비상장이라 없음"인지 "수집 실패"인지 구분이 안 된다.**
  3. 두 컬럼 다 **재수집 외에는 복구 경로가 없다.** 나중에 넣으려면 P4 전량 35,454콜(약 1.8일 쿼터)을 다시 태운다.
- **조치**: 스키마에 `corp_cls TEXT`, `rm TEXT` 2컬럼 추가. **P4 착수 전에.** 추가 API 콜 0.
- **파싱 주의**: `rm` 은 문자 조합(`공정` 실측). `rm='정'` 등호 비교 금지 → `instr(rm,'정')`.
- 부수: `report_nm` 우측 공백 패딩 실측 → 저장 시 `rstrip()`.

### D2. `document.xml` — 계획에 아예 없다. 정기보고서 원문 + 감사보고서(주석 포함)

- **현황**: `DART_DESIGN.md` 전문에 `document.xml` 이 **0회** 등장한다. P0~P5 어느 단계에도 없다.
- **무엇을 놓치고 있나**: 사업보고서 1건의 ZIP 안에 **본문 + 감사보고서 + 연결감사보고서**가 통째로 들어 있다(실측 3엔트리).
  감사보고서 엔트리에는 **재무제표 주석 전문**과 **내부회계관리제도 감사의견**, **외부감사 실시내용**이 있다.
  `fnlttSinglAcntAll.json` 은 계정 139개 숫자만 준다 — **주석·감사의견·계속기업 불확실성 문단은 document.xml 이 유일한 API 경로다.**
  본문 쪽에는 `TOT_STK`(주식총수), `OWN_SHR`(자기주식), `CONT_CHG`(최대주주 변동), `MNG_IMP_CHG`(경영권 변동),
  `SM_VEN_CMP`(중소·벤처기업 해당), `SPC_CRT`(SPC) 같은 시맨틱 `ACLASS` 가 붙어 있다.
- **팩터 용도**: 감사의견 변형(적정/한정/의견거절)·계속기업 불확실성 문단 = 강력한 **부실 예측 / 상폐 위험 팩터**.
  주석의 우발채무·소송·특수관계자 거래 = 텍스트 팩터.
- **비용**: **1콜 = 공시 1건.** P4 를 먼저 돌리면 `dart_disclosure` 에서 `rcept_no` 를 그냥 뽑아 쓰므로 조회 오버헤드 0.
  범위별 예상:

  | 범위 | 예상 콜 | 예상 용량 | 근거 |
  |---|---:|---:|---|
  | 사업보고서(A001)만, 상장사 ~2,800 × FY2015~2025(11년) | **~30,800** | 15~25 GB | 삼성전자 사업보고서 30건/27년 실측, 780 KB/건 실측 |
  | 사업보고서 + 반기(A002) + 분기(A003) 동일 범위 | ~123,000 | 40~60 GB | 연 4건 |
  | 사업보고서, 최근 3년(FY2023~2025)만 파일럿 | **~8,400** | 4~7 GB | 착수 권장 |

- **선행 확인 필요(미확인)**:
  - 정기보고서가 아닌 공시(주요사항보고서 등)의 첨부 개수 분포 — 실측 표본 3건뿐.
  - ZIP 인코딩: 본문 XML 은 `encoding="utf-8"` 선언(실측 3건 모두). 구세대 문서에 EUC-KR 이 섞이는지 **미확인**.
  - `020` 쿼터 소모가 바이트 수와 무관하게 1콜인지 — **미확인**(문서상 "요청 건수" 기준이므로 1콜로 가정).
- **우선순위: P2(높음).** 단 D1 다음. 파일럿 8,400콜부터.

### D3. P4 공시 스윕을 **날짜창 → 종목별**로 바꾸면 ~1만 콜 절감

- **현행 계획**: `DART_DESIGN.md:349` P4 = "공시 스윕 2010-01~2026-08, Σ분기 total_count/100 + 창 67" = **35,454콜**.
  `corp_code` 없는 날짜창 방식이라 **3개월 제한**을 받고, 미확인 항목 (e)「3개월 창의 정확한 경계」에 2콜을 더 쓰기로 돼 있다.
- **실측 근거**: `corp_code` 를 주면 창 제한이 사라진다(1999-01-01~2026-08-24 한 콜 통과, 실측).
  그리고 날짜창 방식은 **전체 공시의 35%인 기타법인 공시를 전부 긁어온다**(2026-08-14 실측: 4,600 중 상장 2,990).
- **재추정**:
  - 날짜창: 16.7년 × 상장·비상장 전건. 기존 추정 35,454콜.
  - 종목별: 모수 3,341 corp_code × ceil(건수/100). 실측 대형주 현대차 30페이지·삼성중공업 14페이지(10.6년).
    전체 공시의 65%가 상장분이므로 상장 총건수 ≈ 3.3M × 0.65 ≈ 2.15M → 21,500페이지 + 종목당 잔여 부분페이지 1개(3,341)
    ≈ **약 25,000콜**.
  - **절감 약 10,000콜(≈0.5일 쿼터)**, 게다가 3개월 경계 확인(2콜)과 창 재개 로직 자체가 불필요해진다.
- **트레이드오프 / 미확인**:
  - 종목별은 **모수(3,341)에 없는 법인의 공시를 놓친다.** 우리가 기타법인 공시를 쓸 계획이 없다면 손실 아님 —
    **이건 계획 확인이 필요한 지점이다.**
  - `page_no` 가 100 을 넘어도 정상 동작하는지 **미확인**(현대차 30페이지까지만 필요하므로 실무상 무해).
  - 재개(resume) 단위가 창→종목으로 바뀌므로 `dart_disclosure.window` 컬럼 의미가 바뀐다(`window` → `corp_code` 스윕 마커).
- **우선순위: P3(중간).** P4 착수 전에 결정해야 한다. 착수 후에는 못 바꾼다.

## 4. 구현 시 반드시 반영할 실측 사항

1. **`document.xml` 성공/실패 판별은 확장자로 못 한다.** 성공=ZIP(`PK\x03\x04`), 실패=XML(`<result><status>013</status>`).
   `api.dart()` 는 `.xml` 경로에서 `r.content`(bytes)를 그대로 돌려주므로 **호출부가 `raw[:2] == b'PK'` 로 스니핑해야 한다.**
   안 하면 오류 XML 200 바이트를 정상 문서로 저장한다(silent corrupt).
2. 없는 접수번호는 `014`(파일없음)가 아니라 **`013`** 이 온다(실측). 오류 분기 시 주의.
3. `rm` 은 문자 조합. `rm='정'` 등호 비교 금지.
4. `report_nm` 우측 공백 패딩 존재. `rstrip()` 필수.
5. `list.json` 의 `corp_name`(`삼성전자`) ≠ `company.json` 의 `corp_name`(`삼성전자(주)`). 이름으로 조인 금지, `corp_code` 로만.
6. `document.xml` 은 1999년 문서에서 **스키마 세대가 다르다**(dart4.xsd 없음, `<PERIOD>` 존재). 파서 분기 필요.
7. 첨부 파일명 규칙 `<rcept_no>_NNNNN.xml`. ZIP 엔트리 순서에 의존하지 말고 `<DOCUMENT-NAME>` 으로 식별할 것.
