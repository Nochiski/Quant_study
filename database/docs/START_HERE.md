## 5-2. 수집 쪽 확인 필요 — **v3 미러가 의도적으로 중단됐고, 그 전제가 틀렸다** (09-07 발견 · 09-08 정정)

처음엔 「크론이 없다」로 적었는데 틀렸다. `scripts/daily_wise.sh` 주석에 이유가 있다 —
*"③ v3 미러 sync_v3 는 2026-09-02 중단 — 직접 수집이 같은 값을 커버. 과거분 ~09-02 는 동결 보관"*.

**그 전제가 틀렸다.** WISE 직접 수집(`stg_consensus_monthly`, cF5001/cF5002)의 metric 어휘는
**`eps | revenue` 뿐**이라 영업이익·순이익이 없다. 즉 G05(영업이익 리비전)·G06(순이익 리비전)의
유일한 재료가 **2026-08-31 에 동결**됐다. 「v3 가 매일 쌓이니 2027년 봄이면 1년치」는 더 이상
참이 아니다.

| 축 | 마지막 |
|---|---|
| 사본 `wisereport.db/v3_consensus_revision_daily` | **08-31** (동결) |
| **원본** `kael-system-v3/quant.db/consensus_revision_daily` | **09-04** (계속 쌓임) |

원본이 살아 있으니 미러를 재개하면 소급 복구된다. **운영 변경이라 사용자 승인 사항.**

### 덤으로 나온 것 — 영업이익·순이익 컨센서스가 WISE 에도 있는데 안 읽고 있다

- `stg_consensus_annual`(c1050001_data)에 `period_kind='E'` 4,836행 · 810종목 · `op`·`ni` 각
  3,448 / 3,403행 채워져 있다.
- `stg_consensus_matrix` 는 사실상 **리비전 패널**이다 — (종목 × target_period × 계정 9 ×
  lookback 5), 계정에 영업이익·순이익·매출액·EPS·투자의견, lookback `current·1w·1m·3m·1y`
  (799종목). 두 관측점을 빼지 않아도 1개월 리비전이 수집일마다 그대로 실려 온다.

→ 이 둘을 `consensus_daily` 에 잇는 슬라이스가 G05~G08 을 「2027년까지 대기」에서 빼낼 수 있는
값싼 경로다. 새 원천 축·PIT 규약·게이트가 필요해 **별도 설계·승인 사안**.

WISE 쪽은 정상이다 — 매일 06:00 KST, 8일 연속 성공(09-01~09-08), 커버 804/2,564 안정.
문서의 「WISE 수집 이틀뿐」은 낡았다 — stage/equity 재빌드만 하면 measured 축이 8일이고 매일 는다.

## 7. 작업 규칙 (짧게)

- **슬라이스 = 테이블 1~3개 + 브랜치 하나 + 검토 요청 하나.** 게이트 술어 ID 가 없으면 착수 금지.
- **재현 테스트 먼저.** 절단본(`database/tests/fixtures/stage_slice`)에 사례가 없으면
  합성 러너를 쓴다(`test_equity_s05_event.py::run_event_sql` · `s06_adj.py::run_adj_sql` 참고).
- **판본을 올리지 않고 산출을 바꾸면 EG5a 가 FAIL 하고 새 판이 폐기된다.** 올린 뒤 **두 번** 지어야
  재현성이 확인된다.
- **게이트가 실패하면 새 판을 버리고 기존 판이 남는다** — 서버 재빌드가 위험하지 않은 이유다.
- 상수는 코드가 아니라 `baseline.json`. 첫 빌드는 측정만 하고 사람 승인 뒤 2회차부터 적용.
- **판단이 필요하면 팩트를 더 실어라.** 라벨을 붙이고 근거를 basis 컬럼에 적고 임계는 소비자에게
  넘긴다. 이름에 해석을 얹지 않는다.
