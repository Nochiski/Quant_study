백테스트 엔진을 만들기 위한 학습 노트

이 문서는 Zipline 사용법 정리가 아니라, 직접 이벤트 드리븐 백테스트 엔진을 만들기 전에 필요한 전략 I/O 계약, 엔진 책임 경계, Decision/Action 프로토콜, Capability 협상, Rust 포팅 경로를 고정하기 위한 설계 아티팩트다.

관찰용 웹앱 열기 FastAPI 코드 보기

현재 결론

전략은 Python 전략 연구와 실험 속도가 중요하므로 Python으로 유지한다.
엔진 코어는 Rust 후보 이벤트 루프, 체결, 포트폴리오 회계는 타입과 성능 이점이 있다.
출력은 StrategyDecision 목표 비중, 긴급 청산, 주문, 취소·정정을 서로 다른 Action 타입으로 표현한다.
스키마와 구현 상태는 분리 프로토콜 자리는 먼저 정의하고 미구현 기능은 Capability에서 명시적으로 거절한다.

읽는 기준

전체 프로토콜 책임 경계 전략 작성 계약 Requirements 선언 Decision / Action 전략별 Context 이벤트 모델 긴급 청산 흐름 포트폴리오 회계 Python/Rust 경계 Capability 상태

이 실험의 진짜 목적

지금 만든 Zipline/PyKRX/FastAPI/Astro 코드는 최종 산출물이 아니다. 목적은 “백테스트 엔진을 직접 작성할 때 무엇을 엔진이 알고 있어야 하고, 무엇을 전략에게 맡겨야 하는가”를 눈으로 확인하는 것이다.

배우려는 것

전략 함수의 입력, 출력, 상태 조회, 주문 변환, 체결, 포트폴리오 회계.

임시로 쓰는 것

Zipline은 기준 동작 관찰용, PyKRX는 한국 주식 데이터 수집용.

구현과 구분할 것

전체 스키마는 먼저 정의하되 실제 엔진 구현 여부는 Capability로 따로 표시한다.

설계 기준은 하나다. 전략은 “판단”만 하고, 엔진은 “시장 시뮬레이션과 회계”를 책임진다.

핵심 설계 결정

출력은 Decision + Action

목표 비중만 강제하지 않는다. 목표, 긴급 청산, 주문, 취소·정정을 합 타입으로 구분한다.

Context는 조회 전용

전략이 포트폴리오 상태를 직접 바꾸면 재현성, 테스트, 결과 대조가 어려워진다.

이벤트는 append-only로 기록

나중에 결과가 이상할 때 event, decision, action, order, fill, snapshot 순서로 추적한다.

스키마와 구현 상태 분리

전체 Action 자리는 미리 정의하고 미구현 타입은 Capability 검증에서 실행 전에 거절한다.

전략 I/O 계약

전략 종류가 모멘텀이든 골든크로스든 리밸런싱이든, 엔진이 호출하는 함수 모양은 동일해야 한다. 전략별 차이는 어떤 Event를 구독하고 Context를 어떻게 조회하며, 어떤 Action을 Decision에 담아 반환하는지에만 둔다.

Requirements필요한 데이터·이벤트·기능을 실행 전에 선언
StrategyEvent시장·타이머·체결·주문 상태가 호출을 시작
StrategyContext현재까지 확정된 데이터와 상태를 조회
StrategyDecision한 번의 판단과 이유를 불변 객체로 반환
StrategyAction목표·청산·주문 등 실행 의미를 합 타입으로 구분
Capability엔진이 처리할 수 없는 요구를 루프 전에 거절

    def requirements(self) -> StrategyRequirements:
        ...

    # 모든 전략은 같은 입력과 출력 타입을 사용한다.
    def on_event(
        self,
        ctx: StrategyContext,

함수 시그니처는 모든 전략이 같고, requirements()의 반환값만 전략마다 다르다. 엔진은 이 선언을 읽어 필요한 가격 창, 이벤트 구독, Action 지원 여부를 미리 검증한다.

Config, requirements(), on_event(), 필요한 경우에만 typed StrategyState.

엔진이 공통으로 제공

StrategyRequirements 스키마, EngineStrategyContext, DataFeed, 주문·체결·포트폴리오 처리.

Requirements: 전략이 먼저 요구사항을 선언한다

StrategyContext가 Requirements를 소유하는 구조가 아니다. 전략이 공통 StrategyRequirements 타입의 값을 반환하고, 엔진은 그 선언을 검증한 뒤 필요한 데이터만 담은 Context를 생성한다.

전략이 만든다

requirements()에서 필요한 종목, lookback, 호출 이벤트와 기능을 값으로 반환한다.

엔진이 검증한다

잘못된 lookback, 없는 종목, 미구현 Action과 공매도 요구를 데이터 로딩 전에 확인한다.

Context Factory가 사용한다

검증된 선언의 범위 안에서만 PriceWindow와 포트폴리오 조회 API를 노출한다.

전략 작성자가 새 Requirements 클래스를 직접 만드는 것이 아니다. 엔진이 제공하는 공통 스키마에 자신의 요구 값을 채우고, 전략 로직과 필요한 typed State만 구현한다.

StrategyDecision과 Action 합 타입

최상위 출력 타입은 하나로 유지하고, 실제 의사결정 의미는 서로 다른 Action 타입으로 나눈다. 새 기능은 기존 타입에 nullable 필드를 붙이지 않고 새로운 Action variant로 추가한다. 

class ActionKind(Enum):
    NO_ACTION = "no_action"
    SET_PORTFOLIO_TARGET = "set_portfolio_target"
    SET_POSITION_TARGET = "set_position_target"
    ADJUST_POSITION = "adjust_position"
    LIQUIDATE_POSITION = "liquidate_position"
    SUBMIT_ORDER = "submit_order"
    CANCEL_ORDER = "cancel_order"
    REPLACE_ORDER = "replace_order"
    BASKET = "basket"

StrategyAction = (
    NoAction
    | SetPortfolioTarget
    | SetPositionTarget
    | AdjustPosition
    | LiquidatePosition
    | SubmitOrder
    | CancelOrder
    | ReplaceOrder
    | BasketAction
)

@dataclass(frozen=True)
class StrategyDecision:
    # 스키마 버전은 Python/Rust 직렬화 계약을 식별한다.
    schema_version: int
    as_of: datetime
    actions: tuple[StrategyAction, ...]
    reason: str | None = None

    @classmethod
    def no_action(
        cls,
        as_of: datetime,
        reason: str | None = None,
    ) -> "StrategyDecision":
        return cls(
            schema_version=1,
            as_of=as_of,
            actions=(NoAction(reason),),
            reason=reason,
        )
같은 전략도 평상시에는 SetPortfolioTarget, 급락 시에는 LiquidatePosition, 체결 반응형 상황에서는 CancelOrder나 ReplaceOrder를 반환할 수 있다.

실제 코드와 테스트가 있어 Decision을 실행할 수 있다.

NOT_IMPLEMENTED

스키마 의미는 확정됐지만 현재 처리 코드가 없다.

UNSUPPORTED

현재 데이터 해상도나 체결 모델로 의미 있게 시뮬레이션할 수 없다.

왜 전략이 포트폴리오를 직접 바꾸면 안 되는가

전략은 매매 판단만 내리고, 실제 상태 변경은 체결된 FillEvent를 받은 포트폴리오가 담당한다. 주문은 거절되거나 일부만 체결될 수 있기 때문에 전략의 판단을 곧바로 보유 수량으로 확정하면 실제 체결 과정이 사라진다.

잘못된 예: 전략이 매수를 확정함

def on_event(self, ctx, event):
    if not isinstance(event, MarketSnapshot):
        return StrategyDecision.no_action(ctx.now)

    bar = event.bar(self.instrument)
    if bar.close > 70_000:
        # 실제로 체결됐는지 알기 전에
        # 현금과 보유 수량을 바꿔 버린다.
        ctx.portfolio.cash -= bar.close * 10
        ctx.portfolio.positions[bar.instrument] += 10

    return StrategyDecision.no_action(ctx.now)

올바른 예: 전략은 Decision만 반환함

def on_event(
    self,
    ctx: StrategyContext,
    event: StrategyEvent,
) -> StrategyDecision:
    if not isinstance(event, MarketSnapshot):
        return StrategyDecision.no_action(ctx.now)

    bar = event.bar(self.instrument)
    if bar.close > 70_000:
        # 목표와 실행 정책을 Action으로 명시한다.
        action = SetPortfolioTarget(
            targets=(WeightTarget(
                instrument=self.instrument,
                weight=0.70,
            ),),
            scope=TargetScope.PATCH,
            execution=ExecutionPolicy.next_open(),
        )
        return StrategyDecision(
            schema_version=1,
            as_of=ctx.now,
            actions=(action,),
            reason="price_above_threshold",
        )

    return StrategyDecision.no_action(ctx.now)
SetPortfolioTarget 경로에서는 전략이 목표와 실행 시점을 말하고, 주문 수량 계산, 주문 가능 여부, 체결 가격과 수량, 수수료 반영은 엔진이 담당한다.

Typed Schema

아래 타입은 단순 데이터 묶음이 아니라 컴포넌트 사이의 계약이다. 각 카드에서 생성 주체와 소비 주체를 분리해 보면 엔진 책임 경계가 더 명확해진다.

ctx와 StrategyContext 사용법

ctx는 Python 예약어나 특별한 문법이 아니라 context를 줄여 쓴 매개변수 이름이다. 엔진이 현재 시점의 읽기 전용 조회 객체를 만들어 strategy.on_event(ctx, event)에 넣어준다. 이름을 context로 바꿔도 동작은 완전히 같다.

Context는 전역 상태가 아니다. 전략 호출마다 엔진이 명시적으로 전달하는 의존성이며, 전략은 이를 통해 현재 상태를 읽고 StrategyDecision만 반환한다. 
class StrategyContext(Protocol):
    # 현재 전략 호출의 기준 시각이다.
    @property
    def now(self) -> datetime: ...

    # 선언한 과거 데이터만 읽기 전용 PriceWindow로 받는다.
    def history(self, request: HistoryRequest) -> PriceWindow: ...

    # 포트폴리오는 조회 API만 노출한다.
    def current_weight(self, instrument: InstrumentId) -> float: ...
    def position_qty(self, instrument: InstrumentId) -> Decimal: ...
    def cash(self) -> float: ...
    def portfolio_value(self) -> float: ...
시장 데이터 조회

history()는 현재 시점까지 확정된 과거 데이터만 반환한다. 미래 bar가 섞이면 look-ahead bias가 된다.

포트폴리오 조회

비중, 수량, 현금은 직전 Fill까지 반영된 Snapshot에서 읽는다. 반환값을 통해 상태를 수정할 수는 없다.

공통 Context 구현체

선언한 데이터만 현재 시점까지 잘라서 돌려주는 엔진 소유 객체다.

@dataclass(frozen=True)
class EngineStrategyContext:
    # 엔진이 매 전략 호출마다 채우는 읽기 전용 값들이다.
    now: datetime
    snapshot: PortfolioSnapshot
    history_store: HistoryStore
    # 전략이 반환한 requirements를 엔진이 검증해 보관한 집합이다.
    declared: frozenset[HistoryRequest]

    def history(
        self,
        request: HistoryRequest,
    ) -> PriceWindow:
        # requirements()에 없던 데이터의 즉석 조회를 막는다.
        if request not in self.declared:
            raise UndeclaredDataAccess(request)

        # end=self.now로 미래 데이터 유입을 차단한다.
        return self.history_store.window(
            request=request,
            end=self.now,
        )

    def current_weight(self, instrument: InstrumentId) -> float:
        return self.snapshot.weight(instrument)

    def cash(self) -> float:
        return self.snapshot.cash
전략별 차이는 Context 클래스가 아니라 declared 데이터와 schedule 값이다.

엔진에서 context 주입하기

실행 전에 요구사항을 읽고, 매 시장 시점에 같은 타입의 Context를 채운다.

# 1. 전략 요구사항을 먼저 검증하고 데이터를 준비한다.
requirements = strategy.requirements()
data_feed.prepare(requirements.histories)

for market in data_feed.snapshots():
    # 2. 전략이 선언한 일정이 아닌 날은 호출하지 않는다.
    if not calendar.matches(
        requirements.schedule,
        market.ts,
    ):
        continue

    # 3. 직전 Fill까지 반영된 상태를 읽기 전용으로 고정한다.
    snapshot = portfolio.snapshot(market.ts)

    context = EngineStrategyContext(
        now=market.ts,
        snapshot=snapshot,
        history_store=history_store,
        declared=frozenset(
            requirements.histories
        ),
    )

    # 4. Python 전략은 Context를 읽고 Decision만 반환한다.
    decision = strategy.on_event(
        context,
        market,
    )

    # 5. Action 종류에 따라 목표·청산·주문 경로로 분기한다.
    orders = decision_router.to_orders(
        decision=decision,
        portfolio=snapshot,
        market=market,
    )

    # 6. BrokerSim이 실행 가능한 Order를 체결한다.
    for order in orders:
        for fill in broker.execute(order, market):
            # 7. 실제 상태 변경은 Fill 적용 시점에만 일어난다.
            portfolio.apply(fill)
같은 market 처리 중에는 snapshot이 변하지 않는다. Fill 결과는 다음 Context에서 보인다.
contextvars.ContextVar와는 다른 개념이다. 표준 라이브러리의 ContextVar는 async 작업별 요청 ID 같은 값을 격리할 때 쓰는 도구다. 백테스트 전략 입력은 숨겨진 ContextVar보다 함수 인자로 명시적으로 전달하는 편이 테스트와 재현에 유리하다.
여기서 dict를 남발하지 않는다. YAML/API/JSON 경계에서는 dict가 나와도 되지만, 엔진 내부로 들어오면 dataclass, enum, typed model로 고정한다.

전략별 Context는 무엇이 달라지는가

Context 구현체를 전략마다 새로 만드는 것이 아니다. 모든 전략은 같은 EngineStrategyContext를 받고, 전략별 StrategyRequirements에 따라 Context 안에서 조회할 수 있는 데이터 창과 호출 일정이 달라진다.

전략 가격 데이터 포트폴리오 조회 호출 일정 전략 전용 상태
골든크로스 한 종목 종가 60일 현재 목표 종목 비중 매 거래일 없어도 됨
횡단면 모멘텀 유니버스 전체 종가 252일 전체 종목 현재 비중 월말 거래일 없어도 됨
페어 평균회귀 두 종목 정렬 종가 120일 양쪽 종목 수량과 비중 매 거래일 FLAT/LONG/SHORT regime

Config, Context, State 구분

전략에 필요한 값을 성격별로 분리해야 재현과 테스트가 쉬워진다.

Config
lookback, 임계값, 유니버스처럼 실행 중 변하지 않는 전략 설정.
Context
현재 시각, 과거 가격 창, 포트폴리오처럼 엔진이 제공하는 읽기 전용 상태.
State
진입 regime, cooldown처럼 전략이 다음 호출까지 기억해야 하는 전략 내부 상태.
전략 State는 변경할 수 있지만 Portfolio는 변경할 수 없다. 재현 가능한 재시작이 필요해지면 State도 typed schema로 직렬화하고 실행 로그에 체크포인트를 남긴다.

def on_event(self, ctx, event):
    if not isinstance(event, MarketSnapshot):
        return StrategyDecision.no_action(ctx.now)

    # requirements()에 선언한 종가 창을 Context에서 가져온다.
    closes = ctx.history(
        self.prices
    ).column(self.config.instrument)

    # 급락은 일반 이동평균 규칙보다 먼저 평가한다.
    drawdown = closes[-1] / max(closes) - 1
    if drawdown <= self.config.emergency_drawdown:
        return StrategyDecision(
            schema_version=1,
            as_of=ctx.now,
            actions=(LiquidatePosition(
                instrument=self.config.instrument,
                execution=ExecutionPolicy(
                    style=ExecutionStyle.MARKET,
                    timing=ExecutionTiming.NEXT_OPEN,
                    time_in_force=TimeInForce.DAY,
                ),
                cancel_open_orders=True,
                persistence=LiquidationPersistence.UNTIL_FLAT,
            ),),
            reason="emergency_drawdown_exit",
        )

    # 지표 계산은 엔진이 아니라 전략의 책임이다.
    short_ma = mean(
        closes[-self.config.short_window:]
    )
    long_ma = mean(closes)
    target = (
        self.config.target_weight
        if short_ma > long_ma
        else 0.0
    )

    # 이미 목표 비중과 비슷하면 불필요한 주문을 만들지 않는다.
    current = ctx.current_weight(
        self.config.instrument
    )
    if abs(current - target) < 0.01:
        return StrategyDecision.no_action(ctx.now)

    # 평상시에는 목표 비중 Action을 반환한다.
    action = SetPortfolioTarget(
        targets=(WeightTarget(
            instrument=self.config.instrument,
            weight=target,
        ),),
        scope=TargetScope.PATCH,
        execution=ExecutionPolicy(
            style=ExecutionStyle.MARKET,
            timing=ExecutionTiming.NEXT_OPEN,
            time_in_force=TimeInForce.DAY,
        ),
    )
    return StrategyDecision(
        schema_version=1,
        as_of=ctx.now,
        actions=(action,),
        reason="golden_cross",
    )
같은 전략이 평상시에는 SetPortfolioTarget, 급락 시에는 LiquidatePosition을 반환한다. MA와 drawdown은 Context 필드가 아니라 PriceWindow로부터 계산하는 전략 로직이다.

def on_event(self, ctx, event):
    if not isinstance(event, MarketSnapshot):
        return StrategyDecision.no_action(ctx.now)

    # Context가 시간축을 맞춘 유니버스 전체 가격을 반환한다.
    window = ctx.history(self.prices)
    # 결측이 없는 종목만 lookback 수익률을 계산한다.
    scores = [
        (
            instrument,
            window.column(instrument)[-1]
            / window.column(instrument)[0] - 1,
        )
        for instrument in self.config.universe
        if window.is_complete(instrument)
    ]
    # 수익률이 높은 순서로 정렬해 상위 N개를 고른다.
    ranked = sorted(
        scores,
        key=lambda item: item[1],
        reverse=True,
    )
    selected = frozenset(
        instrument
        for instrument, _ in ranked[:self.config.top_n]
    )
    weight = 1 / len(selected) if selected else 0

    # REPLACE이므로 목록 밖 기존 포지션도 0 비중으로 간주한다.
    targets = tuple(
        WeightTarget(
            instrument=instrument,
            weight=weight if instrument in selected else 0,
        )
        for instrument in self.config.universe
    )
    action = SetPortfolioTarget(
        targets=targets,
        scope=TargetScope.REPLACE,
        execution=ExecutionPolicy(
            style=ExecutionStyle.MARKET,
            timing=ExecutionTiming.NEXT_OPEN,
            time_in_force=TimeInForce.DAY,
        ),
    )
    return StrategyDecision(
        schema_version=1,
        as_of=ctx.now,
        actions=(action,),
        reason="cross_sectional_momentum",
    )
결측 종목을 임의로 0원 처리하면 순위가 왜곡된다. PriceWindow의 정렬 및 결측 정책을 엔진 수준에서 고정해야 한다.

class PairRegime(Enum):

Context 사용

def on_event(self, ctx, event):
    if not isinstance(event, MarketSnapshot):
        return StrategyDecision.no_action(ctx.now)

    # Context가 날짜를 교집합 기준으로 정렬한 가격을 준다.
    window = ctx.history(self.prices)
    left = window.column(self.left)
    right = window.column(self.right)

    # 두 로그 가격의 차이를 표준화해 진입 신호로 쓴다.
    spread = np.log(left) - self.beta * np.log(right)
    sigma = np.std(spread)
    # 분산이 없으면 z-score를 계산할 수 없다.
    if sigma == 0:
        return StrategyDecision.no_action(ctx.now)

    zscore = (
        spread[-1] - mean(spread)
    ) / sigma

    # 전략 State 변경은 허용되지만 Portfolio는 건드리지 않는다.
    if zscore > self.entry_z:
        self.state.regime = PairRegime.SHORT_SPREAD
        action = self.basket(left=-0.5, right=0.5)

    elif zscore < -self.entry_z:
        self.state.regime = PairRegime.LONG_SPREAD
        action = self.basket(left=0.5, right=-0.5)

    elif abs(zscore) < self.exit_z:
        self.state.regime = PairRegime.FLAT
        action = self.basket(left=0.0, right=0.0)

    else:
        return StrategyDecision.no_action(ctx.now)

    return StrategyDecision(
        schema_version=1,
        as_of=ctx.now,
        actions=(action,),
        reason="pairs_mean_reversion",
    )

왜 Rust를 쓰려는가

Rust를 쓰는 이유는 “빠르니까” 하나로 끝나지 않는다. 백테스트 엔진은 반복 루프, 상태 전이, 수치 계산, 회계 규칙이 섞인다. 이 부분을 타입으로 강제하면 버그를 줄이고, 나중에 여러 종목/긴 기간으로 확장할 때 성능 여지도 생긴다.

타입 안정성

Order와 Fill, Cash와 Quantity를 구분해 실수를 줄인다.

재현성

상태 전이 위치를 엔진 내부로 제한해 결과 추적이 쉬워진다.

성능

반복되는 bar loop와 portfolio update를 Python 밖으로 뺄 수 있다.

학습 가치

실거래 엔진과 유사한 event/order/fill 구조를 직접 익힌다.

maturin / PyO3 경계

전략은 Python으로 유지하고, Rust 엔진은 Python 패키지처럼 import한다. maturin은 Rust crate를 Python wheel로 빌드하는 흐름을 단순하게 해준다.

미구현 요구는 실행 전에 실패한다

Capability 검증은 첫 Bar를 읽은 뒤가 아니라 전략 등록 직후 수행한다. 페어 전략이 Basket과 공매도를 요구했는데 엔진이 지원하지 않으면 긴 실행 끝에 이상한 결과를 만드는 대신 즉시 구체적인 오류를 낸다. 

def prepare_strategy(
    strategy: Strategy,
    capabilities: EngineCapabilities,
) -> ValidatedStrategy:
    # 전략 선언은 데이터 루프보다 먼저 한 번만 읽는다.
    requirements = strategy.requirements()

    # Registry 내부 조회는 map이어도 외부 계약은 typed method로 유지한다.
    for action in requirements.actions:
        capabilities.require_action(action)
    for feature in requirements.features:
        capabilities.require_feature(feature)

    # 모든 요구가 통과한 전략만 Context를 받을 수 있다.
    return ValidatedStrategy(strategy, requirements)

검증 기준

엔진은 “돌아간다”가 아니라 “설명 가능한 결과를 낸다”가 기준이다.

단위 테스트

수수료 계산, 수량 변환, drawdown 계산, 포지션 평균단가 갱신을 작게 검증한다.

골든 테스트

아주 짧은 수동 예제로 cash, position, equity가 손계산과 일치하는지 본다.

Zipline 대조

동일 데이터, 동일 전략, 동일 비용 가정에서 equity curve 차이를 비교한다.

회귀 테스트

엔진 수정 후 기존 전략 결과가 의도 없이 변하지 않는지 diff를 남긴다.

계약 테스트

Requirements에서 선언하지 않은 데이터 조회와 Action 반환이 항상 거절되는지 확인한다.

상태 전이 테스트

Order 생성으로는 자산이 바뀌지 않고 Fill 적용으로만 cash와 position이 변하는지 확인한다.
