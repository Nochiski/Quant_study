## 0. 먼저 알아야 할 3가지

1. **병목은 DART 가 아니라 키움이다.** `f_source_map` 은 키움 587,074콜을 "2.0일(40.8h)"로 적었는데 이는 **레이트 제한만 보고 일일 한도를 무시**한 값이다. `plan_O_ops §2-4·§7-2` 가 실측으로 세운 **유일한 검증 안전 한도는 일 20,000콜**이고, 그 기준이면 키움 코어 471,539콜은 **23.6일**이다. DART 코어는 14.7일. 두 채널은 병렬이므로 **전체 wall-clock = 키움 23.6일**이다. `f_source_map`의 "12일"도 `f_critic`의 "18~19일"도 병목을 잘못 짚었다.
2. **현재 상태로는 키움 백필을 시작할 수 없다.** 키움 앱키가 카엘 운영과 공유 중이고(`xcheck/api.py:6` 이 `kael-system-v3/.env` 를 직접 읽는다), 카엘이 이미 검증 한도 20,000콜을 전량 소진한다. **앱키 분리가 R6의 하드 선행조건**이다. 분리 전에는 R3·R4·R5(KRX/DART/KIS)만 돌린다.
3. **스키마를 먼저 고쳐야 한다.** `schema_final.sql` 은 `column_registry` + `v_contract_violations` + `pit_ctx` 트리거로 **미등록 테이블이 있으면 다음 빌드가 정지**하도록 설계돼 있다(fail-closed, 실행 확인 C6/C7). 즉 **수집 도중에 테이블을 추가할 수 없다.** R0에서 누락 테이블·컬럼을 전부 반영하지 않으면 R3 시작 후 R6 도중에 파이프라인이 멈춘다.

### 4-2. 재확인 루프는 **추가 콜 0** 이다

일일 증분 1콜이 이미 과거를 함께 준다 — `ka10060` 100영업일 · `ka10008` 50영업일 · `ka10014` 372영업일.

KRX 날짜축만 예외(1콜=1일) → 최근 5영업일 × 3엔드포인트 = 15콜/일.

### 4-3. 완결성 게이트 (`rows >= 1` 은 전멸만 잡는다)

```
게이트 A (필수, 미달 시 배치 실패)
  daily_prices 적재 종목수 / 기대 상장종목수  >= 0.995
  trading_calendar 당일 행 존재
게이트 B (경고, 배치는 성공)
  investor_flows / foreign_holdings / short_selling / stock_lending  각각 >= 0.98
게이트 C (추세 이탈 — 기대치를 모르는 테이블용)
  당일 rows / 직전 20영업일 rows 중앙값  >= 0.80
게이트 D (자동 재시도 큐)
  ingest_shard.state='failed' → 다음날 배치 앞단 우선 편입
게이트 E (계약)
  SELECT COUNT(*) FROM v_contract_violations = 0   ← 아니면 pit_ctx 가 ABORT
```

**모든 단계가 처리 건수를 반환하도록 규약을 강제한다** — 게이트 C는 그 숫자가 있어야 성립한다. 카엘은 `rows_affected`를 기록해 두고도 비교를 안 해서 51.5% 결손을 놓쳤다.
