## 0. 결론 3줄

1. **병목은 키움이 아니라 DART다.** 키움 23.6일은 존재하지 않는 한도("일 20,000")에서 나온 값이고, 실측 한도는 **API ID별 5콜/s(오류 1700)** 다. 키움 코어는 4TR 병렬 **14.6시간**이다. 남은 최장 채널이 DART이며 **키 1개 13.8일 / 2개 6.9일 / 3개 4.6일**이다.
2. **콜 총량은 거의 안 변한다.** 키움 471,539 → 477,479(+1.3%), DART 275,593~293,593 → 223,569~313,569(중앙 275,619, 사실상 동일). **바뀐 것은 wall-clock 과 커버리지이지 예산이 아니다.**
3. **지금 상태로 백필을 돌리면 조용히 망가진다.** 인증 실패가 `empty` 로 원장에 확정 기록되고(B01), 재개가 원리적으로 동작하지 않으며(B02), 실행 경로가 맥 scratchpad 절대경로에 묶여 서버에서 뜨지도 않는다(B14). **착수 전 S등급 7건은 협상 대상이 아니다.**

## 2. 착수 전 필수 조치 — 우선순위표

각 항목의 "왜 백필 전이어야 하는가" 를 반드시 읽어라. 순서를 바꾸면 안 되는 이유가 거기 있다.

### P0 — 유량 실험 (20,000콜, 약 15분). 이것 없이는 아래 전부가 무의미하다

**키움 공식 오류코드표에 한도가 3층으로 존재한다** (`kael-system-v3/docs/reference/kiwoom_rest_api/sheets/오류코드.tsv:15-17`):

```
12  1700  허용된 API 요청 개수를 초과하였습니다. 유량={?}, API ID={?}     ← 실측됨 (5콜/s)
13  1701  허용된 전체 요청 개수를 초과하였습니다. 총유량={?}              ← 값 모름
14  1702  허용된 그룹 요청 개수를 초과하였습니다. 총유량={?}, API_ID={?}   ← 값 모름
```

우리가 실측한 429는 **524콜 중 21건, 전부 1700, 전부 `ka10001` 단일 TR** 이다(`data/jsonl/phaseA.json` 10건 + `phaseC.json` 11건). **1701·1702 는 한 번도 본 적이 없고 임계값도 모른다.** 카엘 클라이언트조차 `backend/clients/kiwoom/client.py:123-126` 에서 `연속 10회 429 → "일일 한도 초과 추정"` 이라고 **추정**으로 적어 뒀다 — 카엘도 실측한 적이 없다.

- **왜 백필 전인가**: 1701이 계정 단위면 카엘 15,230콜/일 + 우리 477,479콜이 합산된다. 14.6h 계획이 며칠로 갈리고, **백필 12시간째에 처음 맞으면 그 시점에 재설계**다. 그리고 1701이 계정 단위라면 **앱키 분리가 다시 하드 선행조건이 된다** — 우리가 태워 버리면 카엘 운영 배치가 깨진다.
- **어떻게**: `sustain.py` 방식으로 **실제 백필 대상**(`ka10008` 첫 청크 등)을 태운다 → 낭비 0. 지난 5,204콜이 그대로 R6-4/R6-5 원장이 된 것과 같다.
- **언제**: **카엘 배치 창(20:05~22:55 KST) 밖**에서. 1701이 계정 단위일 가능성이 있으므로 카엘이 도는 중에 하면 안 된다.
- **관측**: 429 본문의 `1701`/`1702` 출현 여부와 누적 콜 수. 복구 시간이 419~759ms(1700 수준)인지 자정까지인지.

### S등급 — 백필이 **조용히** 망가진다. 협상 대상 아님

#### DEFECT-B01: `return_code` 미검증 — 인증 실패가 `empty` 로 확정 기록되어 해당 종목이 영구 skip 된다
- **상황**: `backfill_kw.py` 를 4TR × 2,763종목으로 14.6시간 무인 실행. `TOK` 는 `backfill_kw.py:61` 에서 **import 시 1회만** 발급되고 이후 갱신되지 않는다. `api.py:78` 의 캐시 만료 판정은 응답의 `expires_dt` 가 아니라 **하드코딩 12h** 이며, 시작 시점에 이미 6시간 지난 캐시를 물면 실행 중 만료된다.
- **인풋**: ① `python3 backfill_kw.py --tr ka10008,ka10060,ka20068,ka10014 --from 20100101` ② 실행 6시간째 토큰 만료 → 이후 모든 POST 가 인증오류 또는 `200 + return_code≠0` ③ 각 종목의 **첫 청크**에서 이 응답 수신
- **에러 위치**:
  - `src/backfill_kw.py:105-116` — `call()` 의 재시도 루프가 검사하는 실패 조건은 `status_code == 429` 와 `return_code == 5` **둘뿐**. 그 외 모든 응답은 `:113 return j, False, n429` 로 **성공 처리**된다.
  - `src/backfill_kw.py:118-121` — `extract()` 가 `next((v for v in j.values() if isinstance(v,list)), [])` 로 오류 바디에도 `[]` 를 돌려준다.

### 왜 이 순서인가 — 판정 근거

**① DART 를 가장 먼저 켠다.** 계획서는 "키움이 병목"이라 키움을 앞세웠다. 병목이 DART 로 이동했으므로 **가장 긴 채널을 가장 먼저 시작**한다. 특히 R4-2(`list.json` 스윕)는 밴드가 34,000~76,000 으로 ±2.1일이라, 먼저 돌려서 **실측 `total_count` 를 누적**해야 나머지 일정이 확정된다.

**② 키움은 "싼 것부터"가 아니라 "긴 것부터"다 — 계획서 순서 권고를 뒤집는다.**
계획서(`COLLECT_PLAN.md:166`)는 `R6-1·2 → R6-5 → R6-3 → R6-4 → R6-6` 을 권고했다. 이는 **일 20,000콜 직렬 실행**을 전제한 순서다. 4TR 병렬에서는 임계경로가 `ka10008`(230,429콜 = 14.6h) 하나이고 나머지는 그 안에 다 끝난다(`ka10060` 7.2h / `ka20068` 6.7h / `ka10014` 1.7h). **`ka10008` 을 1분이라도 늦게 켜면 그만큼 전체가 늦는다.**
다만 계획서의 근거("첫날에 벤치마크와 프로그램매매를 확보해 R3~R5 검증을 바로 시작")는 유효하므로 **`ka20006`+`ka90010` 116콜을 맨 앞에 붙인다 — 26초면 끝난다.** 순서: `[ka20006·ka90010 116콜, 26초] → [ka10008 단독 30분 관측] → [나머지 3TR 합류]`.

**③ `ka10008` 30분 단독 관측을 넣는 이유.** P0 유량 실험이 15분짜리라 **누적 한도(1701)를 배제하지 못한다.** 임계경로 TR 을 단독으로 30분(약 7,900콜) 돌려 1701 미출현을 한 번 더 확인한 뒤 나머지를 합류시킨다. 실패해도 손실은 30분이다.

**④ R3-2(KRX 마스터)는 종목축 예산의 선행조건인가 — 부분적으로만 그렇다.**
계획서는 `COLLECT_PLAN.md:96` 에서 "**R3-2 완료 전에는 어떤 종목축 예산도 확정하지 마라**"고 경고했다. **키움에 대해서는 이 경고를 완화한다.** 폐지종목은 키움이 `rc=0`+0행을 주므로 **종목당 1콜**이다. D 가 717이든 1,494이든 4개 TR 합계로 **2,868~5,976콜, 최대 차이 3,108콜(11분)** 이다. 예산에 실질 영향이 없다.
**단 KIS 에 대해서는 경고가 그대로 유효하다.** R7 폐지 공매도는 종목당 41청크이므로 D 의 불확실성이 **29,397 ↔ 61,254콜(2.7h 차이)** 로 직결된다. 그래서 R7 을 D3(R3-2 완료 후)로 배치했다.
**그리고 정확성에 대해서는 여전히 하드 선행조건이다** — 폐지 티커 목록 자체를 R3-2 없이는 만들 수 없다. 목록 없이 생존 2,763만 돌면 **26.75% 생존편향이 원장 단계에서 확정**되고, 키움 로그는 100% 정상으로 보인다.

**⑤ 전기간 종목 합집합 N_all — 계획서의 4,257 은 과대가 아니라 과소일 수 있다.**
`equity_test.db:stock_master` 는 4,073영업일 중 **29일(0.7%)만 표본**인데 이미 다음을 준다:

**반증되지 않은 것**: 2010-01-04 종목 1,961 중 603개 소멸(`krx.db` 재조회 **1,961 / 2,763 / 603 정확 일치**), 오늘 상장 2,763(SECUGRP 합계 2,715+23+12+10+2+1 = **2,763 정확 일치**), 보통주 1,731(2010-01-04) → 2,602(2026-08-20). **계획서가 맞았다. 재검토 금지.**

**⑥ 앱키 분리는 선행조건인가 — 조건부다. 검토 A와 D의 충돌을 이렇게 판정한다.**
검토 A: "1700이 API ID별이므로 시나리오 A(공유 유지)가 불가능→가능. 앱키 분리는 최적화이지 선행조건이 아니다."
검토 D: "1701/1702 미검증이 blocking."
**판정: A 가 옳되 조건부다.** 1700(초당 유량)에 대해서는 A 가 맞다 — 카엘이 쓰는 api-id 는 `ka10001·ka10099·ka10081·ka10059·ka20003·ka10068·ka10016·ka10027·ka10032·ka20006·ka20001·ka10051·ka90010` 이고, **우리 4개 TR(`ka10014`·`ka20068`·`ka10060`·`ka10008`)과 겹치는 것은 0개**다(로컬 카엘 저장소 grep 재확인). 특히 `ka10014` 는 `backend/clients/kiwoom/market_client.py:129-134` 에 `get_short_selling()` 으로 **정의만 있고 호출자가 0곳** — dead code 다.
**그러나 1701(전체 유량)이 계정 단위라면 앱키 분리는 즉시 하드 선행조건으로 복귀한다.** 그래서 P0 실험이 앱키 분리 여부를 **결정**한다. 순서상 P0 가 첫 번째인 이유다.

**⑦ 앱키를 공유하면 1700과 무관하게 토큰이 충돌한다 — 분리를 권고하는 별개 근거.**
카엘: `backend/clients/kiwoom/auth.py:11-13` — `data/.kiwoom_token.json`, 유효 22h, 만료 600초 전 갱신.
우리: `src/api.py:70,78` — `src/.kw_token.json`, 캐시 판정 **하드코딩 12h**.
같은 앱키로 양쪽이 독립적으로 재발급하면, 키움이 재발급 시 이전 토큰을 무효화하는 정책일 경우 **나중에 발급한 쪽이 앞선 쪽을 죽인다.** 캐시 수명이 22h vs 12h 로 달라 어긋나는 시점이 매일 생긴다. **이것은 유량과 무관한 별개의 사고 경로**이고, 우리 쪽 실패는 B01 때문에 `empty` 로 원장에 기록된다.
**→ 1701 결과와 무관하게 키움·DART 앱키를 분리 발급한다.** DART 는 무료·즉시 발급이므로 **최소 2개, 가능하면 3개**(병목이 6.9일 → 4.6일).

**⑧ `ka10099`(R1-E2 소멸성)는 카엘과 겹친다.** 카엘 `backend/pipeline/daily_pipeline.py:236` 이 `ka10099` 를 쓴다. 일 2콜이라 5콜/s 한도에는 영향이 없지만 **같은 초에 쏘지 않도록** 우리 배치를 19:00 KST 로 고정한다(카엘 08:00 KST).

### S5. 카엘과의 시간 분리

**배포안의 전제("카엘 cron 은 11:05·11:30 두 개")는 틀렸다. 실제 30개다.** 그리고 `chain:daily_all` 은 한 점이 아니라 **UTC 11:05 → 13:42 (KST 20:05 → 22:42) 2시간 37분 구간**이다 (`pipeline_runs` 실측: 2026-08-21 11:05:01→13:27:50, 08-20 13:36:37). 내부 단계:
