# S06: 키움 모의 브로커 계약 조사

이 작업은 감당 가능한 위험 안에서 비용 후 수익을 내는 자동매매를 위해, S05 오프라인 실행 기반을
키움 모의계좌에 연결할 때 **로컬 주문 상태와 키움의 주문·체결·계좌 사실이 어디서 어긋날 수 있는지**를
연결 전에 줄인다. 이 문서는 키를 쓰지 않고 공개 공식 문서만 읽은 결과다. 실제 계좌 연결·주문은 하지
않았고, 이 문서만으로 연결·주문을 실행하지 않는다. 확인하지 못한 항목은 "미확인", 모의 계좌로만 답할 수
있는 항목은 "③ 실측"으로 남긴다.

## 목적과 연구 질문

- **목적:** S05 `BrokerPort`(`application/offline_execution/ports/outgoing/execution.py`)를 키움 모의로
  구현하기 전에 인증·호출 한도·주문·체결 이벤트·조회 페이지·취소 의미와 모의/실전 분리를 고정한다.
  사용자마다(동민·상목) 자기 PC에서 자기 모의 계좌를 연결하는 데 필요한 등록 조건도 확인한다.
- **가장 먼저 답할 질문:** 주문 응답(ACK)을 잃었을 때 그 주문을 다시 찾을 수 있는가.
- **불확실성:** 주문 요청에 우리 주문 ID를 실을 수 있는지, 계좌가 요청 인자인지 키에 묶이는지, 체결량
  필드가 누적인지 건별인지, 현금 필드가 S05 현금 의미와 맞는지.

## ACK 유실 재식별 규칙 (초안)

우리 주문 ID를 키움에 실을 수 없으므로 주문 내용과 시각으로 찾는다. S05의 "UNKNOWN 조회 부재는 자동
재발주하지 않는다"를 그대로 지킨다.

1. 전송 직전에 어댑터가 의도·전송 시각을 저장한다(주문번호 칸은 비어 있음). 저장 실패면 보내지 않는다.
2. 주문번호가 비어 있는 의도는 다음 조회에서 당일 `kt00007` 행 중 아래를 모두 만족하는 후보를 찾는다.
   - `comm_ord_tp` = REST API (영웅문 수동 주문 제외). 2026-10-20 모의 실측에서 REST 주문은 "모의투자"로
     남았다. 모의에서 HTS 주문도 같은 표기인지는 미확인이라, 같은 내용의 HTS 주문이 있으면 후보 2건으로 정지한다
   - 종목·매수/매도·주문수량·주문단가·매매구분이 같다(지정가는 명세 "지정가"·"보통", 모의 실측 "보통가")
   - 원주문(`ori_ord`)이 `0000000`이다(정정·취소 행 제외)
   - 주문 시각이 전송 시각 − 여유 이후다. 여유 값은 ③에서 키움 시각과 PC 시각 차이를 재고 정한다
   - 다른 의도에 이미 묶인 주문번호가 아니다
3. 후보가 **정확히 1개**면 묶는다. **0개거나 2개 이상**이면 묶지 않는다. 그 의도는 대사에서 불일치가
   되어 S05 서비스가 신규 주문을 정지하고, 후보 목록을 사람이 확인한다.
4. S05 서비스는 대사가 맞지 않으면 신규 전송을 막으므로 미해결 의도는 한 번에 하나뿐이다. 같은 키로
   다른 프로그램이 같은 내용의 주문을 내면 후보가 2개가 되어 정지한다.

## BrokerPort 대응 (제안)

| S05 포트 | 키움 호출 | 처리 |
|---|---|---|
| `snapshot()` | `kt00007`(당일 주문 전 페이지) → `kt00018`(보유) → `kt00001`(현금) → `kt00007` 재조회 | 두 번의 주문 조회가 다르면 다시 읽는다. 정한 횟수 안에 같아지지 않으면 `BrokerError`(판정 없음). 조회 도중 도착한 체결을 이렇게 함께 대사한다 |
| `submit(intent)` | 전송 기록 → `kt10000`/`kt10001`(`KRX`, `trde_tp` 0 지정가) → 주문번호 저장 | 응답은 접수 확정이 아니므로 결과 상태는 조회로 확정한다 |
| `cancel(intent_id)` | `kt10003`(원주문번호, 수량 0 = 잔량 전부) | 취소 결과도 조회로 확정한다 |

- **주문 상태:** `kt00007`의 주문수량·체결수량·주문잔량·정정취소 표시로 OPEN·PARTIAL·FILLED·CANCELLED를
  정한다. 거부가 이 조회에 어떻게 남는지는 ③ 실측이다.
- **체결대금·비용:** 체결수량 × 체결단가(평균인지 ③ 실측), 수수료·세금은 `tdy_trde_cmsn`·`tdy_trde_tax`
  (주문별 누적인지 ③ 실측).
- **현금:** S05 `cash_krw`(예약 포함 전체 현금)에 맞는 키움 필드는 미확정이다. 후보는 `d2_entra`(D+2
  추정예수금)와 `entr`(예수금)이며 체결 직후 어느 값이 움직이는지 ③에서 잰다. 예약현금은 키움 미체결
  매수(`ka10075` 미체결수량 × 주문가격)와 의도의 비용 예산으로 계산한다.
- **어댑터가 모르는 주문:** 수동 주문 등 의도에 묶이지 않은 주문은 `kiwoom-untracked-<주문번호>` 의도로
  snapshot에 넣는다. S05 `reconcile`이 "untracked broker order"로 판정해 신규 주문을 막는다.

### 포트 계약 판정: 변경 없음 (제안)

키움에는 우리 `intent_id`도, S05 `OrderFact.revision`도 없다. 두 가지를 키움 어댑터 안에서 해결하고
S05 포트·도메인·원장은 바꾸지 않는 것을 제안한다.

- **선택:** 어댑터가 자기 전용 참조 원장(SQLite 파일 하나)에 `intent_id ↔ 주문번호`, 전송 기록, 마지막
  관측값, revision 번호를 둔다. revision은 관측한 누적값(상태·체결수량·체결대금·비용)이 바뀔 때만 1씩
  올린다. 같은 상태를 여러 번 읽어도 같은 revision이 나온다.
- **대안:** S05 원장과 `OrderFact`에 브로커 주문번호 칸을 더하고 `snapshot`이 원장의 의도 목록을 받게
  포트를 바꾼다.
- **선택 이유:** S05 포트 문서가 이미 "intent_id 조회는 가짜 브로커에서만 보장한다"고 적어 어댑터 쪽
  대응을 전제했다. ACK 유실 대비로 전송 전 기록을 어차피 어댑터가 가져야 한다. 포트를 바꾸면 S05
  도메인·원장 스키마·가짜 브로커까지 함께 바뀐다. 두 파일이 어긋나면(예: 참조 원장 삭제) 대사 불일치로
  정지하는 쪽으로 실패한다.

## 계좌 대조와 모의 보장 (제안)

1. 주소는 `https://mockapi.kiwoom.com`·`wss://mockapi.kiwoom.com:10000` 허용 목록만 쓴다. 실전 주소는
   코드에서 막고, 실전으로 넘어가는 fallback은 두지 않는다.
2. 토큰 발급에서 8030이 오면 "실전 키로 보입니다"로 연결을 멈춘다. 8050·8010은 IP 등록 안내로 멈춘다.
3. 토큰을 받은 직후 `ka00001`의 계좌번호를 사용자가 입력한 계좌번호와 비교한다. 다르면 주문을 막는다.
4. 응답에는 모의 여부 필드가 없으므로 "모의 계좌인가"는 1·2로 보장하고, 계좌번호 끝 2자리 해석에
   기대지 않는다.
5. 주문 범위는 `dmst_stex_tp` = KRX(NXT·SOR 금지), `trde_tp` = 0(지정가)만 쓴다. 신용 주문(`kt10006`~
   `kt10009`)·미국주식·금현물은 쓰지 않는다.

## ②-1 구현: 키움 모의 어댑터

`adapters/outbound/kiwoom_mock`이 S05 `BrokerPort`를 구현한다. S05 포트·도메인·원장·서비스는 바꾸지
않았다. bootstrap·HTTP·키 저장에는 연결하지 않았고(②-2·②-3), 테스트는 공식 명세 예시 모양의 가짜
서버로만 돈다. 네트워크 호출은 없다.

- **통신:** 표준 라이브러리 HTTP. 주소는 `https://mockapi.kiwoom.com` 상수 하나이고 경로만 받으며,
  리다이렉트를 따라가지 않는다. TR마다 1.1초 간격을 지키고 `cont-yn`·`next-key`로 모든 쪽을 읽는다.
  토큰은 메모리에만 두고, 조회 TR이 8005면 한 번만 새 토큰으로 다시 읽는다. 주문 TR은 다시 보내지 않는다.
- **연결 차단:** 새 토큰을 받을 때마다 `ka00001` 계좌를 설정한 계좌번호와 대조한다. 8030·8031(실전/모의
  불일치), 8010·8040·8050·8103(IP·단말), 8001·8002·8020(키 검증), 계좌 불일치는 사유 코드
  (`KiwoomBlock`)와 함께 모든 조회를 실패시킨다. 참조 원장은 처음 연결한 계좌의 지문에 묶여 다른 계좌로
  열면 거부한다.
- **참조 원장:** 어댑터 전용 SQLite(application_id `0x4B574D4B`)가 의도 ↔ 주문번호, 전송 직전 기록,
  마지막 관측 사실과 revision, 정지 래치를 둔다. revision은 관측한 (상태·체결수량·체결대금·비용)이 바뀔
  때만 오르고, 전이는 S05 `classify_event`로 검증한다. 재시작해도 같은 상태는 같은 revision이다.
- **조회:** `kt00007` → `ka10076` → `kt00018` → `kt00001` → `kt00007`. 두 번 읽은 주문이 다르면
  처음부터 다시 읽고, 3번 안에 같아지지 않으면 판정 없이 실패한다. 예약현금은 키움 사실이 아니라 추적 중인
  매수 주문으로 계산한 값이다.
- **보내지 않은 의도는 거부로 확정:** 기본값인 미전송(`transmit=False`), 6자리 KRX 코드가 아닌 종목,
  주문 직전 연결 실패는 키움을 부르지 않고 `REJECTED`로 기록한다. 보내지 않은 것이 확실하므로 결과를
  모름으로 두지 않는다. S05 서비스는 이미 그 의도를 UNKNOWN으로 저장한 뒤 어댑터를 부르므로, 오류로
  끝내면 영구 불일치가 된다.
- **응답 유실:** [재식별 규칙](#ack-유실-재식별-규칙-초안) 그대로 후보가 정확히 1건일 때만 묶는다. 추가
  규칙 하나: 키움이 0이 아닌 `return_code`로 답했고 후보도 0건이면 `REJECTED`로 확정한다. 응답이 없었으면
  (시간 초과·읽을 수 없는 응답) 묶지 않고 S05 대사가 멈춘다. 거부로 확정한 의도는 나중에 같은 내용의
  주문이 보여도 다시 묶지 않는다.
- **날짜 넘김:** `kt00007` 당일 조회에서 어제 주문이 빠져도 대사가 이어지도록, 지난 날의 주문은 참조
  원장의 마지막 관측으로 낸다. 끝나지 않은 주문은 그 주문일자로 `kt00007`을 한 번 더 읽어 확정하고, 남은
  잔량은 장 마감으로 소멸한 `CANCELLED`로 본다. `ka10076` 수수료는 당일만 읽히므로 마지막 같은 날 관측 뒤에
  체결이 늘었으면 비용을 알 수 없어 멈춘다. 그래서 거래일마다 장 마감 뒤 조회를 한 번 돌리는 운영을 둔다.
- **수동 주문:** 어댑터에 묶이지 않은 당일 신규 주문은 `kiwoom-untracked-<주문일>-<주문번호>`로 낸다.
  시장가처럼 S05 값 타입에 맞지 않는 값은 형식만 맞춘 자리표시값이며 판정은 이름으로만 한다.
- **멈춤의 두 종류:** 수수료 행이 체결을 따라오지 못했거나 주문이 계속 바뀌는 것은 일시적 실패라 다음
  조회에서 다시 본다. 해석과 맞지 않는 응답(정정 행, 잔량·체결·취소로 설명되지 않는 행, 수량 초과, 음수
  현금, 비용 예산 초과 등)은 정지 래치를 건다. 래치는 사람이 `clear_latch`로 풀기 전까지 모든 조회를 막는다.
- **연결이 끊기면:** S05 서비스는 전송 직전에 반드시 조회·대사를 하므로, 조회가 실패하면 신규 주문이
  나가지 않는다. 실시간 웹소켓은 이 PR에서 쓰지 않는다. S05의 조회 대사 모델은 REST 조회만으로 충분하다.
- **③ 전까지의 가정:** 현금은 `d2_entra`, 체결대금은 체결수량 × 체결단가(평균), 비용은
  `tdy_trde_cmsn` + `tdy_trde_tax`이고 주문의 수수료 행 체결수량 합이 체결수량과 같아야 한다. 거부는
  `acpt_tp`의 "거부"로 본다. 재식별 시각 여유는 60초다. 가정이 틀리면 대사 불일치나 래치로 멈추고, 값을
  고쳐 쓰지 않는다.
- **2026-10-20 모의 실측으로 확인·수정한 것:** 삼성전자 1주 매수·매도·미체결 취소에서 현금은 `d2_entra`가
  체결 즉시 움직였고(`entr`는 결제 전이라 그대로), 비용은 `ka10076`의 주문별 수수료(0.35%, 10원 미만 버림)와
  매도 거래세(0.2%)의 합이었으며, 세 건 모두 S05 대사가 일치했다. `kt00007` 표기가 명세 예시와 달라(통신구분
  "모의투자", 매매구분 "보통가", 접수구분 "주문완료", 원주문 정정취소 "일반", 취소 행은 같은 주문구분에 "취소")
  재식별 후보 판정을 고쳤다. 주문 거부는 행을 남기지 않고 응답 오류로 왔다(공매도 이수 전용 계좌 RC5006).

## ②-2 구현: 키 저장과 연결 확인 API

- **저장:** 앱 키·시크릿·계좌번호를 AI 공급자 키와 같은 사용자 설정 폴더의 `secrets.json`(저장소 밖,
  POSIX 0600 / Windows 현재 사용자 전용)에 항목 하나(`broker.kiwoom_mock`, JSON)로 둔다. 세 값을 한 번에
  바꿔 키와 계좌가 엇갈리지 않게 한다. 저장소 인스턴스는 어시스턴트와 하나를 함께 쓴다.
- **API:** `GET`·`PUT`·`DELETE /api/v1/broker-connections/kiwoom-mock`, `POST …/verify`. 응답에는 저장 여부와
  계좌번호 끝 4자리만 싣는다. 요청 칸은 OpenAPI `writeOnly`이고, 본문 검증 실패도 입력값을 돌려보내지
  않는다. 계좌번호는 숫자 10자리이며 `-`는 지운다.
- **연결 확인:** 사용자가 누를 때만 키를 쓴다. 토큰 발급과 `ka00001` 계좌 대조만 하고 주문하지 않는다.
  결과는 `connected`·`not_saved`·`mode_mismatch`(8030·8031)·`ip_not_allowed`(8010·8040·8050·8103)·
  `auth_failed`·`account_mismatch`·`no_response`·`refused` 코드와 한글 문장이다.
- **TLS:** python.org macOS 빌드는 기본 인증서 목록이 비어 있어 TLS 확인에 실패했다(10-20 실측). bootstrap은
  `truststore`가 있으면 OS 신뢰 저장소로 연결한다.
- **e2e:** `STRATEGY_WORKBENCH_BROKER_FAKE_PROBE=1`이면 키움을 부르지 않는 대본 probe를 쓴다.
- **아직 아닌 것:** 설정 화면(②-3), 저장한 키로 주문 어댑터를 조립하는 실행 진입점(③·S07).
  "공매도 이수 전용" 같은 계좌 종류는 연결 확인으로 가릴 수 없다(주문해야 RC5006로 드러난다).

## ②-3 구현: 설정 화면과 연결 안내

- **화면:** 설정(`/settings`)에 "키움 모의투자 연결" 섹션을 더했다(`features/configure-kiwoom-mock`). 저장 여부와
  계좌번호 끝 4자리, App Key·App Secret·모의 계좌번호 저장 폼, "연결 확인", 삭제 확인이 있다. 키 입력은
  비제어 입력이라 저장 요청으로만 가고 화면 state·react-query 캐시에 남지 않는다(AI 키 설정과 같은 규칙).
  연결 확인 결과 문장은 서버가 완성한 한글 문장을 그대로 보인다.
- **스토리:** US-SM-18(한상목이 자기 PC에서 자기 모의 계좌를 연결하고 확인한다). e2e는 대본 probe로 돈다.
- **안내 문서:** `docs/manual/strategy-workbench/kiwoom-mock-connection.md` — 신청, 모의투자 탭, IP 등록,
  '계좌 등록하기', 키 다운로드, 결과별 대처, 공매도 이수 전용 계좌 주의, 자동 해지.

## 신청·발급·IP 등록 절차

공식 이용안내 기준이다. 로그인 뒤 화면은 직접 확인하지 못했으므로 ②-3 연결 안내 문서에서 실제 화면으로
다시 맞춘다.

1. 키움 계좌를 만들고 HTS ID를 연결한다.
2. 키움 홈페이지 **모의투자 → 상시모의투자 → 주식/선물옵션 → 안내**에서 모의투자를 신청한다(무료).
3. REST API 포털 오른쪽 위 **API 사용신청**에서 로그인하고 약관에 동의한다.
4. **모의투자 App Key 관리** 탭에서 지금 PC의 공인 IP를 등록한다('현재 나의 IP'로 확인, 최대 10개).
5. 계좌 등록(계좌 비밀번호 + SMS 인증)을 마친다.
6. App Key·App Secret을 내려받는다. **다운로드는 1회만** 가능하며 `계좌번호_appkey.txt`·
   `계좌번호_appsecret.txt`로 저장된다.

주의할 점:

- 가정 회선은 공인 IP가 바뀔 수 있다. 바뀌면 8050이 나고 4번을 다시 해야 한다.
- 이용안내에 따르면 3개월 동안 REST API **실서버**에 접속하지 않으면 매월 첫 영업일에 자동 해지되며,
  모의 서버만 쓰면 해지될 수 있다. 해지되면 다시 신청한다.
- 모의 투자원금·이용 기간·만료 조건은 공개 문서에서 찾지 못했다(미확인).

## 진행·보류·기각 조건

- **진행:** 이 조사로 Q1 재식별 규칙, Q12 계좌 대조, Q11 키 분리, Q10 IP 조건이 정해졌다. ②-1 어댑터는
  키 없이 녹화·합성 응답으로 구현·검증할 수 있다.
- **보류:** 모의 키 발급이나 IP 등록이 안 되는 환경이면 ③ 실측만 보류한다. ②는 키 없이 진행한다.
- **기각·재설계:** ③에서 다음이 나오면 해당 설계를 다시 정한다.
  - 같은 내용의 주문을 시각으로도 가를 수 없어 재식별이 자주 0개·2개 이상이 된다
  - 주문 조회의 체결 수량이 실시간 이벤트·잔고와 맞지 않는다
  - S05 현금 의미에 맞는 키움 현금 필드가 없다(대사 범위를 줄일지 사용자 결정이 필요)

## ③ 모의 실측 목록

모의 체결은 실전 시장충격·용량의 증거로 쓰지 않는다. 항목별 결과는 [2026-10-20 실측 기록](S06-mock-measurement-2026-10-20.md)에 있다.

1. 실시간 911 체결량·915 단위체결량·903 체결누계금액이 누적인지 건별인지, 같은 체결이 두 번 오는지
2. `kt00007` 체결단가가 평균인지, 반올림 규칙(어댑터는 평균으로 가정)
3. 수수료·세금 필드가 주문별 누적인지, `ka10076` 행이 주문당 하나인지 체결 건별인지, 모의 수수료율
4. 체결 직후 `entr`·`d2_entra`·`ord_alow_amt` 중 무엇이 움직이는지(어댑터는 `d2_entra`로 가정)
5. 주문 거부가 응답 오류로 오는지, 접수 뒤 이벤트로 오는지, `kt00007`에 남는지(어댑터는 `acpt_tp` "거부"로 가정)
6. 한도 초과 응답의 HTTP 상태와 그 주문이 접수되지 않았는지
7. 주문번호가 하루·계좌 안에서 유일한지, 영업일이 바뀌면 다시 쓰이는지
8. 토큰을 다시 받으면 이전 토큰이 무효가 되는지
9. 모의에서 지정가 주문을 08:30~09:00에 내면 시가 단일가에 참여하는지, 매매구분별 지원 범위
10. 웹소켓이 끊긴 사이의 체결이 다시 오지 않는지(조회로 메워지는지)
11. 키움 주문 시각과 PC 시각의 차이(재식별 여유 값, 지금 60초)
12. 모의에서 `kt00007`에 지난 주문일자(`ord_dt`)를 넣어 조회되는지, 장 마감 뒤 미체결 잔량이 어떻게 남는지
13. 취소 확인 행의 `mdfy_cncl`·`cnfm_qty` 표기와 원주문 `ord_remnq` 변화
