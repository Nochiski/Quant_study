## PR 작성 규칙 (작성자용)

PR body는 아래 구조를 따른다.

```markdown
## 배경
[이슈 링크 + 왜 이 작업이 필요한지 1-2문장]

## 기존 문제점
[현재 코드에서 구체적으로 뭐가 잘못되었는지 bullet point]

## 변경 내용
[실제로 무엇을 수정했는지 bullet point]

## 제약사항
[변경 불가능한 조건. 예: 기존 API 호환성 필수, 특정 라이브러리 버전 제약 등]

## 설계 결정
### N. [결정 사항 제목]
- **선택**: [실제로 선택한 방법]
- **대안**: [고려했지만 선택하지 않은 방법]
- **선택 이유**: [왜 이 방법을 골랐는지]

## Test plan
- [ ] 기존 테스트 통과 (회귀 확인)
- [ ] 추가 테스트 통과 (새 동작 검증)
- [ ] 문서 갱신 필요 여부 확인 — 아키텍처·스택·규칙 변경 시 `.claude/rules/`·README 동반 갱신 (불필요하면 체크만)

## 관련 컨텍스트
[관련 이슈/PR 링크, cross-repo 참조]

Closes #이슈번호
```

설계 결정 섹션 생략 기준:
- **작성**: 여러 대안 중 하나를 선택한 경우, 호환성 제약이 있는 경우, 새 패턴 도입
- **생략**: 버그픽스, 변수명/포맷 수정, 문서/테스트 추가 (선택의 여지 없음)

## PR / 코드 리뷰 규칙 (리뷰자용)

PR 리뷰 또는 코드 분석을 에이전트에 위임할 때:

1. **리뷰 대상의 컨텍스트를 먼저 완전히 파악**
   - PR 설명/본문, 관련 이슈, 로드맵을 반드시 읽고 **의도된 범위와 제약**을 이해
   - "이 PR은 뭘 하려는 건지, 뭘 일부러 안 한 건지" 구분

2. **리뷰어 프롬프트에 스코프 제약을 명시**
   - "이 PR은 Phase N이며 인프라만 구축하는 것이 의도된 범위" 등
   - 의도적으로 포함하지 않은 항목을 명시

3. **리뷰 결과 종합 시 PR 의도와 교차 검증**
   - "의도된 제한"과 "실수로 빠진 것"을 구분하여 보고

## 결함 / 이슈 보고 형식

결함이나 회귀 위험을 issue / findings.md / PR body / docstring 에 기술할 때는 다음 4요소를 모두 명시한다. 단순 "X 가 잘못됨" 류 한 줄 묘사 금지. (코드 안 예외/로그 메시지의 진단 디테일은 `.claude/rules/error-messages.md`.)

1. **상황 (Setup)**: 어떤 사전 상태 / 조건에서 발생하는가. fixture, 호출 시퀀스, 데이터 기간·유니버스 등
2. **인풋 (Input)**: 정확히 어떤 호출 / 파라미터가 들어가는가 (함수 인자, 설정 값, 입력 데이터 특성)
3. **에러 위치 (Where)**: 어느 파일·라인의 어떤 로직에서 발생 / 잘못 동작하는가 (`path/to/file.py:LL-LL` 인용)
4. **위험성 (Why dangerous)**: 이 동작이 왜 spec/기대와 다른가. 어떤 시나리오에서 실제 손실로 이어지는가. 비결정 / silent corrupt / look-ahead bias / 데이터 손실 등 카테고리 명시

### 예시 (issue/findings 양식)

```markdown
### DEFECT-NNN: <한 줄 요약>

- **상황**: <fixture 또는 사전 상태>
- **인풋**:
  1. <step 1 — 호출 + 파라미터>
  2. <step 2 — ...>
- **에러 위치**: `path/to/file.py:LL-LL` — <어떤 함수의 어떤 로직>
- **위험성**: <왜 기대와 다른가, 어떤 시나리오에서 실제 사고>
- **재현 test (있으면)**: `tests/.../test_*.py::test_name`
```

위 4요소가 다 채워지지 않으면 fix priority 판단 자체가 불가능하다. 한 줄 짜리 "X 가 deprecated", "Y 가 stale" 같은 표현은 cleanup 영역으로 분리하고, 진짜 결함은 위 양식으로 기록한다.
